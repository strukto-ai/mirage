## How To Read This Matrix

Use this page to pick the first VFS to try. If you want the fastest path, start with RAM or disk. If you need real integrations, jump from the setup guide to the VFS docs.

The **Access** column separates filesystem access from API actions. `read`, `write`, and `exec` are `MountMode` values; `exec` allows commands to launch binaries from the mount and is typically used with Disk or RAM. `actions` means the VFS also exposes mutating commands such as sending a message or creating an issue; run those commands on a `WRITE` mount. The **Docs** column shows where each VFS is available, with one icon per supported runtime: <Icon icon="python" /> Python, <Icon icon="node-js" /> TypeScript (Node), and <Icon icon="globe" /> TypeScript (Browser). Click an icon to jump to that runtime's docs.

Sections below mirror the **Setup** sidebar so you can pick a category and follow the same path through credentials → VFS docs.

Every VFS accepts `read: bounded`. `read: fresh`, which revalidates cached bytes against the backend before serving them, is accepted today only by the S3-compatible family and GridFS — the backends whose `stat` and read stamp the same kind of content token. Any other mount declaring it is refused at mount time rather than downgraded. This list is maintained by hand for now and grows one backend at a time as each learns to stamp a read fingerprint.

## Recommended Starting Points

- Use [RAM](/python/vfs/ram) if you want to learn Mirage itself.
- Use [Disk](/python/vfs/disk) if you want local file interoperability.
- Use [S3](/python/vfs/s3) or [GitHub](/python/vfs/github) if you want a realistic first external integration.
