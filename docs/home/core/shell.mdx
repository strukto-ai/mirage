Every line runs as a non-interactive Bash runs it (`bash -c`), joined by
pipes, redirects, variables and control flow. A session keeps its working
directory, variables and functions between calls.

[CLIs](/home/setup/clis) and programs on [machines](/home/setup/machine/overview)
run in the same lines.

```bash
$ cd /s3/logs
$ for f in *.jsonl; do echo "$f $(grep -c error "$f")"; done | sort -k2 -nr
app.jsonl 42
worker.jsonl 7
```

## Syntax

| Feature | Example |
| --- | --- |
| Lists and pipes | `grep -c error app.log \| sort -n && echo ok` |
| Redirects | `ls /data /missing > out 2>&1` |
| Here-strings and documents | `wc -w <<< "one two"`, `cat <<EOF` |
| Expansion | `echo ${name:-world} $(date) $((2 + 3))` |
| Globs | `shopt -s globstar; ls /data/**/*.json` |
| Arrays | `declare -A m=([k]=v); echo ${m[k]}` |
| Conditions | `[[ $f == *.json ]] && echo json` |
| Loops | `for f in *.txt; do wc -l < "$f"; done` |
| Functions | `greet() { echo "hi $1"; }; greet sam` |
| Groups | `{ echo a; echo b; } > out`, `( cd /data && ls )` |
| Process substitution | `diff <(sort a) <(sort b)` |
| Background jobs | `sleep 30 & wait $!` |
| Timing | `time -p grep -r TODO /data` |

<Accordion title="Every supported form">
  | Feature | Supported |
  | --- | --- |
  | Command lists | `;`, newlines, `&&`, `\|\|` and `!` |
  | Pipelines | `\|` and `\|&`; `$?` and `${PIPESTATUS[@]}`. With job control off, `shopt -s lastpipe` runs the last stage in the current shell |
  | Redirection | `>`, `>>`, `<`, `<>`, `>\|`, `2>`, `2>&1`, `&>`, `&>>`; duplicating and closing descriptors |
  | Inline input | `<<EOF`, `<<-EOF` and `<<<` |
  | Quoting | `'...'`, `"..."`, backslash escapes and `$'...'` |
  | Expansion | Variables, `${name:-default}`, substring and pattern operations, `$(command)`, backticks and `$((expression))` |
  | Paths | `~`, braces, `*`, `?` and bracket patterns; `GLOBIGNORE` |
  | Extended patterns | `extglob`, `globstar`, `dotglob`, `nullglob` and `failglob` through `shopt` |
  | Variables | Scalars, indexed and associative arrays, positional arguments, `$RANDOM`, `${FUNCNAME[@]}` and `${BASH_SOURCE[@]}` |
  | Conditions | `if` / `elif` / `else`, `test`, `[ ... ]` and `[[ ... ]]`; `shopt -s nocasematch` |
  | Loops | `for`, arithmetic `for`, `while`, `until` and `select`; `break` and `continue` |
  | Functions and branching | `case`, `name() { ...; }`, `function` and `return` |
  | Groups | `{ ...; }` shares the session; `( ... )` runs in a copy of it |
  | Process substitution | `<(command)` and `>(command)` as live `/dev/fd/N` pipes; `$!` holds the last one's PID |
  | Background work | `command &`, `jobs`, `wait`, `kill`, `disown` and `ps`: see [Jobs](#jobs) |
  | Timing | `time`, `time -p` and `TIMEFORMAT`; CPU times read zero |
  | Comments | `#` outside quotes |
</Accordion>

## Sessions

- `ws.shell(...)` keeps the session's working directory, variables and
  functions. Passing `cwd` or `env` runs that call on a copy.
- Calls on one session run in order. Use separate sessions for concurrent
  command streams.
- Python cancels a call through `cancel`, an event; TypeScript through an
  abort `signal`.
- A session can narrow mount modes to `read`, `write` or `exec` (`r`, `rw`,
  `rwx`); unlisted mounts keep their own. `python3` and `js` need `exec`; a
  shell script runs each command with that command's permissions. A
  [session profile](/home/configuration/session) also hides paths and
  restricts commands.

## Jobs

`command &`, `jobs`, `wait`, `kill`, `disown` and `ps` manage Mirage jobs.
There is no terminal job control.

A program a runtime runs outside Mirage is a process of its own. `ps` shows
its real PID and the machine it runs on: a host program's host PID or a
[machine](/home/setup/machine/overview#processes-and-jobs)'s. Mirage's own
commands show `mirage`:

```
    PID MACHINE                         CMD
4194305 mirage                          ps
4194306 mirage                          sleep 300
  19443 host:my-laptop                  python3 train.py
```

Mirage's PIDs start at 4194305, past any Linux PID, so `$!`, `kill`, `wait`
and `ps -p` take either kind.

<AccordionGroup>
  <Accordion title="Processes and groups">
    - Each line of a session runs as one shell process, `$$`, which leads the
      session's process group. Its jobs, pipeline stages, subshells, command
      substitutions and nested shells belong to it; a nested `bash -c` is a
      process of its own, with its own `$$`.
    - A negative operand signals a whole group: `kill -TERM -- -$$`.
    - Unlike Bash, `kill` also stops the jobs a job started and theirs, even
      once the job between them has ended.
    - When time runs out, `timeout` signals its command's process group, so the
      jobs the command started stop too. It does not with `--foreground`,
      `-s INT` or `-s QUIT`.
    - A nested shell `timeout` runs (`timeout 5 bash -c '...'`) is the process
      `timeout` started. One that traps the signal runs its action once its
      current program ends, and goes on, as in Bash: the group's signal ends
      that program first, while with `--foreground` the program runs to its
      end.
  </Accordion>
  <Accordion title="Signals">
    - `kill` takes every Linux signal `kill -l` lists, by name or number.
      A signal that ends a process makes `wait` report 128 plus the signal, as
      in Bash.
    - `STOP` pauses a job (`ps` shows `T`) and `CONT` resumes it; a `TERM` sent
      meanwhile waits for the `CONT`. A Mirage command pauses at its next file
      operation, pipe write, sleep or loop turn; a Monty or Pyodide program where
      it is; a QuickJS or WASI program at its next file operation or output. In a
      browser, `STOP` of a Mirage command is refused.
    - A signal whose default is to be ignored or to pause (`CHLD`, `URG`,
      `WINCH`, `TSTP`, `TTIN`, `TTOU`) succeeds and changes nothing.
    - A Pyodide program, and a program a runtime started on a machine or the
      host, gets the signal as sent. One that handles it runs on, and the job
      ends when it exits, with its status.
    - `KILL` is sent only for `kill -9`, `timeout -k`, or when the workspace
      shuts down.
    - The shell ignores `QUIT`, which stops only the program it runs. A signal
      that stops `$$` ends the line with 128 plus the signal and leaves its jobs
      running, unless the shell traps it.
    - A background job ignores `INT` and `QUIT` when it is one program. A job
      that runs several commands stops only its current command, subshell or
      pipeline and goes on; a job that runs a function ends.
  </Accordion>
  <Accordion title="Job output">
    - A background job writes where the shell that started it writes, as it
      writes, so its lines and the foreground's interleave as in Bash. `wait`
      prints none of a job's output, and `fg` prints only its command line.
    - A `shell()` call returns what reached the session while the line ran.
      Output a job writes after the call returned waits, and comes first in
      the session's next call; Bash prints it at once. With `sink`, it goes to
      the console while a line runs and waits between lines the same way.
    - `$( )` and every pipeline stage but the last wait for the jobs they
      start. Inside `$( )`, `jobs` lists the caller's jobs, but `wait` and
      `kill` reach only its own; `bash -c` sees only its own.
  </Accordion>
  <Accordion title="Traps">
    - `trap 'commands' EXIT` runs at `exit`, in the frame that called it, and
      when a child shell (`bash -c`, a script, `( )`, a pipeline stage, `$( )`,
      a job) ends, or `set -e` or a fatal expansion error ends the shell. `$?`
      starts at the ending status and stays it unless the cleanup calls
      `exit N` or fails under `set -e`.
    - `trap 'commands' ERR` runs where `set -e` would end the shell, and
      `trap 'commands' RETURN` as a function or sourced file returns. A
      function runs its caller's `ERR` and `RETURN` actions only under
      `set -E` / `set -T`.
    - `trap -p` lists `EXIT`, then the signals by number, then `ERR` and
      `RETURN`; `trap - EXIT` removes and `trap '' EXIT` turns off a
      registration. A subshell lists its parent's but runs only its own.
    - A session outlives each `shell()` call, so a call that returns does not
      fire `EXIT`; register it inside `bash -c` to run before the call
      returns. Session stores do not keep traps.
    - `trap 'commands' TERM` takes any signal `kill -l` lists, by name or
      number. The action runs once the command running when the signal
      arrives has ended, as in Bash: a program in the foreground finishes
      first, and `wait` returns at once with 128 plus the signal. `exit` in
      it ends the shell and `return` the function it runs in; `$?` is the
      command's status. `trap '' TERM` ignores the signal.
    - A child shell keeps the signals its parent ignores and runs none of its
      parent's actions. A new shell (`bash -c`, a script) can neither trap
      nor reset a signal ignored as it starts, and one started in the
      background ignores `INT` and `QUIT`. A job that runs commands of its own
      (`{ ...; } &`) lists the `INT` it ignores as `trap -- '' SIGINT` and may
      still trap or reset it; the subshells and shells it starts do not keep
      it. `KILL` and `STOP` are listed but never caught.
    - Cancellation, timeouts and closing a session end the work without
      cleanup. `DEBUG` is refused with
      `bash: line 1: trap: DEBUG: not supported`.
  </Accordion>
</AccordionGroup>

### Jobs across instances

A workspace built under one `workspace_id` by several processes on a shared
[store](/home/infrastructure/overview#workspace-state) runs one instance's
lines at a time, as [Infrastructure](/home/infrastructure/jobs#several-instances-of-one-workspace)
shows. Another instance's line is refused with an error naming the running
one until it closes the workspace. PIDs continue from the highest the
workspace has used, so an instance that takes over never reuses one.

If the running instance goes away without closing the workspace, another
can run lines about 30 seconds later. It reports the jobs left behind as
ended with status 129, as Bash reports a hangup, and stops what they ran
outside Mirage: a sandbox program through a runtime on the same machine, or
a host program on the same machine whose PID still matches.

## Several machines

A workspace that runs programs on a [machine](/home/setup/machine/overview)
has processes in more than one place: Mirage's own commands, and each
machine's programs. These commands answer for all of them, so they read
differently from a shell on one Linux host:

| Command | On one Linux host | In Mirage |
| --- | --- | --- |
| `ps` | The host's processes | What the session started, on every machine, with a `MACHINE` column; `-p` and `-C` select as Linux's do, `--machine NAME` narrows it to one, `-o pid,machine` picks columns |
| `jobs`, `wait`, `kill` | One process table | Each machine is asked what runs there. A PID two machines share is refused as ambiguous; name the machine with `-m` or `--machine`: `kill -m box 13` |
| `pgrep`, `pkill`, `pidof`, `killall` | Every process on the host | Only what Mirage started, on every machine at once |
| `nproc`, `hostname`, `lscpu`, `free` | The host | One row per machine, with the machine on the right. With one machine, `free` prints that machine's table alone, as Linux's `free` does. Inside `$( )`, the default machine's answer; `--machine NAME` picks one, `--machine mirage` the workspace |
| `uptime`, `top` | Always there | Only while a machine or the host runs programs; `top` needs `-b` |
| `df`, `mount` | The host's disks | The workspace's mounts |

With no machine, every row is `mirage`: `ps` shows only Mirage's commands,
from PID 4194305 up, and `nproc` or `free` answers for the workspace, one
processor and its [`max_memory`](/home/limits#memory).
[Processes and jobs](/home/setup/machine/overview#processes-and-jobs) shows
a session with several machines.

## Errors

Errors read as a non-interactive Bash's do, `bash: line N: ...`, and a syntax
error exits 2.

<Accordion title="Error and report lines in detail">
  - Inside a function, `environment` replaces `bash`; inside a sourced file
    or a script, the file's path does.
  - `$LINENO` is the running command's line and `$BASHPID` the process
    running it.
  - When a signal ends a command, Bash's report line follows it, such as
    `bash: line 1:    12 Killed                  sleep 3`; for a background
    job, after the next program, subshell or pipeline, or at `wait`. `TERM`
    prints `Terminated` for a command and nothing for a job; `INT` and `PIPE`
    print nothing. A signal the shell traps prints only its name for a
    command, such as `User defined signal 1`, and nothing for a job. A command
    substitution reports nothing.
  - A program a runtime runs in the foreground is not a process of its own,
    so only a report line without a pid follows when a signal ends it
    (`Terminated`, or a trapped signal's name); its status is still 128 plus
    the signal.
</Accordion>

## Output to files

Most commands write a redirect's file as they print, so
`{ echo a; sleep 9; } > f` shows `a` in `f` at once. `tar`, `gzip` and a few
machine programs write when they end.

<Accordion title="Which commands stream, and what a reader sees">
  - Stream as they print: a sandbox program, a `host` machine's programs
    other than its own `python3`, Mirage's `cat`, `grep`, `awk`, `sed`, `tee`,
    `sort` and `jq`, and the commands in a group, loop or function.
  - Write when they end: `tar`, `gzip`, a `host` machine's `python3`, a
    Daytona program and a microsandbox program given piped input.
  - A command that reads or changes the file meanwhile finds what was
    written so far. `cat` and `grep` refuse to read the file their own output
    goes to.
  - The output follows the file through a rename the same line makes. The
    rest is lost once the line removes the file or renames another over it.
    A rename from another session or through FUSE is not followed.
  - What a stopped command wrote stays, whether `kill`, `timeout` or a
    cancelled call stopped it.
  - A RAM mount shows a streaming write within a tenth of a second; an object
    store such as S3 publishes it when the write ends.
</Accordion>

## Limits

Mirage runs a supported subset of Bash, not a full Bash installation.

- `bg`, `complete`, `compgen`, `ulimit`, `coproc` and `exec -a/-l` are not
  implemented. A positive `read -t` is accepted but never times out.
- `set` and `shopt` recognize more option names than they implement.
- A whole `shell()` call is parsed before it runs, so enable `extglob` in an
  earlier call, or use `eval` after enabling it.
- Command substitutions and background jobs do not inherit stdin. A write
  through an already open output descriptor appends rather than tracking an
  offset.
- A process substitution's `/dev/fd/N` belongs to the command that opened
  it. An input producer can keep running after that command ends; the
  command waits for output consumers. One an `exec` keeps (`exec 3<
  <(command)`, `exec > >(tee log) 2>&1`) belongs to the shell: closing the
  last descriptor on it ends its input, and the shell's end lets it run out
  before the shell's caller goes on, where Bash may print its last output
  later. `exec 3<> <(command)`, which waits forever in Bash, fails with
  status `2`.
