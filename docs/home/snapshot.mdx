## What It Does

A snapshot saves a workspace as one tar file: its mounts (with secret config fields redacted), sessions, history, finished jobs, the RAM file cache, and the version of the remote files the agent read or wrote, where a [supported backend](#vfs-support-matrix) reports one. A version is the backend's own marker of a file's content, such as an S3 ETag or a Drive md5. Loading the tar rebuilds the workspace. Under the default `STRICT` policy, files with a saved revision are read at that revision, and the other recorded files are checked for changes before the first command runs.

When a backend keeps old revisions (S3 object versions, Google Drive, OneDrive and SharePoint versions, GridFS), the snapshot also records which revision the agent read. A restored workspace reads that revision, so it sees the exact bytes the original run saw even after the live file was overwritten. This page calls that a *revision pin*.

## The API

The examples assume an existing workspace `ws`.

<CodeGroup>

```python Python
from mirage import DriftPolicy, Workspace
from mirage.vfs.s3 import S3Config, S3VFS

await ws.snapshot("run.tar")
await ws.snapshot("run.tar.gz", compress="gz")

mounts = {"/s3": S3VFS(S3Config(bucket="my-bucket"))}
restored = await Workspace.load("run.tar", mounts=mounts)
current = await Workspace.load("run.tar", mounts=mounts, drift_policy=DriftPolicy.OFF)

cp = await ws.copy()
```

```typescript TypeScript
import { DriftPolicy, S3VFS, Workspace } from '@struktoai/mirage-node'

await ws.snapshot('run.tar')
const tar = await ws.snapshot()

const mounts = { '/s3': new S3VFS({ bucket: 'my-bucket' }) }
const restored = await Workspace.load('run.tar', {}, mounts)
const current = await Workspace.load('run.tar', { driftPolicy: DriftPolicy.OFF }, mounts)

const copy = await ws.copy()
```

</CodeGroup>

- **Hand back every mount the tar cannot rebuild.** Config fields declared as secret are redacted from the tar, and some backends always ask for the live mount, so such a mount must be passed again at load: `mounts=` in Python, the third argument in TypeScript. Loading without one fails and names the prefix. CLIs whose config was redacted come back the same way (`clis=`, the fourth argument), and the `secrets:` block that secret-backed environment values point to through `secrets=` in Python or the `secrets` option in TypeScript. A CLI you registered in code is saved by name: register its spec with `register_cli_spec` (Python) or `registerCliSpec` (TypeScript) before loading, or hand it back with its config through `clis=` or the fourth argument.
- **Policies on a handed-back mount.** It takes the default read policy unless the override is a `Mount` that declares its own; its `write:` policy is kept, and a load that cannot keep it is refused ([the read policy](/home/yaml#the-read-policy), [the write policy](/home/yaml#the-write-policy)).
- **Compression.** Python can compress the tar (`compress="gz"`, `"bz2"` or `"xz"`); TypeScript writes it uncompressed.
- **The browser** has no file path: `ws.snapshot()` returns the tar as a `Uint8Array` and `Workspace.load(bytes)` takes it back; `Workspace.fromState(state)` restores from a state object.
- **Snapshot waits for running commands.** Running lines and writes get 30 seconds to finish, after which the snapshot fails with `EBUSY` ([Python](/python/access/in-app), [TypeScript](/typescript/access/in-app)). In the browser only running lines are waited for, so await file writes before taking a snapshot.
- **`copy()`** duplicates a workspace in-process, without a tar: RAM and Disk mounts are copied and other mounts shared ([Python](/python/access/in-app), [TypeScript](/typescript/access/in-app)).

## An S3-like store

A snapshot can go to an S3-like store instead of a file. Pass an `S3Config`, the one the [S3 mount](/python/vfs/s3) takes, so S3, R2, MinIO and other S3-compatible stores all work; the first argument (`run.tar`) becomes the object key, under the config's `key_prefix`.

<CodeGroup>

```python Python
from mirage.vfs.s3 import S3Config

store = S3Config(bucket="snapshots", key_prefix="team/")
await ws.snapshot("run.tar", s3=store)
restored = await Workspace.load("run.tar", s3=store, mounts=mounts)
```

```typescript TypeScript
import { type S3Config, Workspace } from '@struktoai/mirage-node'

const store: S3Config = { bucket: 'snapshots', keyPrefix: 'team/' }
await ws.snapshot('run.tar', { s3: store })
const restored = await Workspace.load('run.tar', { s3: store }, mounts)
```

</CodeGroup>

A server never writes a snapshot to its own disk. Over [HTTP](/home/access/http#snapshot-a-workspace) and the [CLI](/home/access/cli#workspaces) the tar goes back to the caller, or into the store its operator gave it (an `S3Config` passed as `build_app(snapshot_store=...)` or `buildApp({ snapshotStore })`; see [server options](/python/access/server)), named by a key.

## What A Snapshot Captures

<Columns cols={2}>
  <Card title="Captured" icon="check">
    - Each mount's config (secret fields redacted), mode, `read:`, `ttl:`, `write:` and index settings
    - The files in RAM and Disk mounts, and the keys in a Redis mount
    - Sessions (working directory, environment, permissions), history and finished jobs
    - The workspace environment, with secret-backed values kept as references
    - CLIs (secret config fields redacted; a script CLI's config is kept as given)
    - The RAM file cache's cached bytes
    - The version of each file the agent last read or wrote on a supported backend, where the backend reports one, and its revision where the backend keeps one
  </Card>
  <Card title="Not captured" icon="xmark">
    - Secret config fields and secret-backed values
    - The contents of other remote backends: files the agent never read, and live state of SaaS mounts (Gmail, Slack, Linear, Notion, ...)
    - A Redis file cache, and the index of listings
    - The workspace's profile and command-limit tables, policy objects, runtimes and the route policy
    - Running jobs
  </Card>
</Columns>

## Drift Detection

On the first command after `load` (a `shell()`, `dispatch()` or file operation), mirage checks every recorded file that has no revision pin, once, before the command runs. If a file's version differs from the recorded one, or the file is gone, the command raises `ContentDriftError`:

<CodeGroup>

```python Python
from mirage.workspace.snapshot import ContentDriftError

try:
    await restored.shell("cat /s3/data.csv")
except ContentDriftError as exc:
    print(exc.path, exc.snapshot_fingerprint, exc.live_fingerprint)
```

```typescript TypeScript
import { ContentDriftError } from '@struktoai/mirage-node'

try {
  await restored.shell('cat /s3/data.csv')
} catch (err) {
  if (err instanceof ContentDriftError) {
    console.log(err.path, err.snapshotFingerprint, err.liveFingerprint)
  } else {
    throw err
  }
}
```

</CodeGroup>

The error names the file and carries the recorded and current versions.

What is checked:

- **Only files the agent read or wrote.** Files it only listed or `stat`ed carry no version and are not checked.
- **A written file** is checked against what the agent wrote, on backends whose write reply names a version (not OneDrive or SharePoint; see below).
- **A file with a revision pin is not checked**: it reads its saved revision, so a change made to the live file elsewhere does not matter.

The check makes the first command after load slower than the rest, since each checked file is looked up on its backend (a few requests on backends that resolve a path folder by folder, such as Google Drive); later commands run at normal speed. `DriftPolicy.OFF` skips the check.

## Drift Policies

| Policy | After loading | Use when |
| --- | --- | --- |
| `STRICT` *(default)* | Pinned files read their saved revision; other recorded files are checked on the first command, and a change raises `ContentDriftError`. | Reproducing an agent run, and you want to know if the world moved. |
| `OFF` | No check and no pins; restored cache entries for recorded files are dropped, so those files are read live. | You want the workspace's structure and sessions, not the original bytes. |

Pass it as `drift_policy=` in Python and `driftPolicy` in TypeScript.

`STRICT` checks only the backends in the [support matrix](#vfs-support-matrix); files on other remote backends are not checked, and runtimes, policy objects and profile tables are not restored.

## VFS Support Matrix

Drift detection and revision pins work on the backends below. Every other remote mount is restored with its config (handed back at load when it holds credentials or its backend asks for it) and has no drift check. RAM and Disk mounts restore their files and need no check; in the browser, OPFS mounts are restored the same way.

| VFS | Python | TS Node | TS Browser | Version checked | Revision pin |
| --- | :---: | :---: | :---: | --- | :---: |
| S3 and S3-compatible stores | ✅ | ✅ | ✅ | ETag | ✅ when the bucket keeps object versions |
| Google Drive | ✅ | ✅ | ✅ | md5, else the head revision (modified time for native Google files) | ✅ (not for native Google files) |
| OneDrive | ✅ | ✅ | ✅ | `cTag` | ✅ |
| SharePoint | ✅ | ✅ | ✅ | `cTag` | ✅ |
| GridFS | ✅ | ✅ | — | file id | ✅ |
| GitHub | ✅ | ✅ | ✅ | blob sha | ❌ |
| Hugging Face models, datasets and spaces | ✅ | ✅ | — | the Hub's file hash | ❌ |
| Hugging Face buckets | ✅ | ✅ | — | the bucket's file hash | ❌ |
| Everything else (Box, Dropbox, Nextcloud, Google Docs/Sheets/Slides mounts, Gmail, Slack, SSH, databases, ...) | ❌ | ❌ | ❌ | none | none |

Legend: ✅ supported · ❌ not supported · — backend unavailable in that runtime.

A file the agent wrote on OneDrive or SharePoint carries no version, because the service can change an Office file after the upload, so it is not checked on replay.

To add snapshot support to your own backend, see [Build a VFS](/python/vfs/new#6-snapshot-support) ([TypeScript](/typescript/vfs/new#6-snapshot-support)).

## How It Composes With Caching

The RAM file cache travels in the tar and is restored as it was, with its original expiry: under `read: bounded` a restored file is served without a request while its entry is still inside the `ttl:` it was cached under, and under `read: fresh` it costs one check. Entries older than the `ttl:` are fetched again. A Redis file cache and the index are not captured; listings are rebuilt on first use. See [the cache](/home/cache).

## Caveats

- **A snapshot can hold sensitive data.** Only secrets are redacted. A script CLI's config, plain environment variables, files, cached bytes and history are saved as they are, so treat the tar as sensitive and keep credentials in secrets rather than in a script CLI's config.
- **Revisions do not last forever.** A pin works only while the backend still holds that revision. S3 lifecycle rules can expire old object versions, and Drive keeps old revisions of non-Google files for 30 days unless they are marked keep-forever; OneDrive and SharePoint keep versions per their library's version-history settings. Treat pins on old snapshots as best-effort.
- **A snapshot from another format is refused.** A snapshot taken by a release with a different snapshot format (older or newer) is refused; take it again with the current release.
