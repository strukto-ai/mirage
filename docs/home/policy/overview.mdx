Policy decides what an agent may do in the virtual terminal: the commands it
runs, the files it reads and writes, and the connections it opens. It runs
inside the shell and the filesystem, so it judges each command after
expansion and each file a command reaches, however the agent connects.

## Example

A review agent that reads a repository, never sees its secrets and deletes
nothing:

```yaml workspace.yaml
mounts:
  /repo:
    vfs: disk
    mode: write
    config:
      root: ./my-repo
profiles:
  reviewer:
    mounts:
      /repo: read
    paths:
      hide: [/repo/.env]
    commands:
      rm: deny
```

A session under `reviewer`, such as `ws.session("agent", profile="reviewer")`:

```bash
$ ls -A /repo
src
$ cat /repo/.env
cat: /repo/.env: No such file or directory
$ grep -r API_KEY /repo        # exit 1: the hidden file is never searched
$ echo x > /repo/notes.md
bash: line 1: /repo/notes.md: Read-only file system
$ rm /repo/src/app.py
rm: Permission denied
```

The host still writes `/repo`; the profile narrows only that session.
[Session Profiles](/home/configuration/session) lists every key, and
[Command rules](/home/configuration/session#command-rules) shows how to write
a rule for a subcommand, an option or an operand.

## Three ways to write policy

| Write | Where | For |
| --- | --- | --- |
| Rules | a [profile](/home/configuration/session)'s `commands`, `paths`, `mounts` and `network` | command rules, hidden paths, read-only mounts |
| A [class](/home/policy/policies) | `policies` on the workspace, in Python or TypeScript | decisions over the full context: each command's expanded words, the paths it reaches, what came back |
| A [script](/home/policy/scripts) | a profile's `policy:` or a server's policy file | the same decisions in config, run sandboxed on Monty or Python on wasm |

## Methods

A class or a script answers at any of these methods. A `pre_` method runs
before the action; a `post_` method runs after it, with what came back, and
never undoes what ran.

| Method | Asked for | May answer |
| --- | --- | --- |
| [`pre_execute`, `post_execute`](/home/policy/line) | each line | Deny or Ask; a Route before, a Limit after |
| [`pre_command`, `post_command`](/home/policy/command) | each command or CLI, nested ones included | Deny or Ask; a Route before |
| [`pre_vfs`, `post_vfs`](/home/policy/vfs) | each file call: commands, file CLIs, runtimes, `session.vfs`, FUSE, SFTP | Deny or Ask |
| [`pre_network`, `post_network`](/home/policy/network) | each connection: `curl`, a CLI's API call, a mount's VFS, a runtime, an SDK | Deny, Ask or Limit before; nothing after |
| [`pre_workspace`](/home/policy/workspace) | a server's create, clone or load, before the workspace is built | Deny |

`None` is no opinion. A Deny refuses, an Ask waits for the host's approval,
a Route picks the [machine](/home/policy/route-machine) and a Limit caps the
output or the connection. See [Answers](/home/policy/policies#answers).

## Order

Built-in checks answer first: mount modes, path rules, the workspace's
`network` lists and its `route_policy`. Then the session's profile rules and
scripts, then the workspace's policies in the order they were added. The first
Deny wins, and an Ask never reopens a Deny, so no policy can allow what
another refuses. See [When answers disagree](/home/policy/policies#when-answers-disagree).

## Why not a tool-call check

A harness's tool-call check, such as Claude Code's `PreToolUse` or an SDK's
`can_use_tool`, sees one tool call: a tool name and a string such as
`cat $(ls /data | head -1)`. A Mirage policy sees what that string runs.

| | Tool-call check | Mirage policy |
| --- | --- | --- |
| Commands | the raw string; `$( )`, `xargs`, `find -exec`, `eval` and variables hide what runs | every command after expansion, nested ones included |
| Files | the paths written in the string | every path a command reaches, such as each file `grep -r`, `tar` or `cp -r` opens |
| Ways in | that harness's own tools | every session and entry point: the SDK, MCP, HTTP, RPC, SSH, FUSE |
