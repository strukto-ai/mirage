---
title: Explain
description: See what a line or a file call would do before running it, allowed, refused or waiting for approval.
icon: lightbulb
---

Explain asks every policy about a line or a VFS call without running it, so
an agent or a host sees the outcome first and can choose what to run.
Nothing runs, nothing is written and no ask is spent.

## Example

```yaml
profiles:
  agent:
    cwd: /data
    commands:
      rm: deny
      curl: ask
```

<CodeGroup>
```python Python
explain = (await ws.session("agent", profile="agent")).explain
r = await explain.shell("rm a.txt")
print(r.outcome, r.exit_code, r.stderr)  # deny 126 rm: Permission denied
```

```typescript TypeScript
const explain = (await ws.session('agent', { profile: 'agent' })).explain
const r = await explain.shell('rm a.txt')
console.log(r.outcome, r.exitCode, r.stderr) // deny 126 rm: Permission denied
```
</CodeGroup>

| Line | `outcome` | Running it would print |
| --- | --- | --- |
| `cat a.txt \| wc -l` | `allow` | its output |
| `rm a.txt` | `deny` | `rm: Permission denied`, exit 126 |
| `curl -s https://example.com` | `ask` | `curl: Permission denied`, exit 126, until a host approves |
| `cat a.txt && rm a.txt` | `deny` | `rm: Permission denied`: the rule on `rm` stops the whole line, so `cat` never runs |

`explain.vfs` takes the same calls as `session.vfs`:
`await explain.vfs.read("/data/a.txt")`.

## Where to ask

| Entry point | A line | A VFS call |
| --- | --- | --- |
| In-app | `session.explain.shell(line)` | `session.explain.vfs.<call>(...)` |
| [MCP](/home/access/mcp#vfs-calls), with `?calls=all` | `shell` with `explain: true` | `vfs_<call>` with `explain: true` |
| [HTTP](/api/operations/shell/run-shell-command) | `POST /shell?explain=true` | `POST /vfs/<call>?explain=true` |
| [RPC](/home/access/rpc) | `shell` with `explain: true` | `vfs/<call>` with `explain: true` |
| [CLI](/home/access/cli#run-lines-vfs-calls-and-tools) | `mirage shell -w ID -s SESSION -c LINE --explain` | `mirage workspace vfs CALL ARGS -w ID -s SESSION --explain` |

Every entry point returns the same fields. Explain reads the line alone, so
a request that also sends stdin, a `cwd` or a `machine` is refused.

## What comes back

| Field | What it is |
| --- | --- |
| `outcome` | `allow`, `deny` or `ask` |
| `reason` | the deciding answer's reason, or empty |
| `source` | where the profile writes the rule, such as `top`; empty for a coded policy |
| `answers` | every policy that answered, in order |
| `decision` | the record the agent would get, or `null` |
| `exit_code`, `stderr` | a line: what the agent would read |
| `node` | a line: the line as a tree, each command with its own `outcome`, `exit_code`, `stderr`, `words` and the `machine` that would run it |
| `error` | a VFS call: the error it would raise (`EACCES`, `EROFS`), or empty |

`mirage shell --explain` prints `node` as an indented tree, one command per
row with its outcome.

## What it cannot see

- `post_` methods, since nothing comes back to judge.
- The file calls of a line, which happen only as it runs: explain the VFS
  call itself to see its `pre_vfs` answer.
- A `pre_command` answer shows on its command, and the line stays `allow`.
- A hidden path explains like any path no rule names, so explain never
  reveals it exists.

## When an action is refused

A refusal reads as a real terminal's:

| Refused | The agent reads |
| --- | --- |
| a line or a command | `rm: Permission denied`, exit 126 |
| one path | the command's own error: `cat: /data/k: Permission denied`, exit 1 |
| a write to a read-only mount | `Read-only file system`, exit 1 |
| a VFS call | `EACCES` |
| an ask | the same as a deny, until a host approves; then the retry runs |
| a hidden path | `No such file or directory` |

The reason is on the result's `decision`, never in stderr. The
[agent tools](/python/access/in-app#session-tools), which MCP and the agent
adapters serve, add one line: `policy denied: <reason>`, or
`requires approval: <reason> (ask <id>)`.

### Which tools the agent gets

`session.tools.names()` lists only the tools the session's profile leaves
it: `shell` needs a command its `commands` lets run, `ls` and `grep` those
commands, `write` and `edit` a mount the session may write. MCP, RPC and the
agent adapters offer exactly those, so an agent is never offered a tool every
call of which would be refused.
