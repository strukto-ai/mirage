A profile gives an agent session its permissions. Agents can share a
workspace while seeing different files and using different commands.

## What a profile controls

| Setting | Purpose |
| --- | --- |
| `commands.allow` | Limit the session to the listed tools. |
| `commands.ask` | Require approval for matching commands. |
| `commands.deny` | Refuse matching commands. |
| `paths.hide` | Make matching files and folders invisible to the session. |
| `paths.show` | Make a specific path visible within a hidden folder. |
| `mounts` | Restrict a data source to `read`, `write` or `exec` access. |
| `cwd` and `env` | Set the session's starting directory and environment; `env` takes the same literals and [credential pointers](/home/configuration#environment-and-credential-pointers) as the workspace's. |

## Example: a research agent

This profile lets an agent browse and search `/data`, keeps it read-only,
and hides `/data/private`.

```yaml workspace.yaml
mounts:
  /data:
    vfs: ram

profiles:
  researcher:
    cwd: /data
    mounts:
      /data:
        mode: read
    paths:
      hide: [/data/private]
    commands:
      allow: [ls, cat, grep, find, stat, pwd]

profile: researcher
```

Replace RAM with your [VFS](/home/setup/vfs). `profile: researcher` selects
the default for new sessions; another session can use a different named
profile. A profile cannot grant access beyond the workspace's permissions.

## Rule matching

Command patterns match token prefixes. `git push` matches `git push origin main`.
Spelling and order matter: `rm -rf` does not match `rm -r -f` or
`rm --recursive --force`. A `*` token matches any token; trailing `*` is redundant.

Omitting `commands.allow` adds no tool allowlist restriction; `allow: []`
admits no installed tools. This list does not govern shell functions,
executed paths or direct VFS calls.

Ask and deny rules can name commands, paths, or map a command to its paths:

```yaml
commands:
  allow: [rm]
  ask:
    - {commands: {rm: ["/data/review/*"]}, reason: deletes need review}
  deny:
    - {commands: {rm: ["/data/*"]}, reason: data is retained}
```

Within one profile’s rules, the deeper literal anchor wins for each path.
Deny wins at equal depth.
Here, `rm /data/review/note.txt` asks for approval despite the broader deny;
`rm /data/other.txt` is denied. A multi-path command must pass each path's checks.

`paths.hide` and ask/deny path entries may be absolute paths or slashless
name patterns such as `*.pem`, including inside mount sections.
`paths.show` entries must be absolute paths. A literal path covers its subtree;
glob patterns use `*`, `?` and `[`, and `*` can cross `/`. A rule naming only
`paths` also applies to direct VFS operations.

`paths.hide` makes a path appear absent; `paths.show` reopens a more specific
path. Ask and deny rules control operations while leaving paths visible.

Use [Explain](/home/policy/explain) to check a rule before running a line.
For conditions beyond these patterns, attach a [policy script](/home/policy/scripts).
