## What It Does

A workspace can be described entirely in YAML and loaded with one call — `load_config` in Python, `loadWorkspaceConfigFile` in TypeScript. This page is the key-by-key reference. Both languages read the same document and refuse the same things: an unknown key is an error, not a warning, so a typo fails loudly at load rather than silently doing nothing.

## Top level

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `mounts` | map | required | Prefix to mount block. See below. |
| `mode` | `read` \| `write` \| `exec` | `write` | The mode a mount inherits when it declares none. |
| `read` | `fresh` \| `bounded` | `bounded` | The read policy a mount inherits when it declares none. There is deliberately no top-level `ttl:` — see [the bound](#the-bound). |
| `write` | `unconditional` \| `conditional` | `unconditional` | The write policy a mount inherits when it declares none. See [the write policy](#the-write-policy). |
| `io` | block | `{buffer_bytes: 65536}` | Capacity of each streaming byte queue. See [I/O buffers](#io-buffers). |
| `command_limits` | map | — | Per-command caps for every session. See [command limits](#command-limits). |
| `clis` | map | — | Installed CLIs, keyed by head word. |
| `runtimes` | list | — | The workspace's ordered runtime world. |
| `profiles` / `profile` | map / string | — | Permission documents, and the default one. |
| `route_policy` | path | — | A `.py` whose last expression names the runtime for a line. |
| `cache` / `index` / `store` / `console` | block | — | Where bytes, listings, workspace state and job output live. See [cache stores](/home/cache#stores) for the `cache` and `index` keys. |
| `env` / `secrets` | map | — | The environment plane and the source table. |
| `default_session_id` / `default_agent_id` / `workspace_id` | string | — | Identity. |

## Mount block

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `vfs` | string | required | The registered backend name, or a `./file.py:Class` reference. |
| `config` | map | `{}` | The backend's own config, validated by that backend's model. A key the model does not declare is refused by name (`linear: team_idz: ...`), never ignored. |
| `mode` | `read` \| `write` \| `exec` | top-level `mode` | This mount's mode. |
| `read` | `fresh` \| `bounded` | top-level `read` | How this mount's cached bytes are served. |
| `write` | `unconditional` \| `conditional` | top-level `write` | Whether this mount's writes carry the version they were based on. An empty `write: ""` means `unconditional`; `null` or no key takes the top-level `write`. |
| `ttl` | integer (seconds) | `600` | The staleness bound for this mount's cached bytes and cached listings, under both `bounded` and `fresh`. |
| `index` | block | top-level `index` | This mount's own listing store, the top-level `index:` keys (`type`, `ttl`, `url`, `key_prefix`). It replaces the top-level block whole; see [per-mount index](#per-mount-index). |
| `command_limits` | map | `{}` | Per-command caps for this mount. |
| `backend` | `workspace` \| `fuse` \| `fskit` | `workspace` | Whether the mount also registers a real mountpoint. |
| `mountpoint` | path | — | Where, for the kernel backends. |

```yaml
mode: write
read: bounded

mounts:
  /fast:
    vfs: s3
    config: {bucket: reports}
    read: bounded
    ttl: 600
  /live:
    vfs: s3
    config: {bucket: feed}
    read: fresh
  /scratch:
    vfs: ram
```

## I/O buffers

```yaml
io:
  buffer_bytes: 262144  # 256 KiB per queue
mounts:
  /:
    vfs: ram
```

`buffer_bytes` defaults to 65536 (64 KiB). It must be an integer from 16384
through 9007199254740991. Unknown keys are rejected. Chunks remain at most
16 KiB; capacity controls how many bytes can wait before writers pause.
A larger value, such as 256 KiB or 1 MiB, absorbs longer bursts at the cost
of more memory per active queue. It does not guarantee faster execution.

The immutable workspace setting applies to shell pipes, command output,
process stdin/stdout/stderr, SDK events and HTTP upload/output queues.
HTTP output counts encoded NDJSON bytes, including base64 overhead; its
raw payload records remain at most 8 KiB. SDK and handler queues count raw bytes.
CLI and MCP calls use their workspace's setting, including MCP over SSE
and stdio. Configure it when creating the workspace; shell calls and MCP
tool arguments do not override it. Snapshots and copies preserve it.

This is a per-queue limit, not a workspace memory limit. One execution can
have several queues. Collected results and whole-output policy buffers
are separate and can exceed this size.

## Command limits

`cat`, `grep`, `rg`, `head`, and `tail` cap their output at 2000 lines, and
every command stops after 600 seconds. Change that with `command_limits` in
three places: at the top level for every session, on a mount for commands
that run on it, and on a profile for sessions created with it:

```yaml
command_limits:
  head:
    max_lines: 500
    timeout_seconds: 30
mounts:
  /data:
    vfs: ram
    mode: WRITE
    command_limits:
      grep:
        max_lines: 50
        on_exceed: error
profiles:
  researcher:
    command_limits:
      head:
        max_lines: 5000
```

A command's limit comes from the first place that names it: the session's
profile, the mount the command runs on, the workspace, then the built-in
default. A command that spans several mounts takes the tightest of their
limits. An entry replaces that command's whole limit, so restate
`timeout_seconds` if you still want a deadline; commands it does not name keep
their defaults.

- `max_lines` / `max_bytes` cap the output; `null` means no cap.
- `timeout_seconds` is a deadline; a command that runs past it exits `124`.
- `on_exceed: truncate` (default) keeps the capped output, adds a stderr
  notice, and leaves the exit code alone. `on_exceed: error` drops the output
  and exits `1`, so `&&` and `||` see the failure.

Caps apply to what each command prints, one command at a time:
`cat big.txt; echo end` still prints `end`. Data going into a pipe, a
redirect, or `$(...)` is never cut, so `cat big.txt | wc -l` counts every
line. See [Output Limits](/python/quickstart#output-limits) for the SDK form.

## The read policy

`read: bounded` serves cached bytes and cached directory listings without asking the backend, for as long as `ttl:` allows. `read: fresh` revalidates against the backend's content token before serving a cached copy, at the cost of one backend stat per file read, and checks a cached listing before serving it: against the listing's stored version where the backend has one, otherwise by re-listing the folder once per command. See [listings under `fresh`](/home/cache#listings-under-fresh).

`fresh` is refused at mount time on a backend that cannot honour it, rather than quietly behaving as `bounded`:

- the backend caches neither reads nor listings, so the check has nothing to run against (`ram`, `redis`, `postgres`, `mongodb`, a local `lancedb`). A backend that caches listings but no bytes (`disk`, `chroma`, `qdrant`, `airtable`, `wandb`) accepts `fresh`, because its listings are checked, and so does any mount whose `index:` (its own or the workspace's) keeps listings for a nonzero `ttl`;
- or it caches reads but stamps no token the check can compare, because its `stat` and its read return different kinds of value, or its read stamps nothing.

[The VFS matrix](/home/vfs-matrix) lists which backends accept `fresh` today.

### The bound

A bare `ttl:` lives only in a mount block. At the top level it would sit beside `index: {ttl: ...}` and mean a different thing, so the workspace-level default is `read:` alone and a workspace-level `bounded` takes 600 seconds. Inside a mount the two are told apart by nesting: `ttl:` is the bound, and a mount's own `index: {ttl: ...}` is how long its listing store keeps a listing, never longer than that bound.

Each listing write is capped by the mount's `ttl`, under both policies. Backends may expire listings sooner, and mounts without a listing cache still keep none. `fresh` also checks listings, so a file added or removed outside mirage shows in the next `ls`, `find` or glob. A cached listing is served without a re-list only when the running command fetched it, a GitHub mount is pinned to a full commit sha and the listing was fetched at it, or the backend's listing version still matches; otherwise the folder is listed again once per command (a read outside a command trusts a listing from the last second). [Listings under `fresh`](/home/cache#listings-under-fresh) has the cost per backend, including Disk's `folder_versions: false` for a network or FUSE root.

Existing listings in a persisted Redis index retain their stored expiry until rewritten.

### Per-mount index

A mount's `index:` block takes the top-level `index:` keys and replaces that block for this mount, whole: nothing is inherited from it, so `type:` is required, a missing `ttl:` is 600 seconds, and a Redis store's `url:` and `key_prefix:` take the block's own defaults, not the top-level ones. A mount without one takes the top-level `index:`, and with neither, the backend's own listing lifetime ([Index TTL](/home/cache#index-ttl)). `index: null` is the same as leaving it out. The file cache has no per-mount block; a mount's `cache:` is refused.

```yaml
index: {type: redis, url: redis://cache:6379/0, ttl: 600}

mounts:
  /drive:
    vfs: gdrive
    read: bounded
    ttl: 86400
    index: {type: ram, ttl: 86400}   # this mount's listings, in RAM, for a day
  /work:
    vfs: disk
    config: {root: /srv/work}
    index: {type: ram, ttl: 0}       # this mount caches no listings
```

The mount's `ttl:` still caps every listing write, so a mount `index: {ttl: ...}` can only shorten how long a listing lives; `/drive` keeps listings for a day because its `ttl:` is raised to match. `fresh` is judged on the mount's own index: a zero `ttl` there takes listing-only `fresh` away from `disk` even under a nonzero top-level `index:`.

Two shapes are refused, because a `read`/`ttl` pair that disagrees is almost always a typo:

- `ttl:` with no `read:` — the bound pins nothing.
- `read: bounded` written out with no `ttl:` — an explicit policy with an implicit bound.

An unset `read:` is a different thing and is fine: it takes the default.

### Across a snapshot

A snapshot records each mount's policy and bound, and a restore keeps them --
but only for a mount the loader rebuilds from the saved state itself. A mount
handed back through `mounts=` takes the default (`bounded`, 600s) instead,
unless the override is a `Mount` that declares its own `read:`.

That is deliberate: a mount saved with redacted credentials *has* to be handed
back, and what comes back may be a different backend entirely. Replaying a saved
`fresh` onto one that cannot revalidate would refuse a restore that had nothing
wrong with it. The saved policy still has to be a policy mirage knows -- a
snapshot naming an unknown one is refused whether or not the mount is overridden.

Declare `read:` again on an overridden mount if you want it back.

### What the bound promises

The bound is stamped on a cache entry when that entry is written, and the store
expires it from there. So the bound that applies to an entry is the one the
mount that *wrote* it declared, not the one the mount reading it declares. Within
a workspace those are the same mount, so `ttl:` means what it says.

They can differ in three situations, and in each the older bound wins until the
entry expires on its own:

- two workspaces sharing one Redis cache declare different `ttl:` for the same
  prefix;
- `ttl:` is lowered and the process restarts against a surviving shared cache;
- a snapshot is restored into a mount whose `ttl:` differs from the one that
  took the snapshot.

Making the reader's bound authoritative would mean recording when each entry was
written somewhere every store can read it back — Redis keeps no such timestamp
today. Until then, treat a shared cache as a place where `ttl:` should agree
across the workspaces that use it.

## The write policy

`write: unconditional`, the default, writes what a command sends, whatever the backend holds by then. `write: conditional` makes every write on the mount carry the version of the file it was based on, and the backend refuses it when the file has changed since:

```yaml
mounts:
  /shared:
    vfs: s3
    config: {bucket: team}
    write: conditional
```

```bash
cat /shared/notes.txt                 # mirage keeps this version
# ... another client rewrites notes.txt ...
echo done > /shared/notes.txt
# /shared/notes.txt: changed since it was read; read it again before writing
```

A refused write leaves that file as it was and drops the cached copy, so reading the file again fetches what is there now, and the write after that read goes through. Until then the refusal keeps the version it lost on: writing again without reading is refused again, rather than going out over the newer file. A file found removed keeps no version, so the next write to it goes out plain. The refusal reads as the command's own failure:
- `cp: cannot create regular file 'X': changed since it was read; ...`;
- `rm: cannot remove 'X': ...`;
- `mv: cannot move 'f' to 'g': 'g' changed since it was read; ...`, naming whichever of the two changed (inside a directory `mv`, the file within it);
- `sed: couldn't edit X: ...` (exit 4, as GNU sed's);
- `find: cannot delete 'X': ...` for `find -delete`;
- for a redirect, `X: changed since it was read; ...`, exit 1.

A command that moves or deletes several files is refused one file at a time, so it can stop partway:
- **`rm -r`** deletes the files that were still the version it measured, keeps the ones that changed, and names the first, as GNU's `rm` does: `rm: cannot remove 'd/x': ...`. Unlike GNU, it names only that one: any other changed file stays refused until it is read. A file the store refuses for another reason (`Permission denied`) is reported instead, naming the operand, and the changed files still stay refused.
- **A directory `mv`** on an object store moves the unchanged files, leaves the changed one where it was, and names it; as with a file `mv`, both ends of a refused file keep their versions. Moved onto a populated directory (the ops API or a kernel rename; the shell refuses that as GNU does), a destination file mirage holds a version of is replaced only while it is still that version; one it holds none of is replaced plain.
- **A file `mv`** onto a destination that changed since it was read is refused, leaving both files as they were, and both keep the version the agent read; reading the destination lets it through. On an object store a source never read is pinned to the version `mv`'s own lookup found, and keeps that version if it changes before the move. One whose copy landed before its source changed keeps the copy and reports `mv: cannot remove 'src': ...`, as GNU's `mv` does when its unlink fails.
- Removing or moving a refused file away (or onto it) ends the refusal, as does a Box `cp -r` that copies a whole folder over its place: a new file written there goes out plain. The exception is a file a directory `mv` moved away before the move was refused on another file: the next write to its old path is refused once (the file is gone, so it keeps no version), then goes out plain.
- On Box and Dropbox a `mv` within the mount is one move of the whole file or folder, so only a destination it replaces is measured ([which backends](#which-backends)).

**Which version a write sends.** A `>>` append, a resize to a nonzero length, and a write at an offset read the file themselves first, so they send the version of the bytes they just read. Finding the file gone, they are refused when the mount holds a version of it (it was removed since it was read) and write it plain otherwise. Any other write sends, in order:

1. what the same line last read or wrote at that path (`cat f; echo x > f`, or two redirects in a row);
2. the version the mount kept from an earlier line: the cached copy's, or, where the bytes were not kept (a `grep` or `head` of the file, the agent's own append, a file bigger than the cache), the version alone.

With neither, mirage holds no version, so there is nothing to compare: the write goes out plain, as on an unconditional mount. Only a file mirage holds a version of is protected, so read a file before overwriting it when another writer may have changed it.

**Emptying counts as a whole-file write.** Emptying a file the way opening it for writing does (`open(path, "w")` in a script, `truncate -s 0`) is one of those "any other" writes, not a read-then-write. Read first, it carries that version; unread, it goes out plain.

**`rm` and the source of an object store's `mv`** are measured against the version the line or the mount saw, else the one their own lookup finds. They are never refused for want of a read. `rm -r` and an object store's directory `mv` hold each file to the version the agent read where there is one, and otherwise to the version their own listing finds.

### Which backends

A mount is refused at load, naming the reason, when it cannot keep the promise.

**The backend has no write conditions.** Today the S3 family, Box and Dropbox have them:
- AWS S3 and SeaweedFS honour them on every write, delete and copy (measured).
- MinIO, and `vfs: s3` on any endpoint other than AWS's, honour them on a write but not on a copy or delete. There mirage refuses what would copy or delete on that mount (such as a `cp` or `mv` within the mount, a `mv` out of it, `rm`, or `find -delete`) itself, before it changes anything (its lookups still run), with `Operation not supported`. A `mv` to another mount of a directory that holds such a mount is refused the same way. A `cp` or `mv` into it from another mount is a write, and goes through.
  - The endpoint is the mount's own: the config's `endpoint_url`, else `AWS_ENDPOINT_URL_S3` or `AWS_ENDPOINT_URL` unless `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS` is `true`. One the environment gives when the mount is built is fixed: the mount's requests keep going there whatever the environment says later. Without one, a write is judged on the endpoint its client uses: the one the client opened with, or, before it opens, the one the environment names now, so an endpoint set later is judged on its own row once a client opens on it. An endpoint set only in an AWS profile is not read, so such a mount gets AWS's row: give a non-AWS server its `endpoint_url` on the mount, or mount it through its own type (`vfs: minio`).
  - AWS's China regions count as AWS.
- The other S3-compatible services (R2, GCS, OCI, Supabase, Ceph, Wasabi, Backblaze B2, DigitalOcean Spaces, Tencent COS, Alibaba OSS, Scaleway, QingStor) are assumed to behave like AWS S3. They are not measured per provider.
- In the browser, an S3 mount that signs through presigned URLs is refused, since those carry no condition.
- Box and Dropbox honour them on every write and file delete (measured). What mirage holds for a file there is its content hash (Box's `sha1`, Dropbox's `content_hash`), which is not the token the service conditions on (Box's `etag`, Dropbox's `rev`). So a write first compares the hash it holds with the file's live one, from the lookup the write makes anyway; a file changed since it was read is refused there, before anything is sent. The write then goes out with the live token (`If-Match`, or an upload in `update` mode and a delete with `parent_rev`), so a change that lands after that lookup is refused by the service.
  - On Box the lookup is the folder listing every Box write already walks, so a conditional write costs no extra request. On Dropbox a write that holds a version costs one `get_metadata` before the upload; one with no version goes out as one upload, as before.
  - `rm -r` of a folder walks it file by file, as on an object store, instead of the one recursive delete it is on an unconditional mount: the files that are still as measured go, the changed ones stay with their folders, and the first is named. That is a listing per folder (a page per 1,000 entries on Box, 2,000 on Dropbox), a delete per folder, file and Box web link (Dropbox also looks the operand up first and lists each folder once more before deleting it) instead of one recursive delete.
  - A `mv` is the service's own move of the file or folder, whole and in one call, so it can neither lose a newer write nor overwrite one: it is not refused when the source, or a file inside a moved folder, changed since it was read, and the newer bytes move with it. Only replacing an existing destination is conditioned. This is where they differ from an object store, where `mv` is a copy and a delete and a changed source is refused. A `mv` to another mount is a copy and a delete on a drive too, so its source delete is measured: when the source changed since it was read, the copy has landed, the source stays, and `mv` exits 1 with `mv: cannot remove 'src': ...`.
  - Their `copy` condition is the replacing of an existing destination: a `cp` or `mv` onto a file mirage holds a version of deletes that file only while it is still that version (`If-Match`, `parent_rev`). Box deletes it before the copy; Dropbox copies first, so a source that is gone costs the destination nothing, and deletes it only when the copy answers that the name is taken, then copies again. The copy itself carries no condition.
  - A file whose content changed and changed back to the bytes mirage read has the same hash again, so a write based on that read goes through; nothing is lost, since what it replaces is what it read.
  - Files Box keeps with no `sha1` (Box Notes, Canvas, Box-hosted Google files) never hold a version, so their writes go out plain.
  - On Box a partial read (such as `head`) keeps no version: Box's download names none, and part of a file cannot be checked against its `sha1`. A file only read that way is written plain. Dropbox names the version on every download, partial or whole.

**The mount is read-only.**

A kernel mount (`backend: fuse` or `fskit`) and an SFTP or `scp` session write through the same rule as a shell line: opening a file to write it carries the version mirage holds, so a file changed since it was read through them is refused at the open. A kernel mount's client sees the host's "stale file handle" error (`ESTALE`); an SFTP or `scp` client sees a generic failure. Neither sees mirage's wording.

**The mount caches no reads** (including a cache `limit` of 0), since the cache is where the version lives.

`write: staged` is refused as well: it needs a staging layer mirage does not have.

### Known limits

- **Versions belong to the cache, not the session.** Two sessions of one workspace, or two workspaces sharing a Redis cache, share versions, so one session's read lets the other's write through.
- **A write with no version is not conditioned.** A file mirage never read, whose version the cache dropped, or that a `cp` or `mv` within the mount just made, is written plain, as on an unconditional mount. Read a file first when another writer may have changed it.
- **Writes outside a shell line keep no version.** A write made outside any shell line (host code calling `ws.vfs` directly) leaves no version for the next one, except through the cache.
- **Some events clear versions:**
  - After a host program, a remote runtime line or an account or script CLI write, cached bytes are dropped ([when the cache is cleared](/home/cache#when-the-cache-is-cleared)), so the next write has no version.
  - A version kept without its bytes lives in the cache like an entry, so a RAM cache's LRU or a Redis server's eviction can drop it. The next write then goes out plain.
  - Otherwise a version a shell line saw outlives the cache's `ttl`. On RAM it lives until the LRU drops it; on Redis it lives 24 hours from the line that last saw it, or as long as its bytes when they live longer, so a server under a `volatile-*` or `noeviction` policy still sheds it. A version from a read outside a shell line (a kernel mount, `ws.vfs`) lives as long as its cached bytes on Redis, the cache's `ttl`.
  - On Redis a version kept without its bytes is not counted against the cache's `limit`: each is a small key of its own, one per file a line read, for 24 hours. On RAM it counts, so the LRU can drop it.
- **Directory markers are unconditional.** `mkdir` and `rmdir` write directory markers unconditionally; a marker holds no content to lose.
- **Dropbox deletes a folder whole.** Dropbox has no delete that refuses a non-empty folder, so a conditional `rm -r` deletes a folder only once a listing shows it empty; a file another client creates in it between that listing and the delete goes with it.
- **A partial `rm -rv` prints no `removed` lines.** When a refusal stops `rm -rv` partway, it prints no `removed '...'` lines for the files it did delete.
- **Browser limit.** In the browser, where lines running at once cannot be told apart, a write while they overlap takes the policy of the mount that owns its path. Two workspaces running lines at once through mounts at the same prefix with different policies cannot be told apart either; a write there is refused (`Operation not supported`) rather than sent without its version.

### Across a snapshot

A snapshot records each mount's write policy and the workspace's default, and a restore or `copy()` keeps them, also for a mount handed back through `mounts=`. Unlike `read:`, a saved `conditional` is not dropped there: a stand-in that cannot refuse a stale write is refused at load, rather than restored writing blind, and an override `Mount` that names a different `write:` is refused rather than ignored, as is (in TypeScript, whose `fromState` takes options) a `write` option naming a different workspace default.

Under `write: conditional`, a restore that pins a file to its saved revision (a versioned bucket) reads that revision, so a write sends the saved version and is refused if the live file has changed since.

A snapshot keeps the versions of the cached copies it holds, but not a version kept without its bytes: after a restore such a file has no version, so its next write goes out plain until it is read again.

A snapshot in another format than this loader's is refused, older (from before the write policy existed) or newer.

## Not yet accepted

`read: pinned` is refused, naming the layer it needs: pinning reads to the content a commit records requires a version layer mirage does not have. `write: staged` is refused the same way. Both are reserved rather than silently ignored, so a config that names one fails at load instead of appearing to work.

## Time-scoped chat and calendar mounts

The `slack`, `discord`, and `gcal` backend config blocks accept `start_time`
and `end_time`: RFC3339 timestamps with a timezone and at most millisecond
precision. Start is inclusive and end is exclusive; either may be omitted or
null. An empty or reversed interval is refused. The same snake_case fields
work through `build_vfs` in Python and `buildVfs` in TypeScript.

```yaml
mounts:
  /calendar:
    vfs: gcal
    mode: read
    config:
      access_token: "<google-access-token>"
      time_zone: UTC
      start_time: "2026-06-01T00:00:00Z"
      end_time: "2026-07-01T00:00:00Z"
```

Chat selects messages by creation time; attachments follow those messages.
Calendar selects events overlapping the interval and retains their original
payloads, including events that cross a bound. Only day directories intersecting
the interval are exposed. Calendar day names use the mount's `time_zone` (or its
primary calendar's timezone); chat day names use UTC. Context such as users,
channels, and `calendar.json` remains available.

Calendar's bare listing includes all past event days. Without `end_time`, future
discovery stops at the end of today +90 days; explicit date paths/globs can reach
further within the configured scope. With `end_time`, that explicit endpoint
replaces the default horizon. Calendar refuses a listing still incomplete after
50 API pages; narrow the range instead of receiving a silently truncated result.

A `gcal` block also takes `bucket_days`: `1` (the default), `7` or `30`, the days
each date directory covers. With `7` or `30` a directory is named by its first
and last day, `2026-08-10--2026-08-16/`, on a fixed grid where 7-day buckets run
Monday to Sunday, and each event file name carries its day
(`<eventId>__2026-08-11_0900-1030_<Title>.gcal.json`). One listing then answers a
week or a month of events. Other values are refused.

```yaml
mounts:
  /calendar:
    vfs: gcal
    mode: read
    config:
      access_token: "<google-access-token>"
      bucket_days: 7
```

Without either bound, Slack and Discord retain their recent listing defaults
(90 and 30 days respectively). Configuring a bound makes the selected interval
discoverable. Bounds are enforced on reads, metadata, listings, and VFS searches;
separately installed account CLIs retain their own access. Read-only does not
freeze upstream changes. Change bounds by rebuilding/remounting the VFS, which
clears its cached state.
