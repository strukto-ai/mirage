## Self-hosted Mirage

Use a Mirage server build with E2B compatibility. Existing E2B SDK clients
and tools can connect to Mirage if they let you change both E2B URLs and use
the supported operations. Mirage supports sandbox creation, reconnection,
health checks, timeout updates, and deletion, plus foreground shell commands
and file operations.

### Configure the server

Use your existing Mirage token. To set a token for a new server, run these
commands in the shell where you’ll launch Mirage.

```bash
export MIRAGE_AUTH_MODE=token
export MIRAGE_AUTH_TOKEN="${MIRAGE_AUTH_TOKEN:-$(openssl rand -hex 32)}"
```

Start Mirage with one worker on port 8765 using the
[HTTP setup guide](/home/access/http#launch-a-server). By default, each
sandbox starts with its own writable, in-memory `/home/user`.

### Point your client at Mirage

Set these variables in the environment of the app that runs the SDK or tool.
Use the same token you set on the server as `E2B_API_KEY`.

```bash
export E2B_API_URL=http://127.0.0.1:8765
export E2B_SANDBOX_URL=http://127.0.0.1:8765
export E2B_HTTP_VERSION=1.1
export E2B_API_KEY="$MIRAGE_AUTH_TOKEN"
```

Both URLs use Mirage's HTTP port. Use your server's reachable address if
the app runs on another host. If the app uses a separate shell, set
`E2B_API_KEY` to the server token in that shell.

If your local daemon uses its default token file, set the key with
`export E2B_API_KEY="$(cat ~/.mirage/auth_token)"`.

Keep your SDK calls and tool registration. If the app passes an endpoint or
key explicitly, update that value to use Mirage. If the app sets a template
name, use `base`.

### Verify the connection

This example uses the Python E2B SDK version 2.64.0.

```python
from e2b import Sandbox

sandbox = Sandbox.create()
try:
    sandbox.files.write("hello.txt", "Hello from Mirage\n")
    print(sandbox.commands.run("cat hello.txt").stdout, end="")
finally:
    sandbox.kill()
```

The script prints `Hello from Mirage`. The upload and command use the same
Mirage workspace.

### Use a saved Mirage template

If you want custom mounts or policies, save a Mirage workspace template
with a writable `/home/user`. Set `MIRAGE_E2B_TEMPLATE` to that template’s
name before starting the server. Clients can keep requesting `base` or
pass the configured name. Mirage uses your saved template for either name.

## Compatibility

| SDK area | Supported operations | Behavioral differences |
| --- | --- | --- |
| Sandbox | Create, reconnect to a live sandbox, check health, set its timeout, and kill it. | Each sandbox is an ephemeral Mirage workspace. The timeout controls the workspace's lifetime. |
| Commands | Run and stream a shell command, list active commands, send stdin, close stdin, and cancel a command with the SDK's `kill` method. | Use the SDK's default Bash command form and opt in to stdin when needed. Command IDs identify live Mirage shell executions. Commands end when the output stream disconnects, the deadline passes, or the sandbox ends. Alternate shells, interactive terminals, detached reattach, process tags, and other signals are unsupported. |
| Filesystem | Read, upload one file, get file information, check existence, list, make a directory, rename, and remove a file or empty directory. | Relative paths start at `/home/user`. A rename stays within one mount. Upload requests are limited to 64 MiB, including the multipart envelope. Watchers, file metadata on upload, and recursive removal through the file API are unsupported. |

Sandbox listing and info, pause and resume, VM metrics, and Code Interpreter
are unsupported. E2B's listing and info responses require VM allocations
that a Mirage workspace does not have. Reconnecting preserves the live
workspace. Reboot and restore options are rejected.

The SDK can generate signed transfer URLs and port hostnames
locally. Those URLs require sandbox-specific ingress. Connect to the local
server through the SDK's normal file methods.

Workspace policy comes from Mirage. Create requests can set the template name,
timeout, and command environment variables. Requests for custom metadata,
VM sizing, network overrides, automatic pause, or idempotency keys are
rejected before creating a workspace. Recognized unsupported requests return
HTTP `501` or Connect `unimplemented`.

Run commands and file operations as the SDK's default `user`. Requests for
another Linux user are rejected. Workspace profiles and mounts determine
what commands and files the sandbox can use. E2B template builds and template
management are unavailable through this adapter. You can save a Mirage
template through the native Mirage API and configure it as described above.

### How the adapter works

The E2B routes share the Mirage server's HTTP listener. Lifecycle requests
use the Mirage token as the E2B API key. When a sandbox opens, the adapter
gives it a separate access token for its command and file requests. The
sandbox ID is the workspace ID.

The adapter owns the lease, request deadlines, and E2B response formats.
Commands use the Mirage shell, and files use the workspace filesystem.
Stopping the workspace revokes the lease before the server closes the runner.
Shutdown waits for already-admitted backend file work to settle.

File removal uses the workspace's file and empty-directory operations.
The adapter refuses to walk a directory and delete its children because the
directory can change during that walk.
