## Self-hosted Mirage

Use a Mirage server build with E2B compatibility. Existing E2B SDK clients
and tools can connect to Mirage if they let you change both E2B URLs and use
the supported operations. Mirage supports sandbox creation, reconnection,
health checks, timeout updates, and deletion, plus foreground shell commands
and file operations.

### Configure the server

Use your existing Mirage token. To set a token for a new server, run these
commands in the shell where you’ll launch Mirage.

```bash
export MIRAGE_AUTH_MODE=token
export MIRAGE_AUTH_TOKEN="${MIRAGE_AUTH_TOKEN:-$(openssl rand -hex 32)}"
```

Start Mirage with one worker on port 8765 using the
[HTTP setup guide](/home/access/http#launch-a-server). By default, each
sandbox starts with its own writable, in-memory `/home/user`.

### Point your client at Mirage

Set these variables in the environment of the app that runs the SDK or tool.
Use the same token you set on the server as `E2B_API_KEY`.

```bash
export E2B_API_URL=http://127.0.0.1:8765
export E2B_SANDBOX_URL=http://127.0.0.1:8765
export E2B_HTTP_VERSION=1.1
export E2B_API_KEY="$MIRAGE_AUTH_TOKEN"
```

Both URLs use Mirage's HTTP port. Use your server's reachable address if
the app runs on another host. If the app uses a separate shell, set
`E2B_API_KEY` to the server token in that shell.

If your local daemon uses its default token file, set the key with
`export E2B_API_KEY="$(cat ~/.mirage/auth_token)"`.

Keep your SDK calls and tool registration. If the app passes an endpoint or
key explicitly, update that value to use Mirage. If the app sets a template
name, use `base`.

### Verify the connection

This example uses the Python E2B SDK version 2.64.0.

```python
from e2b import Sandbox

sandbox = Sandbox.create()
try:
    sandbox.files.write("hello.txt", "Hello from Mirage\n")
    print(sandbox.commands.run("cat hello.txt").stdout, end="")
finally:
    sandbox.kill()
```

The script prints `Hello from Mirage`. The upload and command use the same
Mirage workspace.

### Use a saved Mirage template

If you want custom mounts or policies, save a Mirage workspace template
with a writable `/home/user`. Set `MIRAGE_E2B_TEMPLATE` to that template’s
name before starting the server. Clients can keep requesting `base` or
pass the configured name. Mirage uses your saved template for either name.
