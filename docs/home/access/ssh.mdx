The Mirage server can listen for SSH next to HTTP. The SSH username names the
workspace, every line runs in Mirage's shell, and every file operation goes
through the workspace's mounts.

## Set up

<Steps>
  <Step title="Install the SSH library">
    <Tabs>
      <Tab title="Python" icon="/images/python-logo.svg">
        ```bash
        pip install 'mirage-ai[ssh]'
        ```
      </Tab>
      <Tab title="TypeScript" icon="/images/typescript-logo.svg">
        ```bash
        npm install -g ssh2
        ```
      </Tab>
    </Tabs>
  </Step>
  <Step title="Pick a port">
    ```bash
    mirage daemon config set ssh_port 2222
    ```
    SSH stays off until a port is set.
  </Step>
  <Step title="Authorize your key">
    ```bash
    mkdir -p ~/.mirage/ssh
    cat ~/.ssh/id_ed25519.pub >> ~/.mirage/ssh/authorized_keys
    ```
    Only public keys log in, and the file is read on every login.
  </Step>
  <Step title="Restart the server">
    ```bash
    mirage daemon restart
    mirage workspace create workspace.yaml --id demo
    ```
  </Step>
</Steps>

<Accordion title="Settings">
  An environment variable wins over `~/.mirage/config.toml`, which wins over the
  default.

  | Key | Env var | Default |
  | --- | --- | --- |
  | `ssh_port` | `MIRAGE_SSH_PORT` | unset (off) |
  | `ssh_host` | `MIRAGE_SSH_HOST` | `127.0.0.1` |
  | `ssh_host_key_file` | `MIRAGE_SSH_HOST_KEY_FILE` | `~/.mirage/ssh/host_ed25519_key` |
  | `ssh_authorized_keys` | `MIRAGE_SSH_AUTHORIZED_KEYS` | `~/.mirage/ssh/authorized_keys` |

  The server makes its host key on first start and keeps it, so your
  `known_hosts` entry stays valid.
</Accordion>

## Connect

| Command | Does |
| --- | --- |
| `ssh -p 2222 demo@127.0.0.1` | Open a shell in workspace `demo`. |
| `ssh -p 2222 demo@127.0.0.1 'ls /data \| wc -l'` | Run one line. |
| `ssh -T -p 2222 demo@127.0.0.1 < setup.sh` | Run a script. |
| `sftp -P 2222 demo@127.0.0.1` | Transfer files. |
| `scp -P 2222 notes.txt demo@127.0.0.1:/data/` | Copy a file in. |
| `sshfs -p 2222 -o direct_io demo@127.0.0.1:/ ~/mnt/demo` | Show the workspace as a local folder. |

Each run gets a fresh session, so a `cd` or `export` never leaks between them.
Ctrl-C cancels the running line, and `ssh host cmd` exits with the line's status.
To mount a folder on the machine running Mirage instead, use [FUSE](/home/setup/fuse).

### Over HTTPS

A hosted server carries SSH over its HTTPS port, so it needs no SSH port or key.
`mirage ssh-proxy` relays it with the CLI's token:

```text ~/.ssh/config
Host mirage
  ProxyCommand mirage ssh-proxy %r
```

Then `ssh demo@mirage`, `sftp demo@mirage`, `scp notes.txt demo@mirage:/data/`
and `sshfs -o direct_io demo@mirage:/ ~/mnt/demo` all work. The CLI sends its
token, your [`mirage login`](/home/access/cli#log-in) on a hosted server, and the
login runs under the workspace's default profile.

### In an app

A workspace a FastAPI or Express app holds takes SSH the same way: add it
to a registry, under the name logins use, and start the SSH server next to the
app.

<Tabs>
  <Tab title="FastAPI" icon="/images/python-logo.svg">
    ```python app.py
    from contextlib import asynccontextmanager
    from pathlib import Path

    from fastapi import FastAPI

    from mirage import RAMVFS, MountMode, Workspace
    from mirage.server.registry import WorkspaceRegistry
    from mirage.server.ssh.config import SSHConfig
    from mirage.server.ssh.server import start_ssh_server

    registry = WorkspaceRegistry()
    registry.add(Workspace({"/data": RAMVFS()}, mode=MountMode.WRITE), "demo")
    keys = Path.home() / ".mirage" / "ssh"


    @asynccontextmanager
    async def lifespan(app: FastAPI):
        ssh = await start_ssh_server(
            registry,
            SSHConfig(
                port=2222,
                host="127.0.0.1",
                host_key_file=keys / "host_ed25519_key",
                authorized_keys_file=keys / "authorized_keys",
            ),
        )
        yield
        ssh.close()
        await ssh.wait_closed()


    app = FastAPI(lifespan=lifespan)
    ```

    To carry SSH over the app's own port as well, mount
    [`build_app()`](/python/access/server) in it, which serves the route
    `mirage ssh-proxy` reaches.
  </Tab>
  <Tab title="Express" icon="/images/typescript-logo.svg">
    ```typescript app.mjs
    import { createServer } from 'node:http'
    import { homedir } from 'node:os'
    import { join } from 'node:path'
    import express from 'express'
    import { WebSocketServer, createWebSocketStream } from 'ws'
    import { MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'
    import { WorkspaceRegistry } from '@struktoai/mirage-server/registry'
    import { serveTunnel, startSSHServer } from '@struktoai/mirage-server/ssh/server'

    const registry = new WorkspaceRegistry()
    registry.add(new Workspace({ '/data': new RAMVFS() }, { mode: MountMode.WRITE }), 'demo')
    const keys = join(homedir(), '.mirage', 'ssh')
    const config = {
      port: 2222,
      host: '127.0.0.1',
      hostKeyFile: join(keys, 'host_ed25519_key'),
      authorizedKeysFile: join(keys, 'authorized_keys'),
    }
    await startSSHServer(registry, config)

    const app = express()
    const server = createServer(app)
    const sockets = new WebSocketServer({ noServer: true })
    const allowed = (req) => req.headers.authorization === `Bearer ${process.env.APP_TOKEN}`
    server.on('upgrade', (req, socket, head) => {
      const id = /^\/ssh\/([^/?]+)$/.exec(req.url ?? '')?.[1]
      if (id === undefined || !allowed(req) || registry.visible(id, null) === null) {
        socket.destroy()
        return
      }
      sockets.handleUpgrade(req, socket, head, (ws) => {
        const peer = { address: req.socket.remoteAddress ?? '', port: req.socket.remotePort ?? 0 }
        const local = { address: req.socket.localAddress ?? '', port: req.socket.localPort ?? 0 }
        void serveTunnel(registry, config, createWebSocketStream(ws), id, null, peer, local)
      })
    })
    server.listen(3000, '127.0.0.1')
    ```

    `serveTunnel` carries SSH over the app's own port and admits the login
    without a key, so the upgrade checks the request's credentials first
    (`allowed`). A ProxyCommand that relays its stdin and stdout over the
    WebSocket with those credentials connects to it.
  </Tab>
</Tabs>

## Editors

Cursor, VS Code and Antigravity open a workspace over SSH by installing their
own server on a [machine](/home/setup/machine/overview) the workspace sends its
lines to. [Editors over SSH](/home/agents/remote-ssh) sets it up.

## Auth (optional)

In `local` and `token` mode, an authorized key opens every workspace under the
workspace's default profile. Options in front of a key in `authorized_keys`
narrow it:

```text ~/.mirage/ssh/authorized_keys
mirage-profile="guarded" ssh-ed25519 AAAA... agent-a
mirage-account="alice",mirage-profile="guarded" ssh-ed25519 AAAA... alice-agent
ssh-ed25519 AAAA... me
```

| Option | Does |
| --- | --- |
| `mirage-profile` | Runs every login of the key under this [session profile](/home/configuration/session). The server reads it, so a key cannot pick looser rules. |
| `mirage-account` | Opens only the workspaces this [account](/home/access/http#accounts) created. Another account's workspace answers like a missing one. |

On a [`jwt`](/home/access/http#jwt) server, each login reaches only its
account's workspaces:

| Way in | How |
| --- | --- |
| [Over HTTPS](#over-https) | `mirage login`, then connect through `mirage ssh-proxy`. Your JWT is the account; no key needed. |
| SSH port | The operator adds `mirage-account="you"` to your key. A key without it opens nothing. |

<Accordion title="Account rules in detail">
  - The account holds for shell, exec, `sftp` and `scp` alike.
  - In `local` and `token` mode, a key without `mirage-account` opens every
    workspace.
  - An option that is empty or given twice opens nothing.
</Accordion>

<Accordion title="How sessions behave">
  - Each `ssh`, `sftp` or `scp` run gets a fresh session, closed when it ends.
  - The session's profile and the mount modes apply as in any shell: a
    read-only mount refuses `sftp put`.
  - Output streams as the line prints it.
  - Ctrl-C cancels the running line and sets `$?` to 130.
  - A dropped connection ends the line as sshd would. With a terminal it
    hangs the line up with `SIGHUP`. Without one (`ssh -T`, as editors
    connect), it sends nothing: the line runs on without input, and is hung
    up the first time it writes. On a machine, a process that left the
    line's session with `setsid`, or ignores `SIGHUP`, keeps running.
  - The server sends a keepalive every 15 seconds and closes a connection that
    misses three, so a half-open one hangs its line up as well.
  - A port forward reaches `127.0.0.1` or `localhost` only, where the
    session's lines run ([Editors](#editors)). Agents and X11 are never
    forwarded.
</Accordion>
