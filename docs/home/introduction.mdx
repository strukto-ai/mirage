LLMs are post-trained in terminal environments, so AI agents are most familiar
with the terminal interface. But a terminal today is bound to a single machine
and its operating system kernel, with its files and its computation on that
same machine.

Mirage is a virtual terminal for AI agents that separates the terminal
interface from the data storage and the computing machines. It virtualizes the
shell, the filesystem, the CLIs and the machines. Each virtual terminal starts
with only KBs of memory, so AI agents can use terminal environments
everywhere, inside an application, a mobile app, a browser tab, a FastAPI or
Express server, and even an edge device such as a Raspberry Pi.

- **Controllable.** Each agent gets only the files, commands, credentials and
  machines its profile allows.
- **Scriptable.** The whole terminal is defined in code or one config file, from
  its filesystems, CLIs and machines to its rules.
- **Managed.** State lives on infrastructure that already runs, such as RAM,
  disk, Redis or S3, and every command is recorded and can be exported as an
  OpenTelemetry trace.
- **Lightweight.** Each workspace takes only KBs of memory and Mirage is async
  from the shell down to each service call, so one process serves many agents at
  once. It can be deployed almost everywhere, to a Python or TypeScript server,
  a browser tab, a Cloudflare Worker or a Raspberry Pi.

## Architecture

<img noZoom src="/images/mirage-overview-dark.svg" alt="Mirage connects agents to files, tools, machines and runtimes, with access controls and notifications" className="hidden dark:block w-full" />

- **[Virtual filesystem](/home/setup/vfs).** Virtualize S3, Drive, Slack, databases and more under one root, accessible with `ls`, `cat`, `grep` and `find`.
- **[Virtual CLIs](/home/setup/clis).** Give agents commands such as `git`, `slack` and `ntn`, with credentials configured per tool.
- **[Mirage Shell](/home/core/shell).** Compose files, CLIs and machines with pipes, redirects, variables and jobs.
- **[Session profiles](/home/configuration/session).** Choose what each agent can run and which files and folders it can see.
- **[Policy engine](/home/policy/policies).** Apply rules to commands, file operations and connections before they run.
- **[Machines](/home/setup/machine/overview).** Run programs in the workspace, on your host, or on a container, microVM, cloud sandbox or SSH host.
  - **[Runtimes](/home/setup/runtime/overview).** Run Python and JavaScript on an interpreter inside a machine.
- **[Service credentials](/home/service-credentials).** Connect credentials from environment variables, dotenv, AWS Secrets Manager or 1Password.
- **[Notifications](/home/notifications).** Notify agents about external file or directory changes in the virtual filesystem.

## Benefits

- **Fewer tokens.** One shell interface replaces a tool per service, so agents
  use up to 90% fewer tokens than with MCP tools
  ([AgentVFS](https://agentvfs.org/blogs/agentvfs-1)).
- **Low cost.** A sandbox reserves memory for every agent, busy or idle. An idle
  Mirage terminal is a record of about 10 KB in your server's memory, so one
  server holds thousands. See the
  [comparison](/home/examples/in-process-terminal#infrastructure-cost).
- **Deep integration with each service.** The virtual filesystem translates
  Unix commands into each service's own features, so `grep` or `rg` runs as
  the service's search instead of reading every file. See
  [Search](/home/integration/search).
- **Full control and safety.** Choose which files each agent can see and which
  commands it can run with [session profiles](/home/configuration/session) and
  [policies](/home/policy/overview). Agents use
  [credentials](/home/service-credentials) without seeing them: keys stay in
  the server's memory, never in a file or variable an agent can read, so an
  agent cannot leak them.

## Try Mirage

[Install Mirage](/home/install), then create a workspace with an in-memory
filesystem, write a file with a POSIX-style call, and search it with the shell.
No credentials or services are needed.

<Tabs>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    import asyncio

    from mirage import MountMode, RAMVFS, Workspace


    async def main() -> None:
        ws = Workspace({"/data": RAMVFS()}, mode=MountMode.WRITE)
        await ws.vfs.write("/data/hello.txt", b"hello mirage\n")
        result = await ws.shell("grep -n hello /data/hello.txt")
        print(await result.stdout_str(), end="")
        await ws.close()


    asyncio.run(main())
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'

    const ws = new Workspace({ '/data': new RAMVFS() }, { mode: MountMode.WRITE })
    await ws.vfs.write('/data/hello.txt', new TextEncoder().encode('hello mirage\n'))
    const result = await ws.shell('grep -n hello /data/hello.txt')
    process.stdout.write(result.stdoutText)
    await ws.close()
    ```
  </Tab>
  <Tab title="CLI" icon="terminal">
    [Install the CLI](/home/install#cli), then run:

    ```bash
    cat > workspace.yaml <<'EOF'
    mounts:
      /data:
        vfs: ram
        mode: write
    EOF

    mirage workspace create workspace.yaml --id hello
    echo "hello mirage" | mirage workspace vfs write /data/hello.txt -w hello
    mirage shell -w hello -c 'grep -n hello /data/hello.txt'
    ```
  </Tab>
</Tabs>

The search prints:

```text
1:hello mirage
```

`/data` is a path inside Mirage. Replace RAM with a [supported VFS](/home/setup/vfs)
to use the same commands on your own data. Continue with the
[Python](/python/quickstart) or [TypeScript](/typescript/quickstart) quickstart.

## FAQ

<AccordionGroup>
  <Accordion title="Do I need FUSE?">
    It is not required, but use <a href="/home/setup/fuse">FUSE</a> where the platform supports it. Without it, agents use workspace files through Mirage. With it, the workspace is a real folder on the host, so host tools such as editors and language servers can open those files too.
  </Accordion>
  <Accordion title="Where does the shell run? Is it really bash?">
    Mirage provides a Bash-compatible shell in your application. It supports common commands, pipes, redirects, variables and jobs. See the <a href="/home/core/shell">shell guide</a> for supported behavior and differences from Bash.
  </Accordion>
  <Accordion title="Is it sandboxed?">
    The shell sees only the virtual filesystems in its workspace, and a session profile can narrow that further. A program sent to a machine gets that machine's file and network access, so check <a href="/home/setup/machine/overview#files">machine file and network access</a> before choosing one.
  </Accordion>
  <Accordion title="What about latency and cost?">
    Operations use the APIs of the services you connect, so their latency and usage charges apply.
  </Accordion>
  <Accordion title="Which agent frameworks are supported?">
    Any agent that can call a shell tool can use Mirage. See the <a href="/home/agents">agent integrations</a> for setup guides.
  </Accordion>
  <Accordion title="Python or TypeScript?">
    TypeScript is recommended. It runs in Node, the browser and Cloudflare Workers. Both SDKs provide workspaces, shell commands and service integrations, and the <a href="/home/setup/runtime/overview">runtime comparison</a> shows where their runtimes differ. Start with the <a href="/typescript/quickstart">TypeScript</a> or <a href="/python/quickstart">Python</a> quickstart.
  </Accordion>
  <Accordion title="What if a VFS I want isn't supported yet?">
    You can add a custom filesystem. See <a href="/python/vfs/new">Add a VFS</a> for the required API and examples.
  </Accordion>
</AccordionGroup>
