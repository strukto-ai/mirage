A workspace needs no services. Out of the box it keeps everything in memory
and runs programs inside Mirage. Each part below can move onto infrastructure
you run: Redis, a disk, an S3 bucket, a sandbox or the host's kernel.

## What you can place

| Part | Holds | Choices | Key |
| --- | --- | --- | --- |
| [State](#state) | Symlinks and file attributes, command history, sessions, background jobs and the processes each instance runs | `ram`, `disk`, `redis`; sessions also `s3` | `store` |
| [File cache](#share-the-file-cache-and-index) | File content Mirage has read | `ram`, `redis` | `cache` |
| [Index](#share-the-file-cache-and-index) | Directory listings and file metadata | `ram`, `redis` | `index`, or a mount's own `index` |
| [Runtimes](/home/setup/runtime/overview) | Where programs such as `python3` or `ffmpeg` run | Inside Mirage, on the host, or in a container, VM, cloud sandbox or SSH machine | `runtimes` |
| [Host folders](/home/setup/fuse) | A mount shown as a folder on the host | `fuse`, `fskit`, `nfs` | a mount's `backend` |
| [Credentials](/home/authentication) | Where secret values are read from | The environment, a dotenv file, AWS Secrets Manager, 1Password | `secrets` |
| [Server](#server) | Where the server listens, keeps workspaces and writes snapshots | A port, a state directory, an S3 bucket | `mirage config`, environment variables |

A workspace built in code keeps its state in memory. One the server builds,
through `mirage workspace create` or `POST /v1/workspaces`, keeps it on disk
under `~/.mirage/state`. A `store` block replaces either default.

## Where you set it

One config describes a workspace, the same [YAML](/home/configuration) on
every surface. Python and TypeScript also take each part as a constructor
argument, shown in the [examples](#examples).

| Surface | Takes the config as |
| --- | --- |
| [CLI](/home/access/cli) | A YAML or JSON file: `mirage workspace create workspace.yaml` |
| [HTTP](/home/access/http) | JSON under `config` in `POST /v1/workspaces` |
| Python | `load_config("workspace.yaml")` |
| TypeScript | `loadWorkspaceConfigFile("workspace.yaml")` |

<Tabs>
  <Tab title="CLI" icon="terminal">
    ```bash
    mirage workspace create workspace.yaml --id agent
    ```
  </Tab>
  <Tab title="HTTP" icon="globe">
    ```bash
    curl http://127.0.0.1:8765/v1/workspaces \
      -H "Authorization: Bearer $MIRAGE_AUTH_TOKEN" \
      -H 'Content-Type: application/json' \
      -d '{"id":"agent","config":{"store":{"type":"redis","url":"redis://redis.internal:6379/0"},"mounts":{"/data":{"vfs":"ram"}}}}'
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import Workspace
    from mirage.config import load_config

    ws = Workspace(**load_config("workspace.yaml").to_workspace_kwargs())
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { Workspace, configToWorkspaceArgs, loadWorkspaceConfigFile } from '@struktoai/mirage-node'

    const { mounts, options } = await configToWorkspaceArgs(loadWorkspaceConfigFile('workspace.yaml'))
    const ws = new Workspace(mounts, options)
    ```
  </Tab>
</Tabs>

The server's own settings sit outside the workspace config; see [Server](#server).

## State

`store` sets where a workspace keeps its state, by its `workspace_id`. Give
the workspace a fixed id whenever its state should be found again, after a
restart or by another process.

| `type` | Survives a restart | Shared with |
| --- | --- | --- |
| `ram` | No | Workspaces in the same process given the same store object |
| `disk` | Yes | Processes on the same machine. Background jobs stay in each process's memory. |
| `redis` | Yes | Every process on that Redis, on any machine |

A group key moves one part of the state to a backend of its own: `namespace`
for symlinks and file attributes, `observer` for history, `workspace` for
sessions, which also takes `s3`, and `jobs` for background jobs and
processes, which takes `ram` or `redis`. Every key is listed in
[Workspace configuration](/home/configuration#cache-index-and-store).

## Examples

### Keep state across restarts

Sessions, with their working directories and variables, history and
symlinks come back when the workspace is built again under the same id.

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml workspace.yaml
    workspace_id: agent
    store:
      type: disk
      root: /var/lib/mirage
    mounts:
      /data:
        vfs: disk
        config:
          root: /srv/data
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import MountMode, Workspace
    from mirage.vfs.disk import DiskVFS
    from mirage.workspace.store.disk import DiskWorkspaceStateStore

    ws = Workspace(
        {"/data": DiskVFS(root="/srv/data")},
        mode=MountMode.WRITE,
        workspace_id="agent",
        store=DiskWorkspaceStateStore(root="/var/lib/mirage"),
        owns_store=True,
    )
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { DiskVFS, DiskWorkspaceStateStore, MountMode, Workspace } from '@struktoai/mirage-node'

    const ws = new Workspace(
      { '/data': new DiskVFS({ root: '/srv/data' }) },
      {
        mode: MountMode.WRITE,
        workspaceId: 'agent',
        store: new DiskWorkspaceStateStore({ root: '/var/lib/mirage' }),
        ownsStore: true,
      },
    )
    ```
  </Tab>
</Tabs>

Background jobs end with the process that runs them. To list them from other
processes on the machine as well, add a `jobs` group on Redis:

```yaml
store:
  type: disk
  root: /var/lib/mirage
  jobs:
    type: redis
    url: redis://localhost:6379/0
```

### Run several instances of one workspace

Every process that builds the workspace under the same id on one Redis is an
instance of it, on one machine or several, behind a load balancer or as
replicas of one agent.

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml workspace.yaml
    workspace_id: agent
    store:
      type: redis
      url: redis://redis.internal:6379/0
    mounts:
      /data:
        vfs: s3
        config:
          bucket: agent-data
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import MountMode, Workspace
    from mirage.vfs.s3 import S3VFS, S3Config
    from mirage.workspace.store.redis import RedisWorkspaceStateStore

    ws = Workspace(
        {"/data": S3VFS(S3Config(bucket="agent-data"))},
        mode=MountMode.WRITE,
        workspace_id="agent",
        store=RedisWorkspaceStateStore(url="redis://redis.internal:6379/0"),
        owns_store=True,
    )
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { MountMode, RedisWorkspaceStateStore, S3VFS, Workspace } from '@struktoai/mirage-node'

    const ws = new Workspace(
      { '/data': new S3VFS({ bucket: 'agent-data' }) },
      {
        mode: MountMode.WRITE,
        workspaceId: 'agent',
        store: new RedisWorkspaceStateStore({ url: 'redis://redis.internal:6379/0' }),
        ownsStore: true,
      },
    )
    ```
  </Tab>
  <Tab title="Servers" icon="server">
    ```bash
    for server in http://mirage-a:8765 http://mirage-b:8765; do
      curl "$server/v1/workspaces" \
        -H "Authorization: Bearer $MIRAGE_AUTH_TOKEN" \
        -H 'Content-Type: application/json' \
        --data-binary @workspace.json
    done
    ```
  </Tab>
</Tabs>

On the servers, `workspace.json` holds `{"id": "agent", "config": {...}}`
with the same config on each. The instances then share:

- Sessions, history and symlinks.
- Each session's background jobs: `jobs`, `wait`, `kill %N` and `fg %N`
  work on any instance, whichever started the job.
- Processes: `ps` lists the other instances' as `owner:pid`, and
  `kill owner:pid` stops one.
- Cleanup: when an instance dies, the next one to start stops the programs
  it left running.

A session sees only its own processes, on every instance; a profile with
[`processes: workspace`](/home/profiles) widens that to every session's.
[Shell](/home/core/shell#jobs-across-instances) describes the details.

### Keep sessions on S3

Keep the fast-changing state on Redis and sessions in a bucket:

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml
    store:
      type: redis
      url: redis://redis.internal:6379/0
      workspace:
        type: s3
        bucket: agent-state
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage.vfs.s3 import S3Config
    from mirage.workspace.store.redis import RedisWorkspaceStateStore
    from mirage.workspace.store.s3 import S3WorkspaceStateStore

    store = RedisWorkspaceStateStore(
        url="redis://redis.internal:6379/0",
        workspace=S3WorkspaceStateStore(S3Config(bucket="agent-state")),
    )
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { RedisWorkspaceStateStore, S3WorkspaceStateStore } from '@struktoai/mirage-node'

    const store = new RedisWorkspaceStateStore({
      url: 'redis://redis.internal:6379/0',
      workspace: new S3WorkspaceStateStore({ bucket: 'agent-state' }),
    })
    ```
  </Tab>
</Tabs>

### Share the file cache and index

With the cache and index on Redis, a file one instance read is served to the
others without asking the backend again, and one listing answers them all.

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml
    cache:
      type: redis
      url: redis://redis.internal:6379/0
    index:
      type: redis
      url: redis://redis.internal:6379/0
      ttl: 300
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import Workspace
    from mirage.cache.file.config import RedisCacheConfig
    from mirage.cache.index import RedisIndexConfig

    ws = Workspace(
        mounts,
        workspace_id="agent",
        cache=RedisCacheConfig(url="redis://redis.internal:6379/0"),
        index=RedisIndexConfig(url="redis://redis.internal:6379/0", ttl=300),
    )
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { Workspace } from '@struktoai/mirage-node'

    const ws = new Workspace(mounts, {
      workspaceId: 'agent',
      cache: { type: 'redis', url: 'redis://redis.internal:6379/0' },
      index: { type: 'redis', url: 'redis://redis.internal:6379/0', ttl: 300 },
    })
    ```
  </Tab>
</Tabs>

The keys belong to the workspace, so two workspaces on one Redis never read
each other's files. Naming the same `key_prefix` in several workspaces shares
one cache between them, which is safe only when they mount the same backends
at the same paths. On Redis, `limit` does not evict anything; cap the
server's memory with `maxmemory` instead.

### Run programs in a sandbox

A runtime entry sends programs to a container, VM, cloud sandbox or SSH
machine. Each provider's page lists its config.

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml
    mode: exec
    runtimes:
      - name: docker
        config:
          container: my-sandbox
          mount_type: ssh
    mounts:
      /data:
        vfs: ram
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import RAMVFS, MountMode, Workspace
    from mirage.runtime.sandbox.docker import DockerRuntime

    runtime = DockerRuntime(config={"container": "my-sandbox", "mount_type": "ssh"})
    ws = Workspace({"/data": RAMVFS()}, mode=MountMode.EXEC, runtimes=[runtime])
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { DockerRuntime, MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'

    const runtime = new DockerRuntime({ config: { container: 'my-sandbox', mountType: 'ssh' } })
    const ws = new Workspace({ '/data': new RAMVFS() }, { mode: MountMode.EXEC, runtimes: [runtime] })
    ```
  </Tab>
</Tabs>

See [Runtimes](/home/setup/runtime/overview) for which programs each runtime
takes and [Sandboxes](/home/setup/runtime/sandbox) for the providers.

## Server

The server holds workspaces for the CLI, HTTP, MCP, RPC and SSH. Its settings
apply to every workspace it holds.

| Setting | `mirage config` key | Environment variable | `build_app` / `buildApp` |
| --- | --- | --- | --- |
| Port | `port` | `MIRAGE_DAEMON_PORT` | the port you serve the app on |
| Host names it answers | `allowed_hosts` | `MIRAGE_ALLOWED_HOSTS` | `allowed_hosts` / `allowedHosts` |
| Authentication | `auth_mode`, `jwt_*` | `MIRAGE_AUTH_MODE`, `MIRAGE_JWT_*` | `auth_config` / `authConfig` |
| SSH server | `ssh_*` | `MIRAGE_SSH_*` | `ssh_config` / `sshConfig` |
| State directory | | `MIRAGE_HOME`, as `$MIRAGE_HOME/state` | `state_root` / `stateRoot` |
| Snapshot bucket | | | `snapshot_store` / `snapshotStore` |

```bash
mirage config set port 9000
mirage daemon restart
```

A setting applies when the server next starts. A workspace created again
under the same id finds its state in the state directory, unless its config
names a `store` of its own. The CLI's settings
are on the [CLI page](/home/access/cli#config); running the server yourself
is covered for [Python](/python/access/server) and
[TypeScript](/typescript/access/server).
