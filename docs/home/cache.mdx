## What It Does

Every `Workspace` ships with a **two-layer cache** so repeated work against remote backends (S3, GDrive, Slack, ...) hits local state instead of the network:

- **Index cache.** Listings and metadata. The first directory walk hits the API; later ones are served from the index until the listing expires.
- **File cache.** Object bytes. The first read streams from origin; later pipelines read from cache.

<CodeGroup>

```python Python
from mirage import Workspace
from mirage.vfs.s3 import S3Config, S3VFS

ws = Workspace({"/s3": S3VFS(S3Config(bucket="my-bucket"))})

# 1. Index miss → S3 LISTs of /s3/data/. Every folder's listing is stored.
await ws.shell('find /s3/data/ -name "*.jsonl"')

# 2. Index hit → 0 network calls.
await ws.shell("ls /s3/data/")

# 3. File miss → S3 GET. Bytes stored in the file cache.
await ws.shell("cat /s3/data/log.jsonl | wc -l")

# 4. File hit → 0 network calls.
await ws.shell("grep alert /s3/data/log.jsonl")
```

```typescript TypeScript
import { S3VFS, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace({ '/s3': new S3VFS({ bucket: 'my-bucket' }) })

// 1. Index miss → S3 LISTs of /s3/data/. Every folder's listing is stored.
await ws.shell('find /s3/data/ -name "*.jsonl"')

// 2. Index hit → 0 network calls.
await ws.shell('ls /s3/data/')

// 3. File miss → S3 GET. Bytes stored in the file cache.
await ws.shell('cat /s3/data/log.jsonl | wc -l')

// 4. File hit → 0 network calls.
await ws.shell('grep alert /s3/data/log.jsonl')
```

</CodeGroup>

The network counts above assume the default `read: bounded`. Under `read: fresh`, step 2 lists the folder again, step 3 sends one metadata request before downloading, and step 4 checks the cached copy first. An `ls` caches the one folder it lists; a `find` or `ls -R` caches the whole subtree it walks.

## The Read Policy

Each mount sets two things in its mount block: `read:`, how its cache is served, and `ttl:`, the longest any cached file or listing from that mount is kept (600 seconds by default).

A file's **version** is the backend's marker for its content: an ETag, content hash or modified time, depending on the backend. A **check** is a metadata request (a few on backends that resolve a path folder by folder, such as Google Drive) that compares that version with the cached copy.

| | `read: bounded` (default) | `read: fresh` |
| --- | --- | --- |
| A cached file | Served without a check. | Checked against the backend first: one check per cached file a command reads. |
| A cached listing | Served with no request. | Checked or listed again once per command. |
| An outside change | Can stay hidden for up to the mount's `ttl:`. | Seen by the next command that reads it: a changed file is downloaded again and a deleted one is gone. |
| Your own writes through this workspace | Seen by the next command. | Seen by the next command. |

<Tip>
**Which to choose.** `bounded` when the data changes rarely or a few minutes of staleness is acceptable; after the first read it sends no checks. `fresh` when the agent must see changes made outside mirage, at the cost of a request for each cached file it reads and each cached folder it lists.
</Tip>

<CodeGroup>

```python Python
from mirage import Mount, ReadPolicy, ReadSpec, Workspace
from mirage.vfs.s3 import S3Config, S3VFS

ws = Workspace({
    "/reports": Mount(S3VFS(S3Config(bucket="reports")),
                      read=ReadSpec(policy=ReadPolicy.BOUNDED, ttl=60)),
    "/feed": Mount(S3VFS(S3Config(bucket="feed")),
                   read=ReadSpec(policy=ReadPolicy.FRESH)),
})
```

```typescript TypeScript
import { Mount, ReadPolicy, S3VFS, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace({
  '/reports': new Mount(new S3VFS({ bucket: 'reports' }),
    { read: { policy: ReadPolicy.BOUNDED, ttl: 60 } }),
  '/feed': new Mount(new S3VFS({ bucket: 'feed' }),
    { read: { policy: ReadPolicy.FRESH, ttl: 600 } }),
})
```

```yaml YAML
mounts:
  /reports:
    vfs: s3
    config: {bucket: reports}
    read: bounded
    ttl: 60          # outside changes show within a minute
  /feed:
    vfs: s3
    config: {bucket: feed}
    read: fresh      # every command checks what it reads
```

</CodeGroup>

In YAML a mount's `ttl:` takes `read:` beside it. [The read policy](/home/yaml#the-read-policy) has the full rules.

## Performance And Consistency

### Performance

- **`fresh` costs grow with what a command touches.** A `grep -r` over 500 cached files sends about 500 checks, and a walk can list every cached folder it visits again. On rate-limited APIs (Google Drive, OneDrive, SharePoint, Box), prefer `bounded` with a short `ttl:` for bulk work.
- **`bounded` serves cached files and listings without checking until they expire.** Anything not cached costs a backend request. A cached file whose folder has not been listed costs one metadata lookup per command.

### Listings Under `fresh`

A cached listing is reused across commands only when the backend can show the folder has not changed; otherwise it is listed again, once per command:

| Backends | What a command pays per cached listing |
| --- | --- |
| GitHub, Hugging Face models, datasets and spaces | One small check for the whole mount; none for a GitHub mount pinned to a full commit sha. A new commit lists the mount again. |
| Disk | One local stat per folder. |
| Every other backend | One listing operation per cached folder; it may send several requests. |

Disk detects a changed folder by its change time, which moves reliably only on a local POSIX filesystem. For an NFS, SMB, rclone, s3fs or mirage FUSE root, set `folder_versions: false` in the mount's `config:` so the mount lists folders again instead:

```yaml
mounts:
  /share:
    vfs: disk
    config: {root: /mnt/nfs/share, folder_versions: false}
    read: fresh
```

### Consistency

- **`fresh` checks once per command, not continuously.** A change made while a long command runs shows up in the next command that reads it.
- **A check that cannot be made means a fresh download.** If the backend reports no version or the check request fails, mirage does not serve bytes it could not verify: it drops the cached copy and downloads the file, as on a first read.
- **Commands mirage cannot see into clear the cache** (a host program, a remote sandbox line, a CLI write), so later reads fetch from the backends again ([details](#when-the-cache-is-cleared)).

### Compatibility

A backend that cannot check what it caches refuses `fresh` when the mount loads, rather than quietly behaving as `bounded`. [The VFS matrix](/home/vfs-matrix) lists which backends accept it.

## Writes

### Write Caching

A write of a whole file keeps what it wrote in the file cache, so the next read needs no download, even under `fresh`, whoever made it: a command such as `tee`, `sed -i` or `sort -o`, a `>` redirect, `ws.vfs`, or a runtime writing a file. A write of part of a file (`>>`, a write at an offset, `truncate`) and a `cp` within one mount keep nothing, so the next read downloads the file.

On OneDrive, SharePoint and Hugging Face buckets the upload reply carries no version, so under `fresh` the next read after a write downloads the file.

### Conditional Writes

Under [`write: conditional`](/home/yaml#the-write-policy), mirage refuses a write when the file changed on the backend since the agent read it. It compares against the version it holds in the file cache, so:

- **No version, no protection.** If the cache has dropped the file's version (eviction, a [cache clear](#when-the-cache-is-cleared), or a version on Redis that no shell line has seen for a day), the next write to that file goes out unchecked. On RAM, a larger `limit` keeps more files protected.
- **It guards against writers outside this cache, not against sessions that share it.** Versions belong to the cache, not to the session that read the file, so one session's read lets another session's write through, even if that session never read the file. Conditional writes catch changes made by other tools or by workspaces with their own cache; they are not a lock or a transaction between sessions.

[Known limits](/home/yaml#known-limits) has the full rules.

## Stores

Each layer is a pluggable store with two built-ins:

- **RAM** (default): in-process, zero setup, 512 MB file cache. Best for single-process apps and notebooks.
- **Redis**: shared across workers, processes, and machines. Best for serverless and multi-replica services; see [sharing a Redis cache](#sharing-a-redis-cache).

<CodeGroup>

```python Python
from mirage import Workspace
from mirage.cache.file.config import RedisCacheConfig
from mirage.cache.index.config import RedisIndexConfig
from mirage.vfs.s3 import S3Config, S3VFS

ws = Workspace(
    {"/s3": S3VFS(S3Config(bucket="my-bucket"))},
    cache=RedisCacheConfig(url="redis://localhost:6379/0", limit="8GB"),
    index=RedisIndexConfig(url="redis://localhost:6379/0", ttl=600),
)
```

```typescript TypeScript
import { S3VFS, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace(
  { '/s3': new S3VFS({ bucket: 'my-bucket' }) },
  {
    cache: { type: 'redis', url: 'redis://localhost:6379/0', limit: '8GB' },
    index: { type: 'redis', url: 'redis://localhost:6379/0', ttl: 600 },
  },
)
```

```yaml YAML
cache: {type: redis, url: redis://localhost:6379/0, limit: 8GB}
index: {type: redis, url: redis://localhost:6379/0, ttl: 600}
```

</CodeGroup>

| Block | Key | Default | Meaning |
| --- | --- | --- | --- |
| `cache` | `type` | required in YAML; `ram` in code | `ram` or `redis`. |
| `cache` | `limit` | `512MB` | Largest file kept; on RAM, also the cap on the total kept. |
| `cache` | `max_drain_bytes` | the `limit` | Largest streamed read kept, in bytes. |
| `index` | `type` | required in YAML; `ram` in code | `ram` or `redis`. |
| `index` | `ttl` | `600` | Seconds a listing is kept, capped by each mount's `ttl:`. |
| both, Redis | `url` | `redis://localhost:6379/0` | The Redis server. |
| both, Redis | `key_prefix` | `mirage:cache:` / `mirage:index:` | Prefix for every key the store writes. |

A RAM cache drops least-recently-used bytes once the total passes `limit`; a Redis cache is bounded by the server's `maxmemory` ([below](#sharing-a-redis-cache)). A streamed read larger than `max_drain_bytes` (at most the `limit`) is served but not kept. Unknown fields are refused rather than ignored. In YAML an `index:` `ttl` must be a number, so a quoted one (including one filled in from `${VAR}`) is refused. The file cache has no per-mount block. Raising `limit` keeps more bytes warm at the cost of memory.

### Index TTL

A listing is kept for the first of these that applies:

1. the mount's own `index:` `ttl`;
2. a configured workspace `index:` `ttl` (600 seconds if the block sets no `ttl`);
3. with no `index:` configured at all, the backend's own default ([backend listing defaults](#backend-listing-defaults)).

It is never kept longer than the mount's `ttl:`. A mount's own `index:` replaces the workspace block whole; set it in YAML ([per-mount index](/home/yaml#per-mount-index)) or in code with `Mount(vfs, index=...)`, `ws.add_mount(..., index=...)` or `new Mount(vfs, { index })`. A longer `ttl` means fewer listing requests and staler listings.

## Advanced

### When The Cache Is Cleared

Some commands can change data without mirage knowing which files changed. To avoid serving stale data, mirage clears cached file contents and listings after them, so the next reads fetch from the backends again:

- **Host programs and remote runtimes.** Running a host program, or a line in a remote runtime such as an E2B sandbox, clears cached data across all mounts.
- **CLI writes.** A write through one of mirage's [account CLIs](/home/setup/clis) (`gh`, `gws`, `slack`, ...) or a script CLI you register clears cached data across all mounts too.
- **Mount changes.** Unmounting or remounting a prefix clears that prefix's cached data.

When several workspaces share a Redis cache, these clears can also drop data the other workspaces use; see [sharing a Redis cache](#sharing-a-redis-cache).

### Reads Outside A Command

Under `read: fresh`, each command on a line (`a; b`, every stage of a pipe) checks for itself, and reads that belong to no command (FUSE, `ws.vfs`, an agent's file tools) check a cached file on every read but reuse a listing for up to a second, so a new or deleted file can stay hidden from them that long.

### Caveats

Files mirage renders on read (Google Docs, Sheets and Slides, or a [renderer](/python/vfs/new#renderers-and-the-file-cache) a VFS declares) are not served from the file cache when read through FUSE, `ws.vfs`, a `< file` redirect or a cross-mount `cp`, `sed` or `diff`. Each such read renders again, which costs backend requests. `cat`, `grep`, `head` and `wc` keep their cache hits.

### Backend Listing Defaults

With no `index:` configured, a listing is kept for the backend's own default, still capped by the mount's `ttl:`:

| Default | Backends |
| --- | --- |
| 600 seconds | most backends |
| 300 seconds | Google Calendar |
| 60 seconds | Disk, SSH |
| not cached | RAM, Redis, Postgres, MongoDB, LanceDB |
| a day, applied only on a mount whose `ttl:` is raised to match | Google Drive, Docs, Sheets, Slides, Gmail, GitHub, Dropbox, Box, OneDrive, SharePoint, email, Hugging Face repos |

Configuring a workspace `index:` changes every mount's listing lifetime: Disk and SSH move from 60 seconds to the index's `ttl`, and with a nonzero `ttl` RAM, Redis, Postgres, MongoDB and LanceDB start caching listings. A second mount of the same VFS instance shares the first mount's index.

### Sharing A Redis Cache

These rules matter once more than one worker, process or workspace points at the same Redis.

- **Workspaces that share a `url` and `key_prefix` share one cache**, keyed by virtual path, which is what replicas of one workspace want. Give a different `key_prefix` to workspaces that mount different backends at the same prefix. Python and TypeScript workers can share one Redis.
- **A clear on one workspace reaches the others** ([above](#when-the-cache-is-cleared)). A host program or remote runtime line empties the whole `key_prefix`; a CLI write drops the cached bytes under this workspace's mount prefixes and expires every listing. Every affected replica then fetches again, so give workspaces that often run commands in a remote sandbox their own `key_prefix`.
- **Set `maxmemory` with `allkeys-lru`.** mirage evicts nothing from Redis itself. Listings keep their expiry inside the entry rather than as a Redis key expiry, so a `volatile-*` policy never frees them.
- **Keep `ttl:` the same across workspaces that share the cache.** Entries keep the expiry they were written with, so lowering `ttl:` on one worker does not shorten what others stored.
- **Upgrade every worker together.** The Redis layout is not versioned, so flush both key prefixes before upgrading (delete every key under each `key_prefix`) and expect a cold cache afterwards.

### Relationship To Snapshots

A [snapshot](/home/snapshot) carries the RAM file cache: `ws.snapshot()` writes the cached bytes for every touched path into the tar, and `Workspace.load()` restores them so a replayed run reads from local state. A Redis file cache is not captured. Restored bytes keep their original expiry, so bytes cached longer ago than the mount's `ttl:` are downloaded again. The index cache is not snapshotted; it rebuilds lazily after load ([how snapshots compose with caching](/home/snapshot#how-it-composes-with-caching)).
