A VFS that defines these methods lets `head`, `tail` and `wc` answer without
reading the whole file: a database fetches the first rows with a `LIMIT`,
counts them with `COUNT(*)`, or hands over new rows as they land. The answer
stands in for the file, so the output is the same as a full read.

## Interface

<CodeGroup>

```python Python
from collections.abc import AsyncIterator

from mirage import NULL_INDEX, BaseVFS, PathSpec


class MyVFS(BaseVFS):
    async def first_lines(
        self, path: PathSpec, n: int, index=NULL_INDEX
    ) -> bytes | None: ...

    async def last_lines(
        self, path: PathSpec, n: int, index=NULL_INDEX
    ) -> bytes | None: ...

    async def line_count(
        self, path: PathSpec, index=NULL_INDEX
    ) -> int | None: ...

    async def follow(
        self, path: PathSpec, n: int, index=NULL_INDEX
    ) -> AsyncIterator[bytes] | None: ...
```

```ts TypeScript
import { BaseVFS, type PathSpec } from '@struktoai/mirage-core'

class MyVFS extends BaseVFS {
  override firstLines(path: PathSpec, n: number): Promise<Uint8Array | null> { /* ... */ }

  override lastLines(path: PathSpec, n: number): Promise<Uint8Array | null> { /* ... */ }

  override lineCount(path: PathSpec): Promise<number | null> { /* ... */ }

  override follow(path: PathSpec, n: number): Promise<AsyncIterable<Uint8Array> | null> { /* ... */ }
}
```

</CodeGroup>

| Method | Answer | Otherwise |
| --- | --- | --- |
| `first_lines` | the first `n` lines a read gives, each with its newline; the whole file when it has fewer | `None`: the file is read |
| `last_lines` | the last `n` lines a read gives, each with its newline; the whole file when it has fewer | `None`: the file is read |
| `line_count` | how many newlines a read gives | `None`: the file is read |
| `follow` | a stream of the last `n` lines, then each line added to the file, ending only when the caller closes it | `None`: `tail` reads the file and polls it every `-s` seconds |

An answer must match the file byte for byte: a missing or extra line is a
wrong answer. Raise the error a read of the file would raise, such as
`FileNotFoundError` for a missing file, or `EFBIG` (`File too large`) when the
answer passes a ceiling on one read. A file the read cache holds is read from
the cache instead, so these methods are not asked for it, except `follow`.

These are dispatcher calls, like `read`: hides, path rules, the mount's mode
and policies apply to them as they do to a read of the same file, and so do
output limits.

## Commands and flags

| Method | Command | Used when |
| --- | --- | --- |
| `first_lines` | `head` | `-n N` with `N` above 0, or no count (10); not with `-c`, `-z` or `-n -N` |
| `last_lines` | `tail` | `-n N` with `N` above 0, or no count (10); not with `-c` or `-n +N` |
| `line_count` | `wc` | `-l` alone; not with `-w`, `-c`, `-m` or `-L` |
| `follow` | `tail -f` | one file that opened, followed by descriptor, with `-n N` or no count (10); not with `-F`, `--follow=name`, `-c` or `-n +N` |

Standard input is always read. `tail -f` prints all `follow` streams, so the
last lines and the ones that follow meet at one point: a line added while the
last ones are read prints once. When `follow` answers `None`, the first print
reads the whole file, since the polls go on from where it ends. When the
stream `follow` returned ends, `tail` prints `tail: no files remaining` and
exits 1. Closing the stream must end a wait for the next line, so a stopped
`tail -f` releases the mount.

`wc` rows counted by `line_count` have no byte size, so the columns are as
wide as the widest printed number, where a read pads to the digits of the
files' total size.

## Backends

| Backend | `first_lines` | `last_lines` | `line_count` | `follow` | Ceiling |
| --- | --- | --- | --- | --- | --- |
| PostgreSQL | `LIMIT` on `rows.jsonl` | `COUNT(*)`, then `LIMIT` and `OFFSET` | `COUNT(*)` | | `max_read_rows` |
| MongoDB | | sort by `_id` descending with a limit, on `documents.jsonl` | `count_documents` | the last documents at one snapshot, then a change stream of the inserts after it, on a collection's `documents.jsonl` | `max_doc_limit` |
| Airtable | `maxRecords` on `records.jsonl` and view files | | | | `max_read_records` |

A count past the ceiling that the table fills is `File too large`, the same
as a whole read of that table: `head -n 20000` on a 50,000-row PostgreSQL
table with the default `max_read_rows` of 10,000 prints
`head: error reading '<path>': File too large` and exits 1. `wc -l` counts
past the ceiling. Every other file on these mounts (`schema.json`,
`database.json`, a view's schema) is read as usual. MongoDB's `head` reads the
collection as a stream and stops after the count, so it needs no
`first_lines`.
