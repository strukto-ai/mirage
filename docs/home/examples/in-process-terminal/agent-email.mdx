A customer writes to support about a problem the team has already dealt
with. The answer is in Slack: an engineer posted what happened, and the
report. An agent reads the email, finds the note, and writes the reply with
the report attached. A person reads the draft and decides whether it goes
out.

The agent runs in an
[in-process terminal](/home/examples/in-process-terminal) inside one FastAPI
or Express server:

- **Mail:** [`himalaya`](/python/cli/himalaya) reads the support inbox and
  saves replies to `Drafts` over IMAP, and sends over SMTP.
- **Files:** `/slack` mounts [Slack](/python/vfs/slack) read-only, files
  shared in a channel included, so the agent attaches the report straight
  from Slack. `/workspace`, in [memory](/home/setup/ram), holds the reply's
  text.
- **Policy:** the agent may draft as much as it likes. A
  [policy](/home/policy/overview) on the server refuses a reply to anyone
  but the sender, or with an attachment that is not from Slack, and holds
  every send until a person approves it.

The commands below are what the agent runs in its terminal. An engineer
posted this in `#incidents`:

```text
Incident 2026-11-16: calendar sync for Northwind Health failed 06:10–07:40 UTC.
Cause: an expired Google token on our side; no data was lost.
Fix: token rotated, sync re-run for the window, all 214 events are back.
Report attached for customers who ask.                    📎 incident-report.pdf
```

## Before you start

You need a Slack bot and a mailbox for support.

**Slack.** A bot with `channels:read`, `channels:history` and `files:read`,
plus `groups:read` and `groups:history` for a private channel. See
[Slack](/home/setup/slack). Invite it to `#incidents`, and post the note
above with a PDF as a message in the channel, not as a reply in a thread:
the mount shows a channel's messages, not its threads.

**Mail.** Any IMAP and SMTP account works; see [Email](/home/setup/email).
To try the example without one, run [GreenMail](https://greenmail-mail-test.github.io/greenmail/),
a mail server for tests, in Docker. It takes any password and keeps every
message on your machine, so nothing reaches a real inbox:

```bash
docker run -d --name greenmail -p 3025:3025 -p 3143:3143 greenmail/standalone:2.1.15
```

A real mailbox comes with `Drafts` and `Sent` folders. GreenMail starts with
none, so create them:

```bash
curl -s imap://localhost:3143 -u support@acme.example:any -X 'CREATE Drafts'
curl -s imap://localhost:3143 -u support@acme.example:any -X 'CREATE Sent'
```

Then send the customer's email to the support address:

```bash
curl -s smtp://localhost:3025 --mail-from priya@northwind.example --mail-rcpt support@acme.example -T - <<EOF
From: Priya Shah <priya@northwind.example>
To: support@acme.example
Date: $(date -u -R)
Subject: Our calendar sync failed this morning

Hi, appointments were missing from our calendars this morning.
What happened, and did we lose any data?

Priya
EOF
```

The server needs two keys: `SLACK_BOT_TOKEN`, and `MAIL_PASSWORD`, which
can be anything for GreenMail.

## Workspace

`workspace.yaml` mounts Slack read-only, keeps `/workspace` in memory and
installs `himalaya` with the support account. With your own mailbox, set its
hosts and username, and drop the two ports and `use_ssl`.

The `support` profile is what every terminal gets. Its allow list leaves
the agent three mail commands, to list, read and reply: no `compose`,
`forward`, `delete` or raw `send`. Its policy, `guard.py`, judges each reply
before it runs:

```yaml workspace.yaml
mounts:
  /slack:
    vfs: slack
    mode: read
    config:
      token: {from: env, key: SLACK_BOT_TOKEN}
  /workspace:
    vfs: ram
    mode: write

clis:
  himalaya:
    cli: himalaya
    machine: in_process
    config:
      imap_host: localhost
      imap_port: 3143
      smtp_host: localhost
      smtp_port: 3025
      use_ssl: false
      username: support@acme.example
      password: {from: env, key: MAIL_PASSWORD}

profiles:
  support:
    commands:
      allow: [cd, pwd, echo, cat, ls, grep, jq, head,
              himalaya envelope list, himalaya message read, himalaya message reply]
    policy:
      pre_command:
        - {script: ./guard.py, runtime: monty}

profile: support
```

`guard.py` sees each command after the shell has expanded it, so a variable
or a glob cannot hide a recipient or a path:

- A reply goes to whoever wrote in, and no one else: `--to`, `--cc` and
  `--bcc` are refused.
- An attachment must be a file shared in Slack, under `/slack/`.
- `--send` asks a person. Without it, a reply is only saved to `Drafts`.
- A flag must be written apart from its value, as `--attach FILE`, not
  `--attach=FILE` or `-tADDR`, so the rules above see every value.

```python guard.py
def pre_command(ctx):
    words = ctx["words"]
    texts = [w["text"] for w in words]
    if texts[:3] != ["himalaya", "message", "reply"]:
        return None
    for w in words:
        t = w["text"]
        if w["kind"] == "option" and ("=" in t or (not t.startswith("--") and len(t) > 2)):
            return {"kind": "deny", "reason": "write each flag and its value apart"}
        if t in ("-t", "--to", "--cc", "--bcc"):
            return {"kind": "deny", "reason": "a reply goes only to the sender"}
        if w["option"] == "--attach" and not (w["path"] or "").startswith("/slack/"):
            return {"kind": "deny", "reason": "attach only files shared in Slack"}
    if "--send" in texts:
        return {"kind": "ask", "reason": "a person approves every send"}
    return None
```

## Server

This is the server from the
[Overview](/home/examples/in-process-terminal#simple-server), built from
`workspace.yaml`, with two changes:

- `/sessions/{id}/run` also returns the policy's `decision`, so the agent
  knows why a command was refused, and the ask's ID.
- `GET /asks` lists the sends waiting for a person, and `POST /asks/{id}`
  approves or refuses one.

<Tabs>
  <Tab title="FastAPI" icon="/images/python-logo.svg">
    ```python app.py
    from contextlib import asynccontextmanager

    from fastapi import FastAPI
    from pydantic import BaseModel

    from mirage import Outcome, Workspace
    from mirage.config import load_config, resolve_secrets

    ws: Workspace


    @asynccontextmanager
    async def lifespan(app: FastAPI):
        global ws
        config = await resolve_secrets(load_config("workspace.yaml"))
        ws = Workspace(**config.to_workspace_kwargs())
        yield
        await ws.close()


    app = FastAPI(lifespan=lifespan)


    class Run(BaseModel):
        command: str


    class Answer(BaseModel):
        allow: bool


    @app.post("/sessions/{session_id}")
    async def create(session_id: str) -> None:
        ws.create_session(session_id)


    @app.post("/sessions/{session_id}/run")
    async def run(session_id: str, body: Run) -> dict:
        r = await ws.shell(body.command, session_id=session_id)
        d = r.decision
        return {
            "stdout": await r.stdout_str(),
            "stderr": await r.stderr_str(),
            "exit_code": r.exit_code,
            "decision": d and {"kind": d.kind, "reason": d.reason, "ask_id": d.ask_id},
        }


    @app.get("/asks")
    async def asks() -> dict:
        return {"items": [
            {"id": a.id, "session_id": a.session_id, "command": " ".join([a.command, *a.argv]), "reason": a.reason}
            for a in ws.decisions.pending()
        ]}


    @app.post("/asks/{ask_id}", status_code=204)
    async def answer(ask_id: str, body: Answer) -> None:
        await ws.decisions.answer(ask_id, Outcome.ALLOW if body.allow else Outcome.DENY)
    ```

    ```bash
    export SLACK_BOT_TOKEN=xoxb-...
    export MAIL_PASSWORD=any
    uvicorn app:app --port 3000
    ```
  </Tab>
  <Tab title="Express" icon="/images/typescript-logo.svg">
    ```typescript app.mjs
    import express from 'express'
    import { Outcome, Workspace, configToWorkspaceArgs, loadWorkspaceConfigFile } from '@struktoai/mirage-node'

    const { mounts, options } = await configToWorkspaceArgs(loadWorkspaceConfigFile('workspace.yaml'))
    const ws = new Workspace(mounts, options)

    const app = express()
    app.use(express.json())

    app.post('/sessions/:id', (req, res) => {
      ws.createSession(req.params.id)
      res.sendStatus(201)
    })

    app.post('/sessions/:id/run', async (req, res) => {
      const r = await ws.shell(req.body.command, { sessionId: req.params.id })
      const d = r.decision
      res.json({
        stdout: r.stdoutText,
        stderr: r.stderrText,
        exitCode: r.exitCode,
        decision: d && { kind: d.kind, reason: d.reason, ask_id: d.askId },
      })
    })

    app.get('/asks', (req, res) => {
      res.json({
        items: ws.decisions.pending().map((a) => ({
          id: a.id, session_id: a.sessionId, command: [a.command, ...a.argv].join(' '), reason: a.reason,
        })),
      })
    })

    app.post('/asks/:id', async (req, res) => {
      await ws.decisions.answer(req.params.id, req.body.allow ? Outcome.ALLOW : Outcome.DENY)
      res.sendStatus(204)
    })

    app.listen(3000, '127.0.0.1')
    ```

## Usage

Create a terminal, and define `run`, which sends commands to it and prints
what they print, then the policy's answer when there is one. It needs
[`jq`](https://jqlang.org):

```bash
curl -X POST localhost:3000/sessions/a

run() {
  jq -Rs '{command: .}' |
    curl -s localhost:3000/sessions/a/run -H 'content-type: application/json' -d @- |
    jq -j '.stdout, .stderr, (.decision // empty | "[\(.kind)] \(.reason)\n")'
}
```

The commands between `SH` and `SH` in the blocks below run in the terminal
on the server, not in the shell that calls `run`. Variables the agent sets,
such as `$report`, stay set in the terminal for the next block.


Each step below starts with what the agent knows at that point and why it
runs what it runs, then the commands, what they print, and what the agent
learned.

## 1. Read the email

The agent starts with only the support inbox. It lists what is waiting,
then opens the new message to find out who wrote and what they need:

- `himalaya envelope list` shows each message's ID, sender, subject and
  date. `*` marks one nobody has read.
- `himalaya message read 1` prints message 1 in full.

```bash
run <<'SH'
himalaya envelope list
himalaya message read 1
SH
```

```text
┌────┬───────┬───────────────────────────────────────┬────────────┬────────────────────────┬───────┐
│ ID ┆ FLAGS ┆ SUBJECT                               ┆ FROM       ┆ DATE                   ┆  SIZE │
╞════╪═══════╪═══════════════════════════════════════╪════════════╪════════════════════════╪═══════╡
│ 1  ┆ *     ┆ Our calendar sync failed this morning ┆ Priya Shah ┆ 2026-11-16 09:27+00:00 ┆ 396 B │
└────┴───────┴───────────────────────────────────────┴────────────┴────────────────────────┴───────┘
Date: Mon, 16 Nov 2026 09:27:55 +0000
From: Priya Shah <priya@northwind.example>
To: support@acme.example
Subject: Our calendar sync failed this morning

[1] text/plain (111 B)

Hi, appointments were missing from our calendars this morning.
What happened, and did we lose any data?

Priya
```

Priya Shah, at Northwind Health, asks two things: what happened to this
morning's sync, and whether any data was lost. The email does not say why,
so the agent goes to find out.

## 2. Find what happened

The team posts incidents in `#incidents`, so the answer should be there.
A Slack channel is a folder named after the channel and its ID, with a
folder for each day: the day's messages in `chat.jsonl` and the files
shared that day in `files/`. The email is dated 16 November and says "this
morning", so the agent looks in that day's folder:

- `grep "calendar sync"` searches for the customer's own words, and `jq -r
  .text` prints only the text of each matching message.
- The note it finds says a report is attached, so `ls` finds the PDF in
  the same day's `files/`. The agent keeps its path in `$report` to attach
  later, with no download.

```bash
run <<'SH'
grep -h "calendar sync" /slack/channels/incidents__*/2026-11-16/chat.jsonl | jq -r .text
report=$(ls -d /slack/channels/incidents__*/2026-11-16/files/incident-report__*)
echo "$report"
SH
```

```text
Incident 2026-11-16: calendar sync for Northwind Health failed 06:10–07:40 UTC.
Cause: an expired Google token on our side; no data was lost.
Fix: token rotated, sync re-run for the window, all 214 events are back.
Report attached for customers who ask.
/slack/channels/incidents__C0CJ1LE89NV/2026-11-16/files/incident-report__F0CHLDGQ0NB.pdf
```

The note answers both questions: an expired token stopped the sync from
06:10 to 07:40 UTC, and no data was lost. The agent has the report too.

## 3. Draft the reply

The agent has the answer, but sending is not its decision, so it writes
the reply as a draft:

- It writes the body to `/workspace/reply.txt`, in plain words for the
  customer, so the draft and a later send use the same text.
- `himalaya message reply 1` answers Priya's message, which sets the
  recipient, the `Re:` subject and the thread headers. `--attach "$report"`
  attaches the PDF straight from Slack.
- `--save Drafts`, without `--send`, only stores the message in `Drafts`
  over IMAP. Nothing leaves the mailbox, so `guard.py` lets it through.
- `himalaya envelope list -m Drafts` checks that the draft is there.

```bash
run <<'SH'
cat > /workspace/reply.txt <<'EOF'
Hi Priya,

This morning from 06:10 to 07:40 UTC, calendar sync for Northwind Health
stopped because a Google token on our side had expired. No data was lost.
We rotated the token and re-ran the sync for that window, and all 214
events are back.

The incident report is attached.

Best,
Acme Support
EOF
himalaya message reply 1 --body-file /workspace/reply.txt \
  --attach "$report" --save Drafts
himalaya envelope list -m Drafts
SH
```

```text
Message successfully saved
┌────┬───────┬───────────────────────────────────────────┬──────────────────────┬────────────────────────┬──────────┐
│ ID ┆ FLAGS ┆ SUBJECT                                   ┆ FROM                 ┆ DATE                   ┆     SIZE │
╞════╪═══════╪═══════════════════════════════════════════╪══════════════════════╪════════════════════════╪══════════╡
│ 1  ┆       ┆ Re: Our calendar sync failed this morning ┆ support@acme.example ┆ 2026-11-16 09:42+00:00 ┆ 2.47 KiB │
└────┴───────┴───────────────────────────────────────────┴──────────────────────┴────────────────────────┴──────────┘
```

The reply, with the report attached, waits in `Drafts` for a person to read.

## 4. What the policy refuses

An agent can get things wrong: copy someone it should not, attach the wrong
file, or delete mail. Each of these is refused before it runs, even as a
draft. The agent reads what a real terminal prints for a refused command,
and `run` prints the reason the server returned.

Copy someone else in:

```bash
run <<'SH'
himalaya message reply 1 --save Drafts \
  --cc ceo@other.example
SH
```

```text
himalaya: Permission denied
[deny] a reply goes only to the sender
```

Attach a file that is not from Slack:

```bash
run <<'SH'
himalaya message reply 1 --save Drafts \
  --attach /workspace/reply.txt
SH
```

```text
himalaya: Permission denied
[deny] attach only files shared in Slack
```

Write the flag and its value as one word, which `guard.py` could not check:

```bash
run <<'SH'
himalaya message reply 1 --save Drafts \
  --attach=/workspace/reply.txt
SH
```

```text
himalaya: Permission denied
[deny] write each flag and its value apart
```

Delete the email:

```bash
run <<'SH'
himalaya message delete 1
SH
```

```text
himalaya: Permission denied
[deny] himalaya message delete is not allowed
```

The first three are `guard.py`. The last is the profile's allow list,
which refuses the command before `guard.py` is asked. `Drafts` still holds
only the reply from step 3.

## 5. Ask to send

The draft is ready, so the agent tries to send it: the same command, with
`--send` in place of `--save Drafts`. `guard.py` answers with an ask, so the
command does not run, and the server records it for a person:

```bash
run <<'SH'
himalaya message reply 1 --body-file /workspace/reply.txt \
  --attach "$report" --send
SH
```

```text
himalaya: Permission denied
[pending] a person approves every send
```

## 6. A person approves

A person reads the draft in `Drafts`, then lists the asks and approves this
one. These two requests go to the server from outside the agent's terminal:

```bash
curl -s localhost:3000/asks
```

```json
{
  "items": [
    {
      "id": "f245dd41f481",
      "session_id": "a",
      "command": "himalaya message reply 1 --body-file /workspace/reply.txt --attach /slack/channels/incidents__C0CJ1LE89NV/2026-11-16/files/incident-report__F0CHLDGQ0NB.pdf --send",
      "reason": "a person approves every send"
    }
  ]
}
```

The ask shows the command after expansion, so the person sees the exact
file that will be attached, not `$report`.

```bash
curl -X POST localhost:3000/asks/f245dd41f481 -H 'content-type: application/json' -d '{"allow": true}'
```

## 7. Send

The agent runs the same command again. The approval covers it, so this
time it runs: `himalaya` sends over SMTP and keeps a copy in `Sent`:

```bash
run <<'SH'
himalaya message reply 1 --body-file /workspace/reply.txt \
  --attach "$report" --send
SH
```

```text
Message successfully saved and sent
```

The approval covered that one command. The next send asks again, and a
refused ask leaves the draft where it is.

For the commands and flags `himalaya` supports, see
[himalaya](/python/cli/himalaya). For more on asks, see
[Policies](/home/policy/policies#asks) and [Scripts](/home/policy/scripts).
