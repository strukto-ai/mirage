An agent triages a security or on-call team's alerts, most of them noise.
For each one it reads the alert, looks up what else happened around it,
decides whether to close it, watch it or escalate it, and writes down why. A
cron job can start it every few minutes for the new alerts.

A job this small needs no VM or sandbox, so each alert gets a
[lightweight terminal](/home/examples/lightweight-terminal) of its own: a
session with its own working directory, environment and history. One
FastAPI or Express server holds all of them in one process:

- **Agents:** forty triage agents, with one terminal and one alert each,
  then a lead agent that reads their verdicts and writes the hand-over. The
  agents send each other nothing. They work together through the files they
  share.
- **Files that are kept:** `/cases`, a folder in an
  [S3 bucket](/home/setup/s3): the alerts, the verdicts and the hand-over.
  They are still there after the server restarts.
- **Scratch files:** `/work`, mounted in [memory](/home/setup/ram): the
  day's log and the agents' scripts. They are gone when the server stops.
- **Python:** `python3`, in-process on [Monty](/home/setup/runtime/monty).
- **Shell:** `jq`, `grep`, `awk` and `bash` do the rest. No CLI is needed.

The commands below are what the agents run in their terminals. They triage
40 alerts, each a burst of failed logins from one address. The data is
generated by the page, so you can run every block.

## Server

This is the [Overview](/home/examples/lightweight-terminal#server)'s server
with a second mount. `/cases` is the folder `alert-triage/` of a bucket, and
every terminal on the server can read and write it:

<Tabs>
  <Tab title="FastAPI" icon="/images/python-logo.svg">
    ```python app.py
    import os
    from contextlib import asynccontextmanager

    from fastapi import FastAPI
    from pydantic import BaseModel

    from mirage import RAMVFS, MountMode, Workspace
    from mirage.runtime.python.monty import MontyRuntime
    from mirage.vfs.s3 import S3Config, S3VFS

    cases = S3VFS(
        S3Config(
            bucket=os.environ["CASES_BUCKET"],
            region=os.environ["AWS_REGION"],
            key_prefix="alert-triage",
        )
    )
    ws = Workspace(
        {"/work": (RAMVFS(), MountMode.EXEC), "/cases": (cases, MountMode.WRITE)},
        runtimes=[MontyRuntime(captures=["python", "python3"])],
    )


    @asynccontextmanager
    async def lifespan(app: FastAPI):
        yield
        await ws.close()


    app = FastAPI(lifespan=lifespan)


    class Run(BaseModel):
        command: str


    @app.post("/sessions/{session_id}")
    async def create(session_id: str) -> None:
        ws.create_session(session_id)


    @app.post("/sessions/{session_id}/run")
    async def run(session_id: str, body: Run) -> dict:
        r = await ws.shell(body.command, session_id=session_id)
        return {"stdout": await r.stdout_str(), "stderr": await r.stderr_str(), "exit_code": r.exit_code}
    ```

    ```bash
    CASES_BUCKET=my-bucket AWS_REGION=us-east-1 uvicorn app:app --port 3000
    ```
  </Tab>
  <Tab title="Express" icon="/images/typescript-logo.svg">
    ```typescript app.mjs
    import express from 'express'
    import { MontyRuntime, MountMode, RAMVFS, S3VFS, Workspace } from '@struktoai/mirage-node'

    const cases = new S3VFS({
      bucket: process.env.CASES_BUCKET,
      region: process.env.AWS_REGION,
      keyPrefix: 'alert-triage',
    })
    const ws = new Workspace(
      { '/work': [new RAMVFS(), MountMode.EXEC], '/cases': [cases, MountMode.WRITE] },
      { runtimes: [new MontyRuntime({ captures: ['python', 'python3'] })] },
    )
    const app = express()
    app.use(express.json())

    app.post('/sessions/:id', (req, res) => {
      ws.createSession(req.params.id)
      res.sendStatus(201)
    })

    app.post('/sessions/:id/run', async (req, res) => {
      const r = await ws.shell(req.body.command, { sessionId: req.params.id })
      res.json({ stdout: r.stdoutText, stderr: r.stderrText, exitCode: r.exitCode })
    })

    app.listen(3000, '127.0.0.1')
    ```

    ```bash
    CASES_BUCKET=my-bucket AWS_REGION=us-east-1 node app.mjs
    ```

The mount finds the bucket's credentials where the AWS tools do: in
`AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, or in a profile. Other
object stores have a mount of their own to use in its place, such as
[Cloudflare R2](/home/setup/r2) and [MinIO](/home/setup/minio).

With no bucket at hand, mount a [folder on disk](/home/setup/disk) at
`/cases` instead. The rest of the page runs the same:

from mirage.vfs.disk import DiskVFS

```

import { DiskVFS } from '@struktoai/mirage-node'

const cases = new DiskVFS({ root: 'cases' })
```

## Usage

The Overview's `run` sends commands to one terminal, session `a`. This page
needs a terminal per agent, so `term` takes the session id as its first
argument. It reads commands on standard input, sends them to that terminal and
prints what they print. It needs [`jq`](https://jqlang.org):

```bash
term() {
  jq -Rs '{command: .}' |
    curl -s localhost:3000/sessions/$1/run -H 'content-type: application/json' -d @- |
    jq -j '.stdout, .stderr'
}
```

A session id is created once, with `curl -X POST localhost:3000/sessions/<id>`.
Both servers answer an error if the same id is created again, so to run the
page a second time, start the server again first. The terminals do not
outlast the server; only the files in `/cases` do.

The commands between `SH` and `SH` in the blocks below run in a terminal on the
server, not in the shell that calls `term`. `triage` and the loop in
"All alerts at once" run in your shell, as `term` does.

## Make some alerts

This block stands in for your team's real data. It creates a terminal named
`one` and writes three things:

- `/cases/alerts/`: 40 alerts, one JSON file each, in the bucket. Alert `n`
  reports a burst of failed logins to one user from the address
  `203.0.113.n`.
- `/work/auth.log`: the authentication log for the day, about 30,000 lines,
  in memory. It holds the failed and accepted logins behind the alerts, and
  the ordinary logins of other addresses.
- `/work/known-good.txt`: addresses the team already trusts, such as an
  office or a security scanner.

The first command empties the page's folder in the bucket, so that a second
run of the page starts as the first did. `awk` writes each file's lines from
a formula:

```bash
curl -s -o /dev/null -X POST localhost:3000/sessions/one

term one <<'SH'
rm -rf /cases/alerts /cases/verdicts /cases/handover.md
mkdir -p /cases/alerts /cases/verdicts
seq 1 40 | awk '{
  printf "{\"id\": \"alert-%02d\", \"type\": \"failed-login-burst\", \"user\": \"user%02d@example.com\", \"source\": \"203.0.113.%d\", \"count\": %d, \"time\": \"2026-11-12T%02d:%02d:00Z\"}\n", $1, ($1 * 7) % 13 + 1, $1, 20 + ($1 * 13) % 80, ($1 * 5) % 24, ($1 * 17) % 60 > sprintf("/cases/alerts/alert-%02d.json", $1)
}'
for i in 8 16 24 32 40; do echo 203.0.113.$i; done > /work/known-good.txt
echo 198.51.100.1 >> /work/known-good.txt
awk 'function emit(t, st, u, ip) { printf "2026-11-12 %02d:%02d:%02d sshd %s user%02d@example.com from %s\n", int(t / 3600), int(t % 3600 / 60), t % 60, st, u, ip }
BEGIN {
  for (i = 1; i <= 40; i++) {
    tier = i % 8
    if (tier == 0) f = 800 + (i * 61) % 1500
    else if (tier == 7) f = 250 + (i * 97) % 700
    else if (tier >= 4) f = 60 + (i * 53) % 140
    else f = 3 + (i * 5) % 40
    for (j = 1; j <= f; j++) emit((i * 1009 + j * 211) % 86400, "FAILED", (i + j) % 13 + 1, "203.0.113." i)
    if (tier == 7) for (j = 1; j <= 1 + i % 3; j++) emit(80000 + j * 37, "ACCEPTED", i % 13 + 1, "203.0.113." i)
  }
  for (n = 1; n <= 17000; n++) emit((n * 5081) % 86400, (n % 20 == 0) ? "FAILED" : "ACCEPTED", n % 13 + 1, "198.51.100." (n % 50 + 1))
}' | sort > /work/auth.log
ls /cases/alerts | wc -l
wc -l /work/auth.log
head -n 2 /work/auth.log
SH
```

```text
40
30184 /work/auth.log
2026-11-12 00:00:04 sshd FAILED user03@example.com from 203.0.113.39
2026-11-12 00:00:07 sshd FAILED user12@example.com from 203.0.113.16
```

## One alert

First the agent works through one alert, `alert-07`, in terminal `one`, to
find the routine. It reads the alert with `jq`:

```bash
term one <<'SH'
jq . /cases/alerts/alert-07.json
SH
```

```text
{
  "id": "alert-07",
  "type": "failed-login-burst",
  "user": "user11@example.com",
  "source": "203.0.113.7",
  "count": 31,
  "time": "2026-11-12T11:59:00Z"
}
```

The alert says 31 failures in a short burst. It does not say whether that
address is a nuisance or an attack, so the agent looks at the rest of the
day. `grep -c` counts the matching lines in the log without printing them:
the address's failed logins, and its accepted ones. The `\$` ends the
pattern at the end of the line, so `203.0.113.7` does not also match
`203.0.113.70`. Then `grep -x -F` checks whether the address is on the
known-good list, one whole line against another:

```bash
term one <<'SH'
ip=$(jq -r .source /cases/alerts/alert-07.json)
echo $ip
grep -c "FAILED .* from $ip\$" /work/auth.log
grep -c "ACCEPTED .* from $ip\$" /work/auth.log
grep -c -x -F "$ip" /work/known-good.txt
SH
```

```text
203.0.113.7
929
2
0
```

The address failed 929 times, logged in successfully twice and is not on the
list. A short Python file on [Monty](/home/setup/runtime/monty) turns those
numbers into a decision and writes it to a verdict file with the reason.
The rule in it stands in for the agent's own judgment: known-good addresses
and fewer than 50 failures close the alert, 200 failures or more with at
least one accepted login escalate it, and anything else is watched. The
numbers reach the Python file as environment variables, and the file writes
`/cases/verdicts/alert-07.json` to the bucket:

```bash
term one <<'SH'
cat > /work/rule.py <<'PY'
import json, os

alert_id = os.environ["ALERT"]
alert = json.loads(open("/cases/alerts/" + alert_id + ".json").read())
failures = int(os.environ["FAILURES"])
accepted = int(os.environ["ACCEPTED"])
known_good = os.environ["KNOWN_GOOD"] == "1"

if known_good:
    verdict, reason = "close", "known-good address"
elif failures < 50:
    verdict, reason = "close", f"only {failures} failures in the day"
elif accepted > 0 and failures >= 200:
    verdict, reason = "escalate", f"{failures} failures, accepted logins: {accepted}"
else:
    verdict, reason = "watch", f"{failures} failures, accepted logins: 0"

result = {"id": alert_id, "source": alert["source"], "verdict": verdict, "reason": reason}
open("/cases/verdicts/" + alert_id + ".json", "w").write(json.dumps(result))
print(verdict, "-", reason)
PY
ALERT=alert-07 FAILURES=929 ACCEPTED=2 KNOWN_GOOD=0 python3 /work/rule.py
SH
```

```text
escalate - 929 failures, accepted logins: 2
```

## All alerts at once

The agent saves the same steps as a script, `/work/triage.sh`, that takes the
alert id as its first argument. The script first looks for the alert's
verdict in `/cases` and stops if there is one, so no alert is triaged twice.
`alert-07` got its verdict in the step above:

```bash
term one <<'SH'
cat > /work/triage.sh <<'EOF'
ALERT=$1
if [ -e /cases/verdicts/$ALERT.json ]; then
  echo "skip $ALERT: it has a verdict"
else
  ip=$(jq -r .source /cases/alerts/$ALERT.json)
  failures=$(grep -c "FAILED .* from $ip\$" /work/auth.log)
  accepted=$(grep -c "ACCEPTED .* from $ip\$" /work/auth.log)
  known_good=$(grep -c -x -F "$ip" /work/known-good.txt)
  ALERT=$ALERT FAILURES=$failures ACCEPTED=$accepted KNOWN_GOOD=$known_good python3 /work/rule.py
fi
EOF
bash /work/triage.sh alert-07
bash /work/triage.sh alert-15
SH
```

```text
skip alert-07: it has a verdict
escalate - 305 failures, accepted logins: 1
```

Now for all 40 alerts, with a triage agent for each. `triage` takes an alert
id and uses it as the session id: it creates that agent's terminal, once, and
sends it the one command that runs the script on its alert. The script and
the log are files in the terminals' shared `/work`, so every terminal can use
them. The loop starts all 40 calls in the background with `&` and `wait`
returns when they have all finished. Nothing prints from the loop:

```bash
triage() {
  curl -s -X POST localhost:3000/sessions/$1 > /dev/null
  echo "bash /work/triage.sh $1" | term $1 > /dev/null
}

for n in $(seq -f 'alert-%02g' 1 40); do triage $n & done
wait
```

The server now holds 40 more terminals, one for each triage agent, and runs
their commands on its event loop. The agents for `alert-07` and `alert-15`
found a verdict already there and stopped; the other 38 wrote one. The
agents need no lock, because each one has a different alert and writes only
its own file, `/cases/verdicts/<alert id>.json`. Running the loop a second
time triages nothing: every agent finds its alert's verdict and stops.

## A second agent reads the verdicts

A lead agent gets a terminal of its own, `lead`. It took no part in the
triage: everything it knows comes from the files the forty agents left in
`/cases`. The first command counts the verdict files and the second counts
the verdicts. `jq` writes the escalations with their reasons to
`/cases/handover.md` for whoever is on call. The last command returns to the
log for the five addresses with the most failed logins:

```bash
curl -s -o /dev/null -X POST localhost:3000/sessions/lead

term lead <<'SH'
ls /cases/verdicts | wc -l
cat /cases/verdicts/*.json | jq -r .verdict | sort | uniq -c
jq -r 'select(.verdict == "escalate") | "- " + .id + " " + .source + ": " + .reason' /cases/verdicts/*.json > /cases/handover.md
cat /cases/handover.md
grep FAILED /work/auth.log | awk '{print $NF}' | sort | uniq -c | sort -rn | head -n 5
SH
```

```text
40
     20 close
      5 escalate
     15 watch
- alert-07 203.0.113.7: 929 failures, accepted logins: 2
- alert-15 203.0.113.15: 305 failures, accepted logins: 1
- alert-23 203.0.113.23: 381 failures, accepted logins: 3
- alert-31 203.0.113.31: 457 failures, accepted logins: 2
- alert-39 203.0.113.39: 533 failures, accepted logins: 1
   2264 203.0.113.24
   1776 203.0.113.16
   1740 203.0.113.40
   1288 203.0.113.8
   1252 203.0.113.32
```

The lead agent can report three results:

- Of the 40 alerts, 20 are closed, 15 are on watch and 5 are escalated.
- The escalations are `alert-07`, `alert-15`, `alert-23`, `alert-31` and
  `alert-39`: each address failed hundreds of times and also has an accepted
  login.
- The five addresses with the most failures, 1,252 to 2,264 each, are all on
  the known-good list, so their alerts are closed rather than escalated.

To get there the agents read under 1 KB of output between them. The
authentication log is 2.1 MB, and it stayed in the terminals: `grep -c` and
`sort | uniq -c` ran next to the file and sent back only the counts.

## After a restart

Stop the server and start it again, as a deploy would. The terminals are
gone, and so is everything in memory: `/work` has no log and no scripts. The
bucket is as the agents left it. An on-call agent on the next shift, in a new
terminal, finds the hand-over and all 40 verdicts:

```bash
curl -s -o /dev/null -X POST localhost:3000/sessions/oncall

term oncall <<'SH'
ls /work | wc -l
ls /cases
cat /cases/handover.md
ls /cases/verdicts | wc -l
SH
```

```text
0
alerts
handover.md
verdicts
- alert-07 203.0.113.7: 929 failures, accepted logins: 2
- alert-15 203.0.113.15: 305 failures, accepted logins: 1
- alert-23 203.0.113.23: 381 failures, accepted logins: 3
- alert-31 203.0.113.31: 457 failures, accepted logins: 2
- alert-39 203.0.113.39: 533 failures, accepted logins: 1
40
```

So memory is for what an agent can make again, and the bucket is for what
the next agent needs. An escalation would also be sent on with a CLI that
the server registers, such as `slack` or `linear`, so that a person sees it.
See [CLIs](/home/setup/clis).
