An agent needs somewhere to run commands: Bash, Python, and CLIs such as
`git`. The usual answer is a sandbox, a container or microVM for each agent.
A sandbox reserves memory for every agent, takes time to start and needs a
service to manage it.

Most of what an agent runs does not need a machine. It reads files, calls
services and pipes text from one command to the next. A lightweight terminal
runs that work inside the server you already have. Each terminal is a Mirage
session with its own working directory, environment and history, and
[Monty](/home/setup/runtime/monty) runs Python in-process. One server process
holds many terminals on its event loop.

| | Sandbox per agent | Lightweight terminal |
| --- | --- | --- |
| Commands run in | a container or microVM | your server process |
| Memory per agent | 128 MB to 1 GB reserved ([1](https://modal.com/docs/guide/sandbox-resources), [2](https://developers.cloudflare.com/containers/platform/pricing/), [3](https://docs.e2b.dev/pricing), [4](https://www.daytona.io/docs/en/sandboxes/)) | tens of kilobytes when idle, plus the files it holds |
| Start | boots a container or microVM | adds a session to a running process |
| You operate | a sandbox service | nothing new |
| Runs | any program | Bash, Python on Monty, CLIs, MCP servers |

A command that needs more, such as `numpy` or a GPU, can still go to a machine:
[Runtime Routing](/home/examples/runtime-routing) sends only those commands
there.

## What an agent can run

| | Example | Where it runs |
| --- | --- | --- |
| Bash | `grep -c ERROR app.log`, pipes, redirects, variables, `curl`, `jq` | [Mirage's shell](/home/core/shell) |
| Python | `python3 report.py` | [Monty](/home/setup/runtime/monty), a subset of Python with no network or host access |
| CLIs | `git log --oneline -5` | a [CLI](/home/setup/clis) the server registers, such as `git`, `gh` or `slack` |
| MCP servers | `deepwiki ask-wiki-question '{...}'` | any [MCP server](/python/cli/mcp), installed as a CLI: each of its tools is a subcommand |

**The files they work on live in a virtual filesystem (VFS).** Each source of
files, such as memory, an S3 bucket or Google Drive, is a
[VFS](/home/setup/vfs) mounted under its own path, and a server can mount
several side by side:

| Mount | For | Example |
| --- | --- | --- |
| Memory | scratch files, gone when the server stops | `cat /work/notes.txt` |
| S3, Google Drive, a database | files that must outlast the server | `cp /work/report.csv /s3/reports/` |

This page mounts memory at `/work`, which needs no account.

## Server

One endpoint creates a terminal, another runs a command in it.

<Tabs>
  <Tab title="FastAPI" icon="/images/python-logo.svg">
    ```python app.py
    from contextlib import asynccontextmanager

    from fastapi import FastAPI
    from pydantic import BaseModel

    from mirage import RAMVFS, MountMode, Workspace
    from mirage.runtime.python.monty import MontyRuntime

    ws = Workspace(
        {"/work": (RAMVFS(), MountMode.EXEC)},
        runtimes=[MontyRuntime(captures=["python", "python3"])],
    )


    @asynccontextmanager
    async def lifespan(app: FastAPI):
        yield
        await ws.close()


    app = FastAPI(lifespan=lifespan)


    class Run(BaseModel):
        command: str


    @app.post("/sessions/{session_id}")
    async def create(session_id: str) -> None:
        ws.create_session(session_id)


    @app.post("/sessions/{session_id}/run")
    async def run(session_id: str, body: Run) -> dict:
        r = await ws.shell(body.command, session_id=session_id)
        return {"stdout": await r.stdout_str(), "stderr": await r.stderr_str(), "exit_code": r.exit_code}
    ```

    ```bash
    uvicorn app:app --port 3000
    ```
  </Tab>
  <Tab title="Express" icon="/images/typescript-logo.svg">
    ```typescript app.mjs
    import express from 'express'
    import { MontyRuntime, MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'

    const ws = new Workspace(
      { '/work': new RAMVFS() },
      { mode: MountMode.EXEC, runtimes: [new MontyRuntime({ captures: ['python', 'python3'] })] },
    )
    const app = express()
    app.use(express.json())

    app.post('/sessions/:id', (req, res) => {
      ws.createSession(req.params.id)
      res.sendStatus(201)
    })

    app.post('/sessions/:id/run', async (req, res) => {
      const r = await ws.shell(req.body.command, { sessionId: req.params.id })
      res.json({ stdout: r.stdoutText, stderr: r.stderrText, exitCode: r.exitCode })
    })

    app.listen(3000, '127.0.0.1')
    ```

    ```bash
    node app.mjs
    ```
  </Tab>
</Tabs>

## Usage

```bash
curl -X POST localhost:3000/sessions/a
curl -X POST localhost:3000/sessions/a/run -H 'content-type: application/json' \
  -d '{"command": "cd /work && echo \"print(sum(range(10)))\" > s.py && python3 s.py"}'
```

The run prints `45`. A later call to session `a` starts in `/work`, where the
`cd` left it.

The examples below send several lines in one request. This shell function
reads the lines from standard input, sends them to session `a` as the
`command`, and prints what they print, errors included. It needs
[`jq`](https://jqlang.org):

```bash
run() {
  jq -Rs '{command: .}' |
    curl -s localhost:3000/sessions/a/run -H 'content-type: application/json' -d @- |
    jq -j '.stdout, .stderr'
}

run <<'SH'
pwd
python3 s.py
SH
```

```text
/work
45
```

The lines between `SH` and `SH` run in the terminal on the server, not in
the shell that calls `run`.

## Terminals per server

A sandbox is a machine, so it reserves memory for its agent whether the agent
is working or waiting. A terminal is not a machine. It is a record in your
server's memory: a working directory, variables and a history.

<SandboxesVsTerminals />

Each square is 128 MB, the least that the sandbox services linked above
reserve for one agent. The server is drawn at the same scale, four squares
for 512 MB, and then enlarged to show its terminals. Move the slider to add
agents.

What a terminal costs depends on what it is doing:

| A terminal that is | Holds | Is limited by |
| --- | --- | --- |
| idle, between an agent's turns | its variables and history | memory, tens of kilobytes each |
| waiting on a service, as in `curl` or `gh pr list` | the reply it is reading | memory |
| working on data, as in `sort` or a Python script | the data in its pipes | the server's CPU, then memory |

- **Idle terminals are nearly free.** No process or thread waits for one. A
  server with the memory that one sandbox reserves holds thousands of them,
  so an agent can keep its terminal between turns.
- **Terminals waiting on a service run at once.** A command that waits for a
  reply uses no CPU while it waits, and the server runs other terminals'
  commands in the meantime. See [Async](#async).
- **Terminals working on data share the CPU.** Commands that sort, search or run
  Python share the server's CPU, so each takes longer as more run together.
  A command that needs a core to itself belongs on a machine: see
  [Runtime Routing](/home/examples/runtime-routing).
- **Files in a memory mount are the server's memory.** A 2 MB log in a
  memory mount is 2 MB that the server holds. For data you do not want in
  memory, mount storage: see [VFS](/home/setup/vfs).

Press each button to see four terminals run a command at the same moment:

<WaitingOrWorking />

Size the server as you would any web service: by how many terminals are busy
at the same moment, not by how many exist.

## Limits

Every terminal runs in the one server process, so a command that takes too much
memory takes it from the other terminals. Mirage caps what a terminal can
take, and the caps are on by default:

| A command that | Is stopped by | Default |
| --- | --- | --- |
| keeps growing a variable | `max_env` | 2 MB for each terminal |
| fills memory with files or a command's output | `max_memory` | 96 MB for the workspace |

A terminal that reaches a cap gets an error, as it would from bash, and
keeps working. The first block doubles a variable without end, and the
second writes a 120 MB file:

```bash
run <<'SH'
x=aaaaaaaaaaaaaaaa
while true; do x=$x$x; done
SH
run <<< 'echo the terminal still works'
```

```text
bash: xmalloc: cannot allocate 2097153 bytes (past max_env of 2097152 bytes, a mirage workspace setting)
the terminal still works
```

```bash
run <<'SH'
head -c 120000000 /dev/zero > /work/big.bin
rm /work/big.bin
SH
```

```text
bash: line 1: /work/big.bin: Disk quota exceeded
```

`max_memory` is for the workspace, and the server on this page has one
workspace. Its terminals share the 96 MB, so a file that one terminal leaves
in `/work` counts against all of them. Write a file from each terminal, then
remove one:

<SharedBudget />

To give each agent its own budget, give it its own workspace.

Set the caps where the server creates the workspace:

<Tabs>
  <Tab title="FastAPI" icon="/images/python-logo.svg">
    ```python
    ws = Workspace(
        {"/work": (RAMVFS(), MountMode.EXEC)},
        runtimes=[MontyRuntime(captures=["python", "python3"])],
        max_memory="32MB",
        max_env="256KB",
    )
    ```
  </Tab>
  <Tab title="Express" icon="/images/typescript-logo.svg">
    ```typescript
    const ws = new Workspace(
      { '/work': new RAMVFS() },
      {
        mode: MountMode.EXEC,
        runtimes: [new MontyRuntime({ captures: ['python', 'python3'] })],
        maxMemory: '32MB',
        maxEnv: '256KB',
      },
    )
    ```
  </Tab>
</Tabs>

A cap needs headroom to work. While a command writes a file, the server holds
several times the bytes written, so a write that reaches the default 96 MB
cap can take a few hundred megabytes for a moment. A server with 512 MB or
more has that room. On a smaller server, set `max_memory` lower: otherwise
one large write can end the process before the cap refuses it.

[Limits](/home/limits) lists every limit, including the ones for a loop that
never ends and for a command that starts processes without end.

## Async

`ws.shell` is a coroutine in Python and a promise in TypeScript, and it never
blocks the event loop. The handlers above are `async`, so while one terminal
waits on a file read, a runtime or a slow command, the server keeps serving
every other terminal, with no thread or process per terminal.

<Tabs>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    import asyncio

    for sid in ["a", "b", "c"]:
        ws.create_session(sid)
    await asyncio.gather(*(ws.shell("sleep 1", session_id=sid) for sid in ["a", "b", "c"]))
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    for (const sid of ['a', 'b', 'c']) ws.createSession(sid)
    await Promise.all(['a', 'b', 'c'].map((sid) => ws.shell('sleep 1', { sessionId: sid })))
    ```
  </Tab>
</Tabs>

The three commands finish together in about a second; 20 sessions take the
same. Within one session, commands run one after another in order, as in a real
terminal, so three `sleep 1` commands on session `a` take three seconds.

## Sharing and security

- Terminals share the workspace's mounts, so a file one writes under `/work`
  is visible to the others. Give each terminal its own directory, or its own
  workspace, to keep files apart.
- The server runs any command for any caller that names a session. Put
  authentication and a check that the caller owns the session in front of it
  before it listens beyond localhost.
- A [session profile](/home/configuration/session) and a
  [policy](/home/policy/overview) decide which commands a terminal may run
  and which files it sees. [Policy & Security](/home/examples/policy-security)
  walks through one.
