Explain answers what a session's call would do, without doing it:
`explain.shell(line)` for `session.shell(line)`, and
`explain.vfs.<call>(...)` for each of the 24 VFS calls on `session.vfs`.
Nothing runs, nothing is recorded and no grant is spent. A policy that
reads a file to decide still reads it; its writes fail with `EROFS`.

```python
explain = (await ws.session("reviewer")).explain
line = await explain.shell("rm /data/x")
call = await explain.vfs.write("/vault/key", b"x")
```

```typescript
const explain = (await ws.session('reviewer')).explain
const line = await explain.shell('rm /data/x')
const call = await explain.vfs.write('/vault/key', 'x')
```

## Every door

Explain is an option on the call itself, and every door answers the same
fields as JSON.

| Door | A line | A VFS call |
| --- | --- | --- |
| In-app | `session.explain.shell(line)` | `session.explain.vfs.<call>(...)` |
| [HTTP](/home/access/http#shell-vfs-calls-and-tools) | `POST /shell?explain=true` | `POST /vfs/<call>?explain=true` |
| [RPC](/home/access/rpc) | `shell` with `explain: true` | `vfs/<call>` with `explain: true` |
| [MCP](/home/access/mcp#vfs-calls-and-explain), with `?calls=all` | `shell` with `explain: true` | `vfs_<call>` with `explain: true` |
| [CLI](/home/access/cli#run-lines-vfs-calls-and-tools) | `mirage shell -c LINE --explain` | `mirage vfs CALL ARGS --explain` |

Only the line is read: stdin, `cwd`, `runtime` and a background job would
change what runs, so a door refuses them with explain.

## The answer

Every answer has:

- `outcome`: `allow`, `deny` or `ask`.
- `reason`: the rule's reason, or empty.
- `source`: where the rule is written (`top`, `mounts./runbook`,
  `commands.allow`).
- `answers`: each policy's answer, in order.
- `refusal`: the record the agent would get, or `null`.

| Explained | Adds |
| --- | --- |
| A line | `exit_code` and `stderr` the agent reads if the line is refused whole, else `0` and empty; `node`, the parse tree; `answers` from placement |
| A command (a tree node) | `command`, `argv`, its own `exit_code` and `stderr`, `operands` (`text`, `path`, `matched`), `runtime` |
| A VFS call | `call`, `paths`, `error` (`EACCES`, `EROFS`, or empty) |

A line is refused whole by a rule or an unanswered ask, and its verdict
is the first command that does so. Anything else fails only its own
command: in `rm /x; echo done`, with `rm` not on the allow list, the line
is `allow` and `rm` is `deny`.

## The tree

A line's `node` holds `list`, `pipeline`, `subshell`, `group`,
`substitution`, `line` (`bash -c`, `eval`, `xargs`) and `command` nodes.
`mirage shell --explain` prints it:

```text
cat /data/a | wc -l && echo $(cat /data/keys/a)  [deny, exit 1: sealed]
  list: cat /data/a | wc -l && echo $(cat /data/keys/a)
    pipeline: cat /data/a | wc -l
      cat /data/a  [allow]
      wc -l  [allow]
    echo $(cat /data/keys/a)  [allow]
      substitution: cat /data/keys/a
        cat /data/keys/a  [deny, exit 1: sealed]  top
```

## Limits

- A hidden path explains like a path no rule matches; explain never
  reveals a hide.
- `list_files` is judged at its listing, not per entry.
- In TypeScript without async task isolation (a browser), `explain.vfs`
  throws and `explain.shell`'s policies act for real.
