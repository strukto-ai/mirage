## How To Read This Matrix

Events split into two halves, and they have different support stories:

- **Delivery** (`ws.events()` + `ws.notify()`) works on **every mount** today.
  Delivery is notify-driven: any detection you run maps its signal to a
  `FileEvent` and injects it, and Mirage handles invalidation, scope matching,
  and the event stream. No per-backend code is involved.
- **Detection** is the provider's push, per backend. Where the push names
  the change, Mirage ships a **mapper** (`to_events`, `toEvents`) that turns the
  payload into paths. Where the push is only a **ping**, the mount's
  `delta_hook()` (`deltaHook()`) answers it with one read of the provider's
  change feed.

| VFS | Push signal (provider-side) | Mirage answers it with |
| --- | --- | --- |
| Disk | inotify / FSEvents / watchdog / chokidar | mapper `DiskEventHook` |
| S3 / S3-compatible | S3 Event Notifications (SQS, SNS, EventBridge) | mapper `S3EventHook` |
| GitHub | repository `push` webhooks | mapper `GitHubEventHook` |
| Nextcloud | `webhook_listeners` (Nextcloud 30+) | mapper `NextcloudEventHook` |
| MongoDB | change streams | mapper `MongoDBEventHook` |
| GridFS | change streams on `<bucket>.files` | mapper `GridFSEventHook` |
| Slack | Events API | mapper `SlackEventHook` |
| Redis | keyspace notifications | mapper `RedisEventHook` |
| Discord | Gateway dispatches (`MESSAGE_*`, reactions, channels, members, guilds) | mapper `DiscordEventHook` |
| Linear | webhooks (`Issue`, `Comment`) | mapper `LinearEventHook` |
| Trello | board webhooks (actions) | mapper `TrelloEventHook` |
| Notion | webhook events (`page.*`, `database.*`, `data_source.*`) | mapper `NotionEventHook` |
| Email (IMAP) | IMAP IDLE (`EXISTS`, `EXPUNGE`, `FETCH`) | mapper `EmailEventHook`, `unknown` on the folder |
| Airtable | webhook notifications (base, webhook, time) | ping: `delta_hook()` reads each webhook's `payloads` |

Where each mapper is imported from, on both hosts, is in the
[Notifications overview](/home/events#payloads).

A mapper reads the payload and, at most, the backend for what the payload
leaves out (GridFS counts the revisions a name has left; MongoDB lists a
database's views; Discord, Linear, Trello and Notion read a name the payload
gives only as an id, once, and remember it). A ping handler reads the change
feed from its cursor and never walks the tree. Calendar issues a sync token
only at the end of a full sync, so it reads a calendar whole for its baseline
and when its token expires. Airtable reads every webhook on each base the event
root covers, so one webhook per base with the `tableData`, `tableFields` and
`tableMetadata` data types covers records, fields and table names.

## What A Ping Handler Keeps

The checkpoint `pull` hands back is opaque, but it is more than the feed's
cursor. A feed that names items by id (Drive, Graph, Box) says where an item is
now, not where it was, so the checkpoint keeps the path of each item a pull has
placed, and a later rename, move or delete leaves that path. Airtable names
tables by id, so its checkpoint keeps each table's directory. An item seen for
the first time is a `create` when the provider says it is as it was made (its
created and modified times agree, or the feed says it was added) and an
`update` otherwise; where it was before is left to the index's expiry.

A cursor the provider no longer honors answers `unknown` on the event root and
a fresh cursor: a Dropbox reset, a Graph `resyncRequired`, a Gmail history id
past what Gmail keeps, a Box stream position older than two weeks, since Box
replays whatever it still has rather than refusing an old position, and
Airtable payloads past their seven days or a webhook that is gone.

## Delivery Without A Mapper

Any backend delivers events end to end the moment you have a signal from
anywhere:

<CodeGroup>

```python Python
async for event in ws.events("/s3/exports/*.csv"):
    ...

await ws.notify(
    FileEvent(
        kind=FileChangeKind.CREATE,
        path=PathSpec.from_str_path("/s3/exports/jan.csv"),
        timestamp=datetime.now(timezone.utc),
    )
)
```

```typescript TypeScript
import { FileChangeKind, FileEvent, PathSpec } from '@struktoai/mirage-node'

for await (const event of ws.events('/s3/exports/*.csv')) {
  console.log(event.kind, event.path.virtual)
}

await ws.notify(
  new FileEvent({
    kind: FileChangeKind.CREATE,
    path: PathSpec.fromStrPath('/s3/exports/jan.csv'),
    timestamp: new Date(),
  }),
)
```

</CodeGroup>

`events()` is an async generator, so it subscribes on the first iteration, not
at the call: the loop and the `notify` call belong to different tasks (a
request handler, a queue consumer). Awaiting `notify` before anything consumes
the iterator drops the event.

The guarantee is identical on every backend: caches for the changed path and
its ancestor listings are invalidated before delivery, plus the cached subtree
of a removed folder that still has a listing cached at or under it, so reads
after an event are fresh within the limit the [Notifications overview](/home/events)
describes.

## The Dropbox Longpoll Example

[`dropbox/events.py`](https://github.com/strukto-ai/mirage/blob/main/examples/python/dropbox/events.py)
and [`dropbox/events.ts`](https://github.com/strukto-ai/mirage/blob/main/examples/typescript/dropbox/events.ts)
own the loop in the embedding program: take a baseline with `pull`, wait for
`list_folder/longpoll`, then pull and `notify` each change. The examples read
the cursor from the checkpoint (`dropbox.cursor`) to longpoll on it, while
passing the entire checkpoint back to `pull`. This is Dropbox-specific example
code; other consumers should treat checkpoints as opaque. On a reset, pull with
the old checkpoint: the hook reports the event root as `unknown` and takes a
fresh cursor. A missing event root retries after 30 seconds.

Set `DROPBOX_APP_KEY`, `DROPBOX_APP_SECRET`, and `DROPBOX_REFRESH_TOKEN`;
optionally set `DROPBOX_ROOT_PATH`. Then run one of:

```bash
./python/.venv/bin/python examples/python/dropbox/events.py
```

```bash
pnpm --filter @struktoai/mirage-examples exec tsx dropbox/events.ts
```

The first runs from the repo root, the second from `typescript/`. Ctrl-C
cancels the current request and closes the workspace. Because `pull` has no
cancellation parameter, the TypeScript example then allows one more second
before exiting with status 130 if an in-flight pull still holds the process
open; the deadline never interrupts workspace cleanup.

Dropbox's [longpoll endpoint](https://docs.dropboxapi.com/dropbox-api/api-reference/user-endpoints/files/list-folder-longpoll)
uses the notification host without an Authorization header. Its timeout is
30 to 480 seconds; the HTTP timeout must also allow up to 90 seconds of server
jitter. The returned `backoff` is a required minimum delay before the next
longpoll, including a response with no changes. The examples let transport or
unexpected API failures surface and close their resources on cancellation.
