`microsandbox` runs captured programs in a running
[Microsandbox](https://microsandbox.dev) guest, by name. Python and Node
use the `msb` CLI, just like the smolvm provider uses its CLI. No Microsandbox
SDK package is needed. You create and start the sandbox; Mirage only runs
programs in it.

## Installation

Install `msb` 0.7.8 or later on the host and put it on `PATH`; older
releases, such as 0.5, have no `exec --no-tty`, so every command fails.
Create a sandbox from an image with Mirage, `fuse3`, and the programs your
captures need. The
[sandbox image](/home/setup/runtime/sandbox#the-sandbox-image) can be pushed
to an OCI registry and used by Microsandbox:

```bash
msb create my-registry/mirage-fuse:latest --name mirage-box
```

The runtime was verified with released Microsandbox 0.7.8 on macOS
Apple Silicon, using its stock CLI, firmware and Linux aarch64 guest agent.
No local Microsandbox patches are required. `/dev/fuse` was present and usable
as root. If programs run as another user, configure that user's device
and mount permissions inside the guest.

## Usage

`captures` defaults to [`@external`](/home/setup/runtime/overview#captures).
Add `python3` to run Python programs in the guest too.

<Tabs>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import RAMVFS, MountMode, Workspace
    from mirage.runtime.sandbox.microsandbox import MicrosandboxRuntime

    runtime = MicrosandboxRuntime(
        captures=["python3", "@external"],
        config={"sandbox": "mirage-box"},
    )
    ws = Workspace({"/data": RAMVFS()}, mode=MountMode.EXEC, runtimes=[runtime])
    await ws.shell("python3 -c 'print(1 + 1)'")
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { MountMode, RAMVFS, MicrosandboxRuntime, Workspace } from '@struktoai/mirage-node'

    const runtime = new MicrosandboxRuntime({
      captures: ['python3', '@external'],
      config: { sandbox: 'mirage-box' },
    })
    const ws = new Workspace({ '/data': new RAMVFS() }, { mode: MountMode.EXEC, runtimes: [runtime] })
    await ws.shell("python3 -c 'print(1 + 1)'")
    ```
  </Tab>
  <Tab title="YAML" icon="file-code">
    ```yaml
    mode: exec
    runtimes:
      - name: microsandbox
        captures: ["python3", "@external"]
        config:
          sandbox: mirage-box
    mounts:
      /data:
        vfs: ram
    ```
  </Tab>
</Tabs>

## Connecting the workspace

Choose how files reach the guest with `mount_type` in Python or YAML,
or `mountType` in TypeScript:

- `ssh` serves the host workspace's session view over SFTP to `sshfs`
  inside the guest. Host RAM files, writes, hides and mount permissions
  are shared through that session. Install `mirage-ai[ssh]` on a Python
  host or the optional `ssh2` dependency on a Node host, and `sshfs` in
  the guest. Guest Mirage is not needed for this mode.
- `fuse` uses mounts served by Mirage inside the guest. The host refuses
  commands while a session rule covers a guest-served mount whose file
  operations it cannot enforce.
- `both` uses existing guest mounts and serves the remaining prefixes
  over SFTP, applying the same rule checks to guest-served mounts.
- Leaving the option unset preserves the original behavior: arrange
  file access yourself, as with smolvm.

For a host workspace shared over SFTP:

```python
runtime = MicrosandboxRuntime(
    captures=["python3", "@external"],
    config={"sandbox": "mirage-box", "mount_type": "ssh"},
)
```

```typescript
const runtime = new MicrosandboxRuntime({
  captures: ['python3', '@external'],
  config: { sandbox: 'mirage-box', mountType: 'ssh' },
})
```

Mirage holds an `msb exec --stream` pipe open for passive `sshfs`, which
preserves SFTP bytes without a terminal. This serves files from the host
to the guest; Microsandbox's separate native SSH/SFTP interfaces serve
the guest's files to SSH clients. The mount mode needs no SSH listener,
authorized key, or SSH daemon. Each `ssh` or `both` runtime instance serves
only its first session until it closes. Closing unmounts
host-served prefixes and leaves the sandbox running.

For `fuse`, put a `sandbox.yaml` in the image or copy it into the sandbox:

```yaml
mounts:
  /data:
    vfs: ram
    mode: WRITE
    backend: fuse
    mountpoint: /data
```

```bash
msb copy sandbox.yaml mirage-box:/tmp/sandbox.yaml
msb exec mirage-box -- mkdir -p /data
msb exec mirage-box -- mirage workspace create /tmp/sandbox.yaml
```

The guest serves its own workspace. A RAM mount there has its own data;
matching the host's path does not share the host's RAM mount. To share an
external backend, configure both workspaces to use it. The guest config
decides its permissions and credentials; the host workspace's policies
do not automatically apply to guest file operations.

## Notes

- Each command checks `msb status NAME --format json` and requires `Running`.
  Probes time out after ten seconds; cancellation stops the probe process too.
- Released `msb exec` can automatically start a stopped guest. Mirage refuses
  guests already stopped when checked, but if the guest stops between the
  status check and execution, the CLI may start it again. Avoid stopping or
  restarting the guest while Mirage is using it. This race remains until a
  released CLI offers execution without automatic startup.
- Commands preserve stdin, stdout, stderr, exit status, environment and cwd.
  Process arguments and the working directory are passed as separate arguments,
  not interpolated into shell code.
- As a temporary workaround for released agents blocking during startup in an
  SSHFS directory, Mirage starts a shell in `/`, changes to the requested
  directory inside that shell, then replaces it with the requested program.
  The guest needs a POSIX `sh`; a working directory the guest does not have
  fails the command with exit status 126, as on Docker.
  This delayed-`cd` workaround can be removed once nonblocking guest startup
  is released and required.
- Passive SSHFS symlink handling is explicit; Mirage does not pretend to be
  OpenSSH or change the SSH identification banner.
- Closing the runtime leaves the user's sandbox running.
- Each sandbox shares files and processes across its commands. Use a
  separate sandbox per tenant.
- Environment variables passed with `-e` are visible in the host's process
  arguments. Do not pass secrets this way on a host shared with untrusted users.
- Mount startup errors keep a bounded tail of CLI stderr.
- A Mirage timeout cancels the host CLI call. The guest agent cleans up that
  connection's commands; kernel-blocked filesystem cleanup may take longer.
  Use Microsandbox's own limits when required.
