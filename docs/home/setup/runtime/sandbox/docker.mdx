`docker` runs captured programs in a running container, by name. You start
and stop the container; Mirage only runs programs in it. Python SDK and
Node.

## Installation

Start the container with FUSE allowed, from an image that has what
[connecting the workspace](#connecting-the-workspace) needs:

```bash
docker run -d --cap-add SYS_ADMIN --device /dev/fuse \
  --name my-sandbox my-image sleep infinity
```

## Usage

`captures` defaults to [`@external`](/home/setup/runtime/overview#captures):
every program Mirage does not have itself. Name `python3` to run it in the
container too.

<Tabs>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    from mirage import RAMVFS, MountMode, Workspace
    from mirage.runtime.sandbox.docker import DockerRuntime

    runtime = DockerRuntime(
        captures=["python3", "@external"],
        config={"container": "my-sandbox", "mount_type": "ssh"},
    )
    ws = Workspace({"/data": RAMVFS()}, mode=MountMode.EXEC, runtimes=[runtime])
    await ws.shell("python3 -c 'print(1 + 1)'")
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { DockerRuntime, MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'

    const runtime = new DockerRuntime({
      captures: ['python3', '@external'],
      config: { container: 'my-sandbox', mountType: 'ssh' },
    })
    const ws = new Workspace({ '/data': new RAMVFS() }, { mode: MountMode.EXEC, runtimes: [runtime] })
    await ws.shell("python3 -c 'print(1 + 1)'")
    ```
  </Tab>
  <Tab title="YAML" icon="file-code">
    ```yaml
    mode: exec
    runtimes:
      - name: docker
        captures: ["python3", "@external"]
        config:
          container: my-sandbox
          mount_type: ssh
    mounts:
      /data:
        vfs: ram
    ```
  </Tab>
</Tabs>

## Connecting the workspace

A program in the container opens workspace files at the same paths as in
Mirage, so the container must see the mounts there. `mount_type` picks how:

| `mount_type` | How the files get there | Rules that apply |
| --- | --- | --- |
| `ssh` | Mirage serves every mount over `docker exec`; the container mounts each with `sshfs` | This workspace's mount modes, hides, permissions and policies |
| `fuse` | A Mirage inside the container mounts your backends with FUSE | That Mirage's own config |
| `both` | The container's own FUSE mounts where it has them, `ssh` for the rest | Each side's own |
| unset | Nothing; you put the files there yourself | The container's |

### ssh

- The image needs only `sshfs`. No Mirage, keys or open port in the
  container.
- The host needs `pip install 'mirage-ai[ssh]'` (Python) or `pnpm add ssh2`
  (Node).
- Each file call is a round trip to the workspace; with `both`, keep bulk
  data on the container's own mounts.
- The container shows one session's view, the first that runs a line there.
  Give each agent its own container.
- The root mount and `/dev` are not served.

### fuse

Build [the sandbox image](/home/setup/runtime/sandbox#the-sandbox-image), which
carries Mirage and `fuse3`. Write the same mounts at the same paths into
`sandbox.yaml`, and start Mirage with it in the container:

```yaml
mounts:
  /data:
    vfs: s3
    config:
      bucket: my-bucket
    backend: fuse
    mountpoint: /data
```

```bash
docker cp sandbox.yaml my-sandbox:/tmp/sandbox.yaml
docker exec my-sandbox mirage workspace create /tmp/sandbox.yaml
```

- This workspace's rules do not reach those files, so a line is refused
  while the session's permissions hide or narrow anything under them.
- Keep the container's paths in step with the host's mounts yourself.
  `sandbox.yaml` can differ where it should, such as an endpoint
  (`host.docker.internal`) or narrower credentials.

## What is wired

| | In the container |
| --- | --- |
| Command | The captured program and its words, as typed |
| Piped input | stdin |
| Environment | The session's, over the config `env` |
| Working directory | The shell's, unchanged |
| Workspace files | By `mount_type`, above |
| Disk and network | The container's own |

## Notes

- `container` takes a name or an ID. The Docker CLI is the transport, so
  Docker Desktop, Colima and a compatible Podman alias all work.
- Sizing, GPUs, networks, volumes and bind mounts go on your own
  `docker run`. You can bake `sandbox.yaml` into the image instead of
  copying it.
- A [timeout](/home/setup/runtime/sandbox#timeouts) does not kill the program in the container.
