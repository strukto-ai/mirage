A sandbox runtime runs captured programs somewhere you already have: a
container, a microVM, a cloud sandbox or a machine over SSH. You create and
stop it; Mirage only runs programs in it. Each runtime's `captures` defaults
to [`@external`](/home/setup/runtime/overview#captures), every program
Mirage does not have itself.

A program there opens workspace files at the same paths, so the sandbox
must see the mounts. `docker`, `e2b`, `ssh`, `smolvm`, `microsandbox`, and `apple_container` pick how with `mount_type`: `ssh`
serves them from the workspace, `fuse` from a Mirage inside the sandbox, and
`both` mixes the two. Daytona uses a Mirage inside.

| Runtime | Runs programs in | Workspace files through |
| --- | --- | --- |
| [Docker](/home/setup/runtime/sandbox/docker) | A Docker container | `mount_type`: `ssh`, `fuse` or `both` |
| [E2B](/home/setup/runtime/sandbox/e2b) | An E2B cloud sandbox | `mount_type`: `ssh`, `fuse` or `both` |
| [Daytona](/home/setup/runtime/sandbox/daytona) | A Daytona cloud sandbox | FUSE, from a Mirage inside |
| [smolvm](/home/setup/runtime/sandbox/smolvm) | A microVM with its own kernel | `mount_type`: `ssh`, `fuse` or `both` |
| [Microsandbox](/home/setup/runtime/sandbox/microsandbox) | A microVM with its own kernel | `mount_type`: `ssh`, `fuse` or `both` |
| [Apple Container](/home/setup/runtime/sandbox/apple_container) | A container on macOS, one per agent if you map them | `mount_type`: `ssh`, `fuse` or `both` |
| [SSH](/home/setup/runtime/sandbox/ssh) | Any machine running `sshd` | `mount_type`: `ssh`, `fuse` or `both` |
| [Sandlock](/home/setup/runtime/sandbox/sandlock) | This Linux host, confined | A [FUSE folder](/home/setup/fuse) you grant |

After following a provider page's **Connecting the workspace** steps, run the
shared [workspace file check](/home/setup/runtime/overview#verify-workspace-file-access)
to confirm reads and writes cross the runtime boundary.

## Language compatibility

Python modules, file modes and other language APIs come from the interpreter
installed in the sandbox image or on the remote machine. For Sandlock, they
come from this host's interpreter. Mirage forwards the captured program's
arguments, input, environment and working directory; a working directory
the sandbox lacks fails the program with exit 126. Each provider's
**Runtime behavior** table describes that boundary.

File operations reach workspace mounts through the connection configured
for that provider. They also remain subject to the sandbox or host's own
permissions and confinement.

## The sandbox image

A sandbox that serves the mounts with its own Mirage needs `fuse3` and
Mirage. The repository's Dockerfile builds that image from the current
checkout, with every mountable backend:

```bash
docker build -f docker/sandbox/Dockerfile --target fuse -t mirage-python-fuse .
```

Narrow it to the backends you use with `MIRAGE_EXTRAS`:

```bash
docker build -f docker/sandbox/Dockerfile --target fuse \
  --build-arg MIRAGE_EXTRAS=s3,postgres -t mirage-fuse-lean .
```

The same image serves every provider: run it under Docker, Apple's
`container`, Microsandbox or smolvm, or use it as a Daytona image or an E2B template base.
Add the programs your captures need, such as Node.js for `node`. The Mirage
inside is the Python build, whichever SDK the host uses.

## Timeouts

`command_limits` apply to a sandboxed program as to any command: past
`timeout_seconds` it exits 124, and `max_bytes` and `max_lines` cap its
output.

<Warning>
  A timeout stops Mirage waiting; it does not always stop the program.
  Sandlock kills it. E2B tries to kill the command, but its child processes
  may survive. The other providers leave it running, and a Daytona sandbox has no timeout of its
  own, so it keeps running and billing. Use the provider's own limits.
</Warning>


## Serving the session's files

With `mount_type: ssh`, workspace file access follows the session's permissions
and policies. You do not need to expose a public file server or copy service
credentials into the sandbox. Each sandbox is assigned to one session.

Mirage refuses to run a program when it cannot enforce the session's file
restrictions. Unsupported cases include:

- Restrictions on `/` or `/dev`.
- Hiding a mount when doing so would expose the sandbox's own files underneath.
- Restrictions on mounts served by a separate Mirage inside the sandbox.
- File rules that depend on which program opens a file.
