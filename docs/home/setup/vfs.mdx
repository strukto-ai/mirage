Mirage turns your data sources into one unified virtual filesystem. Each
source is a VFS mounted under its own folder, such as S3 under `/s3`, Slack
under `/slack` and PostgreSQL under `/pg`, and an agent reads them all with
`ls`, `cat`, `grep` and `find`.

Each VFS turns its service into files and folders. An S3 object is a file, a
Slack channel is a folder with one `chat.jsonl` per day, and a PostgreSQL
table is a folder with its rows in `rows.jsonl`. [RAM](/home/setup/ram) needs
no credentials, so start there to try it.

## Example: Slack

Mount Slack under `/slack` with a [bot token](/home/setup/slack), plus a user
token for search:

<Tabs>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    import os

    from mirage import MountMode, Workspace
    from mirage.vfs.slack import SlackConfig, SlackVFS

    slack = SlackVFS(
        config=SlackConfig(
            token=os.environ["SLACK_BOT_TOKEN"],
            search_token=os.environ["SLACK_USER_TOKEN"],
        )
    )
    ws = Workspace({"/slack": slack}, mode=MountMode.READ)
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { MountMode, SlackVFS, Workspace } from '@struktoai/mirage-node'

    const slack = new SlackVFS({
      token: process.env.SLACK_BOT_TOKEN!,
      searchToken: process.env.SLACK_USER_TOKEN,
    })
    const ws = new Workspace({ '/slack': slack }, { mode: MountMode.READ })
    ```
  </Tab>
  <Tab title="YAML" icon="file-code">
    ```yaml
    mounts:
      /slack:
        vfs: slack
        mode: read
        config:
          token: ${SLACK_BOT_TOKEN}
          search_token: ${SLACK_USER_TOKEN}
    ```
  </Tab>
</Tabs>

Slack becomes:

```text
/slack/
  channels/
    general__C04KEPWF6V7/
      2026-04-05/
        chat.jsonl
        files/
          roadmap__F07AB12CD.pdf
  dms/
    alice__D0AQDJ5FP9V/
      2026-04-05/
        chat.jsonl
  users/
    alice__U12345678.json
```

Each channel and DM has one folder per day for the last 90 days, and a day's
`chat.jsonl` holds one message per line. A name ends with its Slack ID after
`__`, so two channels with the same name stay apart.

```bash
ls /slack/channels/
head -1 /slack/channels/general__C04KEPWF6V7/2026-04-05/chat.jsonl
grep -rw refund /slack/channels/
```

The `head` prints:

```json
{"type":"message","user":"U12345678","text":"PR #326 is up for review","ts":"1775383200.000100"}
```

The `grep` uses Slack's own search: it asks Slack which days mention `refund`
and reads only those, not every day of every channel. That takes the
`search_token` (a user token with `search:read`) and `-w`,
since Slack matches whole words. Without them, or when Slack's search cannot
answer, `grep` reads the files. Slack searches message text, file names and
reactions, and finds a new message only once it has indexed it. Attachments
under `files/` are always read.

## Mount capacity

A RAM, disk, Redis, OPFS or SQL mount keeps the files itself, and takes
`capacity` in its `config` to cap the bytes it holds, as a
[size](/home/configuration#sizes):

```yaml
mounts:
  /data:
    vfs: ram
    mode: write
    config:
      capacity: 100MB
```

A write past it fails with `EDQUOT` ("Disk quota exceeded", the same message
for every VFS). Through a [FUSE folder](/home/setup/fuse), a program gets it
when it syncs or closes the file. Stored data stays readable and removable,
and `df` shows the capacity as the mount's size.

What counts toward it depends on the VFS:

- **Disk, Redis and OPFS:** two workspaces on one folder, key prefix or OPFS
  directory each count only their own writes.
- **SQL:** every file in the database counts, and SQL mounts handed one
  driver with the same `capacity` share one count.
- **RAM:** files also count against the workspace's
  [`max_memory`](/home/core/output-limits#limit-a-workspaces-memory), which
  refuses a write the same way.

## Read and write behavior

Two keys decide when a mount serves its cached copy of a file, and what
happens when someone else changed the file. Set them on a mount, or set
`read` and `write` at the top of `workspace.yaml` as the default for every
mount.

### Reads

| `read` | Mirage serves a cached copy |
| --- | --- |
| `bounded` | Without asking the VFS, for up to `ttl` seconds. The default. |
| `fresh` | Only after asking the VFS whether the file changed, by its ETag or version. |

A mount that sets `read: bounded` also sets `ttl`, in whole seconds. A mount
that sets neither serves its cached copy for 600 seconds.

### Writes

| `write` | A write |
| --- | --- |
| `unconditional` | Replaces the file, and the last write wins. The default. |
| `conditional` | Carries the version the session last read, so a write based on a stale read is refused. |

`write: conditional` works on the [S3 VFS and the VFSes built on
it](/home/setup/s3#s3-compatible-vfses), [Box](/home/setup/box) and
[Dropbox](/home/setup/dropbox). It needs a writable mount that caches reads.
Any other mount that declares it is refused when it mounts.

Under `write: conditional`:

- A write or a delete based on a stale read is refused. Read the file again
  before you retry.
- If the session last saw no file at a path (a failed `cat` or `test -e`,
  or its own `rm`), a write there only creates the file. It fails if someone
  else created the file first. S3 sends `If-None-Match: *` for this. A VFS
  that cannot check it writes as usual.
- A refused write stays refused until the session reads the file again,
  even if the file was deleted.
- A write to a path the session never read or checked overwrites it, as on
  a normal filesystem.
- An append can be refused when someone else changed the file. Mirage
  returns the error and does not retry the append or rerun the command.
- The check lasts only while the session is live. It does not survive a
  workspace restart.

### When Mirage rewrites the whole file

Some VFSes, such as S3 and the other object stores, cannot append, write at
an offset or truncate in place. For these writes Mirage reads the whole file
and writes it back:

- an append;
- a write at an offset;
- a truncate to a nonzero size.

If that read finds no file, the write back only creates the file, under
either `write` setting. It fails if someone else created the file between
the read and the write, and that file keeps its bytes. A VFS that cannot
check this returns an unsupported-operation error.

An append with nothing to add, such as `cmd >> f` when `cmd` prints
nothing, is not rewritten. It leaves an existing file alone, and creates a
missing one under the same create-only rule.

A VFS with its own append, offset write or truncate, such as RAM, keeps its
own behavior. A plain replacement and a truncate to zero follow the mount's
`write` setting.
