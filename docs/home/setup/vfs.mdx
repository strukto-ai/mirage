Each data source is a VFS mounted under its own folder: S3 under `/s3`, Slack
under `/slack`, PostgreSQL under `/pg`. An agent reads them all with `ls`,
`cat`, `grep` and `find`. [RAM](/home/setup/ram) needs no credentials, so
start there.

## Example: Slack

<Tabs>
  <Tab title="YAML" icon="file-code">
    ```yaml
    mounts:
      /slack:
        vfs: slack
        mode: read
        config:
          token: ${SLACK_BOT_TOKEN}
          search_token: ${SLACK_USER_TOKEN}
    ```
  </Tab>
  <Tab title="Python" icon="/images/python-logo.svg">
    ```python
    import os

    from mirage import MountMode, Workspace
    from mirage.vfs.slack import SlackConfig, SlackVFS

    slack = SlackVFS(
        config=SlackConfig(
            token=os.environ["SLACK_BOT_TOKEN"],
            search_token=os.environ["SLACK_USER_TOKEN"],
        )
    )
    ws = Workspace({"/slack": slack}, mode=MountMode.READ)
    ```
  </Tab>
  <Tab title="TypeScript" icon="/images/typescript-logo.svg">
    ```typescript
    import { MountMode, SlackVFS, Workspace } from '@struktoai/mirage-node'

    const slack = new SlackVFS({
      token: process.env.SLACK_BOT_TOKEN!,
      searchToken: process.env.SLACK_USER_TOKEN,
    })
    const ws = new Workspace({ '/slack': slack }, { mode: MountMode.READ })
    ```
  </Tab>
</Tabs>

```text
/slack/
  channels/
    general__C04KEPWF6V7/
      2026-04-05/
        chat.jsonl
        files/
          roadmap__F07AB12CD.pdf
  dms/
    alice__D0AQDJ5FP9V/
      2026-04-05/
        chat.jsonl
  users/
    alice__U12345678.json
```

```bash
ls /slack/channels/
head -1 /slack/channels/general__C04KEPWF6V7/2026-04-05/chat.jsonl
grep -rw refund /slack/channels/
```

- Each channel and DM has one folder per day for the last 90 days, one
  message per line. A name ends with its Slack ID after `__`.
- `grep -w` with a `search_token` asks Slack's search which days match and
  reads only those. Without them, `grep` reads the files.

## Mount capacity

RAM, disk, Redis, OPFS and SQL keep the files themselves. `capacity` caps the
bytes a mount holds, as a [size](/home/configuration/workspace#sizes):

```yaml
mounts:
  /data:
    vfs: ram
    mode: write
    config:
      capacity: 100MB
```

- A write past it fails with `EDQUOT` (`Disk quota exceeded`). Through
  [FUSE](/home/setup/fuse), a program gets it on sync or close.
- Stored files stay readable and removable, and `df` shows the capacity.
- Disk, Redis and OPFS count only the mount's own writes. SQL counts every
  file in the database, and SQL mounts on one driver with the same `capacity`
  share one count. RAM also counts against [`max_memory`](/home/core/output-limits#limit-a-workspaces-memory).

## Read and write behavior

`read` and `write` go on a mount, or at the top of `workspace.yaml` for every
mount.

| `read` | A cached copy is served |
| --- | --- |
| `bounded` | Without asking the VFS, for `ttl` seconds: 600 by default. The default. |
| `fresh` | Only after the VFS confirms the file did not change, by ETag or version. |

| `write` | A write |
| --- | --- |
| `unconditional` | Replaces the file; the last write wins. The default. |
| `conditional` | Is refused when it is based on a stale read. |

`write: conditional` works on [S3 and the VFSes built on it](/home/setup/s3#s3-compatible-vfses),
[Box](/home/setup/box) and [Dropbox](/home/setup/dropbox), on a writable mount
that caches reads. Any other mount refuses it. Under it:

- A refused write stays refused until the session reads the file again.
- Where the session last saw no file, a write only creates one, and fails if
  someone else created it first.
- A path the session never read is overwritten, as on a normal filesystem.
- A refused append is not retried.
- The check lasts while the session is live, not across a restart.

Object stores cannot append, write at an offset or truncate in place, so
Mirage reads the whole file and writes it back. If that read finds no file,
the write only creates one. An append of nothing leaves the file alone.
