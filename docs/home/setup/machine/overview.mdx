A machine is somewhere you already have: a container, a microVM, a cloud
sandbox or a host over SSH. You create and stop it; Mirage only runs programs
on it.

Declare each machine under `machines:` with the `provider` that reaches it,
and run captured programs there with the `machine` runtime. `captures`
defaults to [`@external`](/home/setup/runtime/overview#captures), every
program Mirage does not have itself.

```yaml
machines:
  box:
    provider: docker
    container: my-sandbox
runtimes:
  - name: machine
    machine: box
```

A line or a command can also name its machine: `execute(machine=)`, a
`machine` on the shell request, or a policy's `Route(machine=)`.

| Provider | Runs programs in |
| --- | --- |
| [Docker](/home/setup/machine/docker) | A Docker container |
| [E2B](/home/setup/machine/e2b) | An E2B cloud sandbox |
| [Daytona](/home/setup/machine/daytona) | A Daytona cloud sandbox |
| [smolvm](/home/setup/machine/smolvm) | A microVM with its own kernel |
| [Microsandbox](/home/setup/machine/microsandbox) | A microVM with its own kernel |
| [Apple Container](/home/setup/machine/apple_container) | A container on macOS, a VM of its own |
| [SSH](/home/setup/machine/ssh) | Any machine running `sshd` |

[Sandlock](/home/setup/runtime/sandlock) is a runtime, not a machine: it runs
programs on this Linux host, confined.

To try one, start with [Docker](/home/setup/machine/docker).

## Connecting the workspace

A program on a machine opens workspace files at the same paths as in Mirage,
so the machine must see the mounts. `mount_type` picks how:

| `mount_type` | How the files get there | Rules that apply |
| --- | --- | --- |
| `ssh` | Mirage serves every mount over the provider's connection; the machine mounts each with `sshfs` | This workspace's mount modes, hides, permissions and policies |
| `fuse` | A Mirage on the machine mounts your backends with FUSE | That Mirage's own config |
| `both` | The machine's own FUSE mounts where it has them, `ssh` for the rest | Each side's own |
| unset | Nothing; you put the files there yourself | The machine's |

Daytona takes no `mount_type`: run a Mirage on the machine, as `fuse` does,
or put the files there yourself. Once connected, run the shared
[workspace file check](/home/setup/runtime/overview#verify-workspace-file-access).

### ssh

- The machine needs only `sshfs`. No Mirage, keys or open port.
- Each file call is a round trip to the workspace. With `both`, keep bulk
  data on the machine's own mounts.
- A machine shows one session's view, the first that runs a line there. An
  sshfs already serving a path Mirage serves is left alone and the line exits
  1. Give each agent and each workspace its own machine.
- If the machine restarts, Mirage mounts the paths again. A line caught
  mid-restart exits 126 without running.
- A write the workspace refuses, such as one past a mount's `capacity`,
  looks done to the program, but its command fails when the program ends:
  stderr names the file, as `docker: /data/big.bin: Disk quota exceeded`,
  and a command that would exit 0 exits 1.
- The root mount and `/dev` are not served.

Mirage refuses to run a program when it cannot enforce the session's file
rules: restrictions on `/` or `/dev`, hiding a mount when that would expose
the machine's own files underneath, restrictions on mounts a Mirage on the
machine serves, and rules that depend on which program opens a file.

### fuse

Build [the machine image](#the-machine-image), write the same mounts at the
same paths into `sandbox.yaml`, and start Mirage with it on the machine. Each
provider page has the commands.

```yaml
mounts:
  /data:
    vfs: s3
    config:
      bucket: my-bucket
    backend: fuse
    mountpoint: /data
```

- This workspace's rules do not reach those files, so a line is refused
  while the session's permissions hide or narrow anything under them.
- If a path the machine mounted goes away, lines exit 126 until it is
  mounted again. Start Mirage from the image's entrypoint so a restart
  mounts it again.
- Keep the machine's paths in step with the host's mounts yourself.
  `sandbox.yaml` can differ where it should, such as narrower credentials.

## What a program sees

| | On the machine |
| --- | --- |
| Command | The captured program and its words, as typed |
| Piped input | stdin |
| Environment | The session's, over the config `env`, plus `MIRAGE_PROCESS`, the id of its Mirage process. Docker, Apple Container, smolvm and Microsandbox pass it on the exec command line, where other users of the host can see it in `ps`. |
| Working directory | The shell's, unchanged; one the machine lacks exits 126 |
| Disk, network, language modules | The machine's own |

## Processes and jobs

One session can run jobs on several machines at once. `jobs`, `wait`, `kill`
and `ps` ask the machines what is running, so they answer with what is true
there now. `ps` lists each program with its real pid and its machine, and what
the program started under it:

```text
    PID MACHINE                         CMD
4194305 mirage                          ps
     13 docker:box                      python3 train.py
     19 docker:box                      sleep 300
     13 ssh:gpu                         python3 eval.py
```

`ps -o pid,machine` selects those columns, and `ps f` draws each command
under its parent's. `$!` is the program's real pid, and `STAT` is what the
machine reports, `T` for a program `kill -STOP` paused.

`kill` sends a signal to a program as you sent it: a program that traps `USR1`
runs on, and one that `TERM` ends exits with its own status, which `wait`
reports. KILL is sent only when you ask for it (`kill -9`, `timeout -k`) or
when Mirage shuts the workspace down.

Mirage's own commands have pids from 4194305 up. A pid two machines both have
is refused as an ambiguous job spec, so name the machine with `-m`, as `ps`
shows it or without the provider: `kill -m box 13` or `wait -m ssh:gpu 13`. All
of this follows the session's `processes` grants.

## Machine states

| State | Means |
| --- | --- |
| `managed` | Mirage sees and stops every process its programs start there. The workspace's own host is always `managed`. |
| `reachable` | Mirage reached it, but sees and stops only what it started itself. The machine lacks `/proc`, `sh`, `tr` or `grep`. |
| `unreachable` | The last check failed. |

Mirage finds a run's processes by `MIRAGE_PROCESS` in `/proc`, so it misses
one that drops the variable or whose `/proc` entry it cannot read, such as a
process of another user.

`GET /v1/workspaces/{id}/machines` checks every machine, and
`GET /v1/workspaces/{id}/machines/{machine}` checks one and lists its
processes. `{machine}` is the id `ps` shows, `provider:name` such as
`docker:box`; a bare name answers 400. `mirage workspace list-machines -w ID`
prints each machine and its state.

## The machine image

Every machine needs a POSIX shell at `/bin/sh` and `grep`. E2B and Daytona
also need `dd` and `base64`, which carry a program's output back. With
[libfaketime](https://github.com/wolfcw/libfaketime) in the image, programs
see the workspace's [`system_time`](/home/configuration#system-time). With
`mount_type: ssh` the machine also needs `sshfs`, and a machine that runs its
own Mirage needs `fuse3` and Mirage.

The repository's Dockerfile builds an image with `fuse3`, Mirage and
libfaketime for every provider. It has no `sshfs`: add it for
`mount_type: ssh`.

```bash
docker build -f docker/sandbox/Dockerfile --target fuse \
  --build-arg MIRAGE_EXTRAS=s3,postgres -t mirage-fuse .
```

Leave out `MIRAGE_EXTRAS` for every mountable backend. Add the programs your
captures need, such as Node.js for `node`.

## Timeouts

`command_limits` apply to a program on a machine as to any command: a line
past its `timeout_seconds` exits 124, and `max_bytes` and `max_lines` cap its
output.

A timeout sends TERM, then KILL a second later, to every process of that run,
and gives up after 5 seconds if the machine stops answering. That needs
`/bin/sh`, `tr`, `grep` and `/proc` on the machine.

<Warning>
  In TypeScript, a Daytona command keeps running after a timeout, and a
  Daytona sandbox has no timeout of its own, so it keeps billing. Use the
  provider's own limits for anything that must not outlive a timeout.
</Warning>
