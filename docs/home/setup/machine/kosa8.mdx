The `kosa8` machine provider runs the programs it captures in a
[kosa8](https://kosa8.com) sandbox, a microVM reached through kosa8 Cloud's
API. Leave out `sandbox_id` and Mirage starts a sandbox when the first
program needs one, lets it sleep when the workspace has no work there, and
deletes it when the workspace is deleted. Give `sandbox_id` and Mirage runs
programs in your sandbox and leaves its lifetime to you. Python and Node.

## Installation

Nothing to install: the machine calls kosa8's REST API with the HTTP client
Mirage already has. Set `api_key` in the config, as a value or a
[credential pointer](/home/service-credentials#pointer-fields), or
`KOSA8_API_KEY`. Set `api_url`, or `KOSA8_CLOUD_URL`, to reach a kosa8 Cloud
other than `https://api.kosa8.com`.

## Usage

`captures` defaults to [`@external`](/home/setup/machine/overview#captures):
every program Mirage does not have itself. Name `@python` to run
Python in the sandbox too. Without `sandbox_id`, the first program starts
the sandbox; Mirage's own commands start none.

## Network

Programs on a machine connect from that machine, so Mirage's own
[`network`](/home/configuration/workspace#network) lists and
[`pre_network`](/home/policy/network) policies do not see them. A kosa8
machine takes lists of its own, which kosa8 enforces inside the sandbox:

| Setting | Programs on the sandbox reach |
| --- | --- |
| `network: false` | Nothing. |
| `network: true` | Anything. |
| `allowed_domains: [...]` | Only what the list names. |
| `denied_domains: [...]` | Anything but what the list names. A denied entry wins over an allowed one. |
| none of them | Whatever the sandbox's own policy, or your kosa8 organization's, allows. |

An entry is a host (`pypi.org`), a wildcard (`*.github.com`), an IPv4
address or an IPv4 range (`10.0.0.0/8`); `*` is every host. kosa8 does not
take ports or IPv6, so an entry with a `:` is refused when the machine is
built rather than widened. A denied name is refused at DNS; an allow list
is the boundary.

A sandbox Mirage starts has the policy from boot. A
sandbox you bring gets it each time the workspace connects, replacing the
one it had; leave the settings out to keep the sandbox's own.

```yaml
machines:
  sandbox:
    provider: kosa8
    allowed_domains: ["*.github.com", pypi.org, files.pythonhosted.org]
    denied_domains: [gist.github.com]
    secrets: [GITHUB_TOKEN]
```

`secrets` names [kosa8 secrets](https://kosa8.com/docs) to broker into a
sandbox Mirage starts. A program there sees a placeholder in place of the
value, and kosa8 puts the real value in only on requests to the host the
secret is bound to, so the program never holds the key.

## A sandbox Mirage starts

Without `sandbox_id`, the first program that needs the sandbox starts one
from `template` (kosa8's `base` when unset) or from `image`, an OCI image
booted cold. The sandbox carries the label `mirage_machine: <name>`. The
workspace keeps its ID in its state, so a later build of the same workspace
reaches the same sandbox, and one that is gone is started anew.

Once nothing has run there for `idle_timeout` seconds, 60 when unset, kosa8
puts the sandbox to sleep: its disk and memory are kept and its compute is
not billed. kosa8 counts a sandbox with a busy process as working, so a long
program keeps it awake. The next line wakes it, usually in under a second.
Closing the workspace puts the sandbox to sleep; deleting the workspace
deletes it.

```yaml
machines:
  sandbox:
    provider: kosa8
    template: base
    idle_timeout: 300
```

## A sandbox you bring

Create the sandbox with the kosa8 CLI, the dashboard or an SDK, and pass its
ID as `sandbox_id`. Mirage never deletes your sandbox. A sleeping sandbox
wakes on the next line. Closing the workspace leaves the sandbox as it is.

To put the sandbox to sleep when the workspace pauses, set `on_pause: pause`
on the machine:

```yaml
machines:
  sandbox:
    provider: kosa8
    sandbox_id: ${KOSA8_SANDBOX_ID}
    on_pause: pause
```

`template`, `image`, `idle_timeout` and `secrets` apply only to a sandbox
Mirage starts, so the machine refuses them beside `sandbox_id`.

Once the sandbox is deleted, a line exits 1, and its error names the fix:

```text
sandbox sbx_123 is not running: it was deleted or never existed; create a new sandbox and set the machine's sandbox_id to it
```

A line that is running when the sandbox goes, or when kosa8 cannot be
reached, exits 129. The next line connects again.

## Connecting the workspace

kosa8 takes no `mount_type`. Put the files the programs need in the sandbox
yourself, or pass them in on stdin.

## Notes

- Output comes back as the program wrote it, binary included, with stdout
  and stderr apart.
- kosa8's exec takes no stdin. Piped input is uploaded to a file in
  Mirage's folder on the sandbox, which the program reads as its stdin and
  which is removed once open. So the program starts once its input has
  ended: a line whose input never ends never starts, and one whose input
  passes 64 MiB fails with exit 126. Without piped input, stdin reads as
  empty.
- kosa8 takes an argv of at most 256 words of at most 8,192 characters
  each. A longer line, or one with many variables, is uploaded as a script
  the same way and runs unchanged.
- kosa8 keeps a command running when its stream ends, so Mirage stops a
  cancelled line, a [timeout](/home/setup/machine/overview#timeouts) or a
  `kill` by the line's own tag: every process of that run.
- Commands run concurrently, each with its own input and output.
- The `base` template is Alpine, with BusyBox and no `bash`. Use `image`
  for a Debian or Ubuntu userland.
- Sizing, regions, snapshots and forks stay kosa8 settings.
