## Credentials

The resource reads a Unity Catalog volume over the Databricks Files REST API.
It needs two things, and they are supplied separately: a workspace **host**,
which is configuration, and a **bearer token**, which reaches the resource
through a token provider your program writes.

The config never holds a credential, so nothing is redacted in a snapshot and
nothing leaks into a config file.

### 1. Get Your Workspace Host

Your workspace URL, e.g. `https://dbc-xxxxxxxx-xxxx.cloud.databricks.com`
(AWS) or `https://adb-xxxxxxxxxxxx.xx.azuredatabricks.net` (Azure).

### 2. Create a Personal Access Token

1. In the workspace, open **Settings** -> **Developer** -> **Access tokens**.
1. Click **Generate new token**, set a comment and lifetime, and copy it.

### 3. Set Environment Variables

```bash
# .env.development
DATABRICKS_HOST=https://dbc-xxxxxxxx-xxxx.cloud.databricks.com
DATABRICKS_TOKEN=dapi...
```

Your program reads these; MIRAGE does not. It takes the host as config and the
token from the provider you hand it.

### Beyond a personal access token

MIRAGE ships one provider, `StaticTokenProvider`, for a token you already
hold. Anything that mints, refreshes or exchanges a credential (OAuth
machine-to-machine, on-behalf-of a signed-in user, a `~/.databrickscfg`
profile) is application code implementing the same one-method interface. See
the [Python](/python/setup/databricks) and
[TypeScript](/typescript/setup/databricks_volume) setup guides for worked
providers.

MIRAGE calls the provider before each Files API operation, never caches or
refreshes the token, and never retries a 401. Caching and refresh belong to
the provider, which is the only party that knows how its credential is minted.
