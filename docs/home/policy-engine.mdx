The admission gate that [Permissions](/home/permissions) describes
declaratively is one client of a general mechanism: the **policy
engine**, an ordered stack of `Policy` objects the workspace consults at
every state-changing surface. It answers two questions for everything a
session touches (files, commands and CLIs, variables, processes):

1. **Does it exist for this session?** A hidden path, variable, process
   or command is absent: `ENOENT`, missing from every listing, `command
   not found`, unset. The session's visibility answers this, through the
   views and the built-in hide, before any policy is asked.
2. **May the session do this?** Every policy answers in its own words:
   refuse, ask a host, place the line on a runtime, or bound the result.

A `Policy` is one concern's answers to the workspace lifecycle. It
overrides only the hooks it cares about, answers an action to state an
opinion or nothing to stay silent, and a hook that raises fails closed:
the command or op is refused, naming the policy.

```python
from mirage import Workspace
from mirage.policy import CommandContext, Deny, Policy

class NoForcePush(Policy):
    async def pre_command(self, ctx: CommandContext) -> Deny | None:
        if ctx.program[:2] == ("git", "push") and "--force" in ctx.argv:
            return Deny("force pushes go through an operator")
        return None

ws = Workspace(mounts, policies=[NoForcePush()])
```

```typescript
const noForcePush: Policy = {
  async preCommand(ctx) {
    if (ctx.program?.[0] === 'git' && ctx.program?.[1] === 'push' &&
        ctx.argv.includes('--force'))
      return { kind: 'deny', reason: 'force pushes go through an operator' }
    return null
  },
}
const ws = new Workspace(mounts, { policies: [noForcePush] })
```

More arrive later through `ws.policies.add(...)`. Hooks left
un-overridden are detected at the seam and never called, so an empty
policy costs nothing.

## The six hooks

Each hook fires on one plane, and each accepts a fixed set of answers:
returning a kind the hook cannot carry is a loud `PolicyError`, never a
silent allow.

- **`pre_command`**: once per classified command, before it runs. The
  `CommandContext` carries the name, the raw `argv`, every path the
  line names (`paths`, with `operands` alone beside it for rules that
  read a slot by position), the admission `tokens` with their `program`
  head (a CLI's verb path canonicalized), the cwd, and the session and
  agent ids. May answer **Deny or Ask**.
- **`pre_execute`**: once per typed line, after the line clears
  admission and before it runs. The context is the `RouteContext` a
  [route policy](/home/route-policy) reads: the line, its commands and
  their paths, the cwd, env, session and agent. May answer **Deny or
  Route**. The workspace's `route_policy` answers here as a built-in,
  ahead of the policies registered in code. Nested lines (`$()`,
  `eval`, `source`, `xargs`) keep the placement of the line that ran
  them.
- **`pre_ops`**: once per VFS op at the op doors (the dispatcher and
  the `ws.vfs` facade, which is also how FUSE, the runtime guests,
  `find -delete` and the warm cache arrive) and on the command tier's
  backend I/O, before any backend or cache read. The op is named per
  door, so a portable policy keys on `write` and `path`. May answer
  **Deny**, which the doors raise as `EACCES`, or **Ask**, which a door
  puts to the host only when no line is running behind the op (a file
  tool, the host's own `session.vfs` call) and refuses inside one,
  since the line was admitted without it. This is the hot path,
  thousands of ops under one recursive command, so keep it cheap;
  expensive decisions belong at `pre_command` or precomputed into
  policy state. A denied directory reads like a mode-000 one: it still
  lists and stats, and a walk (`find`, `du`, `ls -R`, `grep -r`)
  reports `Permission denied` for it. A command you register yourself
  and that reads its accessor directly never reaches a door, so this
  hook never sees those reads; that handler is trusted host code.
- **`pre_session`**: once per session-state write, before it lands.
  `export`, a plain assignment, `${X:=default}`, `$((X=5))` and
  `printf -v` all clear the same gate, because every writer goes
  through `SessionView.set`. The context carries a key, never a
  pseudo-path, so a path-scoped rule cannot match one by accident. May
  answer **Deny**.
- **`post_ops`**: one completed op at the doors. A **Deny** suppresses
  the result; a **Limit** caps a byte-producing one.
- **`post_execute`**: one finished `execute()` line. A **Limit**
  returned here merges with every other opining policy's and caps the
  line's output at the workspace boundary. This caps the whole response,
  on top of each command's own `command_limits`.

## The answers

- **Silence** (`None`/`null`): no opinion, the next policy speaks.
- **`Hide`** is the built-in's alone: the op answers as absent
  (`ENOENT`) before any other policy is asked, and leaves no record. No
  surface ever names a hide, `explain` included.
- **`Deny(reason, scope)`**: with the default `COMMAND` scope the line
  reads `<command>: Permission denied` at exit 126, bash's own wording,
  and the reason travels as the result's `refusal` record
  (`kind: deny`, the reason, the policy's class name, the scope); the
  `OPERAND` scope keeps the GNU operand voice instead: the command's
  own line for an operand it may not open, at its operand exit code
  (`cat: /vault/aws.token: Permission denied`, exit 1), the reason
  again on the record. Exit codes derive from the plane and the scope,
  never from a number a policy returns. At the op and session doors a
  Deny is `EACCES` (`<NAME>: permission denied` for a session write),
  and the reason rides the raised `PolicyDenied`'s `refusal` and the
  line's record. A surface that hands the agent text appends the record
  as one line, `policy denied: <reason>`.
- **`Ask(reason)`** (`pre_command`, and `pre_ops` where no line is
  running): the line or the op does not run, the agent reads
  `Permission denied` with a `pending` refusal record naming the ask id,
  and the question lands in `ws.decisions` for a host to answer: the
  same ledger, `on_ask` handler, CLI and REST doors as a profile's `ask`
  rules; see [Asks](/home/permissions#asks).
- **`Route(runtime)`** (`pre_execute` only): the named runtime serves
  every command it captures on the line, as a route policy's verdict
  naming it does.
- **`Limit(max_bytes, max_lines, timeout_seconds, on_exceed)`**: a
  bound on a result. Every opining policy's limits merge to the
  tightest value per field.

Answers rank **by kind**, not by who registered first: a Hide outranks
everything, then a Deny, then an Ask, then a Route or a Limit. So a
later policy's Deny is never re-opened as a question, an approval never
re-opens a refusal, and a Deny at `pre_execute` refuses the line
whoever placed it. Two Routes that name different runtimes refuse the
line (`policies place the line on different runtimes: ...`), since
neither choice is the line's.

## The stack and its order

Within one kind, registration order picks which answer shows: the
first Deny's reason is the one the agent reads. The order is the
tie-breaker, not the security model: a policy can only tighten the
workspace, never loosen it.

The registry seeds two built-ins ahead of everything: `MountRootPolicy`
(mount-root semantics are mount semantics: the POSIX `EBUSY` rules for
`rm`/`rmdir`/`mv`/`mkdir`/`touch`/`ln` on a mount root, and the refusal
to read one whole into an archive or copy) and `OutputCapPolicy` (the
per-command output caps, fed the per-mount overrides). The workspace
follows with the profile pair, `PermissionsPolicy`, reading each
session's compiled [profile](/home/permissions), and `ScriptPolicy` for
profile policies, the `policy:` file a profile names, then `policies=`
in list order, then anything added later through `ws.policies.add()`.
At `pre_execute` the workspace's `route_policy` answers first, as
`PlacementPolicy`; at `pre_ops` the hide answers before every policy and
the mount mode (`MountModePolicy`) after them.

A policy that raises does not fail open: the loop answers a Deny naming
the policy and the error is logged. The route policy is the one
exception: a mistake in it (an unknown runtime, a verdict it cannot
parse) is the deployment's to fix, so it raises to the caller as it
always has.

## One line, its judgments

A typed line clears them in a fixed order:

1. **Syntax.** An unparsable line exits 2 and no policy is consulted.
2. **Admission.** Every command in the line is judged before any of it
   runs, so a rule-refused line never runs halfway, and a line the rules
   refuse is never placed: no placing policy, route script included,
   ever sees it.
3. **Placement.** `pre_execute` places the line: the route policy, then
   the coded policies, then each runtime's own `script:` when nothing
   placed it. A Deny refuses the line whole, at exit 126.
4. **Execution.** Each command clears its own gate where it runs, which
   reads the values the runtime expanded. A whole line handed to a
   runtime clears the same per-command gate before the runtime sees a
   byte of it. Each VFS op clears `pre_ops`, including ops a routed
   runtime performs against the mounts, every env write clears
   `pre_session`, and the finished line is bounded by `post_ops` and
   `post_execute`.

## What a profile compiles to

A [profile](/home/permissions) compiles once per session into three
parts, and nothing else reads the session's rules:

- **Setup**: the `cwd` and `env` a session starts with.
- **Visibility**: `paths` (hide and show), `vars`, `processes.list` and
  `commands.allow`, which say what exists. The views (listings, globs,
  walks, command lookup, `env`, `ps`) filter through it, and the op
  doors answer a hidden path as absent.
- **Policies**: the mount modes, the `commands` rules (as
  `PermissionsPolicy`), the profile's `policy:` script (as
  `ScriptPolicy`), `command_limits` and `processes.max`.

A rule is **POSIX level** when it names paths and no command (`deny:
[{paths: ["/vault/*"]}]`): it holds at every door, a command's or an
op's. A rule that names a command, or no path, is **command level**: it
holds where a line is judged.

## Which door enforces what

| Door | Command level: `commands.allow`, rules naming a command, `pre_command`, `pre_execute` | POSIX level: hides, path rules, mount modes, `pre_ops` / `post_ops` |
| --- | --- | --- |
| `ws.shell`, `session.shell`, the `shell` / `ls` / `grep` tools, `ssh ws@host [cmd]`, codex-exec commands | yes | yes |
| The `read` / `write` / `edit` / `glob` tools, `ws.vfs`, `session.vfs`, FUSE / FSKit, `sftp` / `scp`, codex-exec file ops, a runtime guest's own file ops | no | yes |

A door that sees only ops warns at startup about the command-level rules
it skips. The agent tools follow the same profile: each session's tool
list is derived from it, so a door never offers a tool every call of
which would be refused. `shell` needs a command the allow list installs,
`ls` and `grep` need those commands, `write` and `edit` need somewhere
the session may write; `session.tools.names()` is the list, and MCP,
RPC and the agent adapters offer exactly it. A path rule that asks is
put to the host from a file tool too, keyed by the rule and the path:
an `allow` once covers one tool call, every op it makes on that path.

## Scripts by job

Scripts come in two jobs, and each job runs one way:

- **Policy scripts judge.** A profile's `policy:`, the workspace's
  `route_policy` and a runtime's `script:` answer a question about a
  line, a command, an op or a write. They run on the workspace's
  evaluator runtime, see a `ctx` payload, and answer with data. Each
  evaluation is bounded by one timeout, 10 seconds, after which the
  judged line is refused (or, for a route policy, fails).
- **Program scripts run as the session.** A script CLI (`clis:`) is a
  program: it runs as the session, so everything it does is judged like
  any line the agent types.

## Dry runs

`ws.explain(line, session_id)` (`session.explain(line)` on a session's
handle, the same names in TypeScript) runs the gates without running the line: one `Explanation` per
command with the exact `exit_code` and `stderr` the agent would see,
every policy's answer to the command (`answers`), every answer at
`pre_execute` (`placement`) and the runtime that would serve the
command (`runtime`). `ws.explain_op(op, path, session_id)`
(`ws.explainOp` in TypeScript) is the single-op form, for the doors that see ops and no command. A hide is
never among the answers; see [Dry runs](/home/permissions#dry-runs).
