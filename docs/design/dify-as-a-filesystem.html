Mirage · backend design, explained

Why a Dify Knowledge Base
can be a filesystem

A knowledge base is not stored as files. So how does an agent get to run cat, grep, and find on it? The trick is that a filesystem is an interface, not a place. Anything that can answer three questions can wear it.

filesystem  =  list  +  read  +  stat

1 · The contract 2 · The mapping 3 · Folders from slugs 4 · Reading = reassembly 5 · Live terminal 6 · grep vs search

Step 1

A filesystem is an interface, not a storage medium

"Filesystem" does not mean "bytes on a disk." It means a small contract of questions a thing can answer. Every shell tool you know is built on just these three. So the real question for any backend is never "is it a filesystem" but "can it answer list, read, and stat?"

question 1

list

Given a directory, what are its children?

powers: ls · tree · find
question 2

read

Given a file, hand me its bytes.

powers: cat · head · grep
question 3

stat

File or directory? What size, type, and time?

powers: stat · ls -l · wc
Mirage's whole premise (mount anything) is this: implement list / read / stat once per backend, and every shell tool, plus every AI agent that already speaks shell, comes along for free.

Step 2

What Dify gives us to answer those questions

A Dify Knowledge Base, stripped down, is a dataset holding a flat list of documents, where each document is split into segments (the chunks Dify embeds for retrieval). That is exactly enough structure to fill in the contract.

Filesystem conceptDify reality
the mount / rootthe dataset dataset_id
a filea document (one PDF, page, or markdown file ingested)
a file's bytesits segments, fetched and rejoined with \n
the path to a filea slug in the document's doc_metadata (e.g. guides/quickstart)
a directoryinferred from common slug prefixes (no real folder exists)
stat (size / time / type)document fields: upload size, created_at, always TEXT
So "read a file" literally means: fetch that document's segments and glue them back together. The file is reconstructed on demand. It is not sitting anywhere as a contiguous blob.

Step 3 · the one genuinely hard part

Folders conjured from a flat list

Dify has no folders. Documents are a flat list. A filesystem is a tree. The bridge: each document carries a slug, and directories are derived from the prefixes those slugs share. Toggle documents below and watch the tree rebuild. This is the same move S3 makes with object keys.

Step 6

    
The bonus Dify gives that a disk cannot

    
A real disk can only match exact bytes. Dify can match meaning. So this backend keeps the POSIX tools for literal matching and adds one extra command, search, that exposes Dify's native vector retrieval through the same paths.

    

      

        exact
        
grep

Calls Dify's /retrieve endpoint: embeds your query, ranks segments by semantic similarity, returns them with scores.

        
    
          
  • Finds "rate limited to 100/min" when you ask about throttling.
    • 
          
  • search "how am I throttled?" /knowledge
    • 
          
  • Path scope becomes a metadata_filtering condition on the slug.
    • 
        

      

    

    
This is the inverse of the usual problem. Instead of forcing Dify into the filesystem box, the backend surfaces Dify's superpower through the box: ranked semantic retrieval, addressable by path.

  






  

    
The one-line answer. Dify can be a filesystem because a filesystem is just list + read + stat, and a Dify dataset can answer all three: documents are files, segments are their bytes, slug metadata is the path, and directories are faked from shared prefixes, the same way S3 fakes them from object keys.
