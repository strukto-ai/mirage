Goal: Turn the per-command timeout safeguard from a best-effort report into a guarantee that actually stops work, and extend its coverage to the paths it currently misses (stderr, cross-mount, dry-run, VFS ops, whole-pipeline).

Architecture: The safeguard stays a per-mount, per-command CommandSafeguard resolved by resolve_safeguard. We do not change the resolution model. We harden the enforcement points and widen where resolution is consulted. One new construct (a job-level budget) is added as a separate layer above the per-command safeguard, not folded into it.

Tech stack: Python 3.12, asyncio, pytest, pydantic. Run tests with ../../../python/.venv/bin/python -m pytest from python/. Lint with ./python/.venv/bin/pre-commit run --files <changed> from repo root.

Background: how the safeguard works today

Two enforcement paths, because a command is either a builtin (eager, returns bytes) or a streaming mount command (lazy async generator):

  • Builtins are wrapped whole in command_dispatch.py execute_command: await asyncio.wait_for(body, timeout).
  • Mount streams are wrapped at the byte level in command.py handle_command via with_timeout(stream, seconds, cmd), which budgets the whole stream with a monotonic clock.
  • Both raise CommandTimeoutError, caught once in workspace.py, surfaced as exit 124.

Resolution (safeguard.py resolve_safeguard(name, command_default, mount_override)) is three layers: per-mount override → per-command default (@command(safeguard=...)) → built-in fallback table (5 commands carry max_lines=2000; everything else gets FALLBACK_SAFEGUARD with timeout_seconds=600). The full three-layer resolve only happens on the single-mount command path (mount.py:456); every other call site passes the name only.

Cross-cutting invariant: streaming (lazy) exit codes

A streaming command does not know its exit code when its handler returns. grep with no matches should exit 1, but it returns a lazy async generator with a provisional io.exit_code = 0; the real code is set only when the stream is fully drained (exit_on_empty stamps it on the source IOResult), and sync_exit_code() walks the _stream_source chain to pull it after materialization. The timeout wrap, truncation, and pipeline teardown all sit in the gap between stream creation and materialization, so every task that touches a stream must preserve this. These invariants are currently untested and must get explicit tests.

The two helpers (used by Tasks 1, 4, 5, 6)

# in mirage/commands/builtin/utils/safeguard.py, next to with_timeout
def maybe_with_timeout(stream, safeguard, command):
    """Wrap a byte STREAM with a timeout if the safeguard calls for one,
    else return it untouched. Single source of the 'should I wrap' rule."""
    if stream is None or isinstance(stream, bytes):
        return stream
    if safeguard is None or not safeguard.timeout_seconds:
        return stream
    if safeguard.timeout_seconds <= 0:
        return stream
    return with_timeout(stream, safeguard.timeout_seconds, command)

async def run_with_timeout(coro, seconds, name):
    """Wrap a COROUTINE (eager builtin, dry-run, or VFS op) with a deadline."""
    if not seconds or seconds <= 0:
        return await coro
    try:
        return await asyncio.wait_for(coro, timeout=seconds)
    except asyncio.TimeoutError as exc:
        raise CommandTimeoutError(name or "?", seconds) from exc

Task 2 · Cancellation-safety harness and handler audit P0 foundation

asyncio.wait_for cancels by throwing CancelledError into the inner coroutine. If a handler swallows it, or holds a raw socket / sync cursor / backend client, the timer fires but the work leaks. Today nothing proves cancellation is clean. We build that proof first, then fix whatever fails it.

Create: python/tests/workspace/test_cancellation_safety.py · python/tests/workspace/_cancel_probe.py (a reusable probe handler/resource) · Modify: the leaking handlers found by the audit (unknown until Step 3)

Phase A: build the objective check

Step 1. Write the probe. A fake async resource that records open/close, and a handler that acquires it then awaits forever. Two probe variants: one that re-raises CancelledError (good citizen), one that swallows it (the failure we want to catch). 
class Probe:
    def __init__(self): self.opened = False; self.closed = False
    async def __aenter__(self): self.opened = True; return self
    async def __aexit__(self, *a): self.closed = True

async def good_handler(probe, stop):
    async with probe:
        await stop.wait()        # cancelled cleanly, __aexit__ runs

async def leaky_handler(probe, stop):
    probe.opened = True
    try:
        await stop.wait()
    except asyncio.CancelledError:
        return None              # SWALLOWS cancel, never closes
Step 2. Write the assertion harness. Run a handler under asyncio.wait_for(..., 0.1), then assert: (a) CommandTimeoutError raised, (b) probe.closed is True, (c) no pending tasks remain (asyncio.all_tasks() back to baseline). This is the pass/fail signal. 
async def assert_clean_cancel(handler, probe):
    stop = asyncio.Event()
    with pytest.raises(asyncio.TimeoutError):
        await asyncio.wait_for(handler(probe, stop), timeout=0.1)
    await asyncio.sleep(0)        # let __aexit__ / finally run
    assert probe.closed, "resource leaked on cancel"
    assert not _extra_tasks(), "task leaked on cancel"
Step 3. Prove the harness discriminates. good_handler passes, leaky_handler fails.

Task 3 · Honor per-mount overrides on cross-mount and fan-out P1

def _tightest(mounts, cmd_name):
    timeouts = []
    for m in mounts:
        sg = resolve_safeguard(cmd_name, None, m.command_safeguards.get(cmd_name))
        if sg and sg.timeout_seconds and sg.timeout_seconds > 0:
            timeouts.append(sg.timeout_seconds)
    return min(timeouts) if timeouts else None

Task 6 · One stage ending ends the whole pipeline P2 new feature

Decision (per review): any stage ending, whether by timeout or by finishing early, tears down the entire pipeline, including any still-producing upstream streaming stage. The clean way to get this is to enforce a single deadline around the whole-pipe consumption rather than per-stage bookkeeping. Because mirage pipes are one consumer pulling a chained set of async generators (head pulls grep pulls cat), one wait_for around the final materialize makes expiry unwind the entire chain through the pipe's existing finally that aclose()s intermediate streams. This composes with per-command timeouts as "first to fire wins": the pipeline budget can only end things sooner, never extend a stage past its own limit.

Create: python/mirage/shell/job_budget.py (a small monotonic budget object) · Modify: python/mirage/workspace/executor/pipes.py (handle_pipe, wrap the final consumption) · Test: python/tests/workspace/test_pipeline_budget.py

The hard part: the streaming-bytes case

"Tear down the pipeline" is easy to claim and hard to prove for chained async generators. The pipe's finally already calls close_quietly → aclose() on every intermediate stream, but aclose() only stops a producer that honors GeneratorExit / cancellation. A cat mid-fetch on a 2GB S3 object that ignores GeneratorExit keeps downloading after we declared the pipeline done. So the test must assert the producer actually stopped, not just that the consumer stopped reading. This is the producer-side of Task 2 and depends on it.

Note the builtin asymmetry: a builtin stage returns bytes eagerly and fully completes under its own wait_for before passing them on, so it can never be "mid-stream." Only streaming (async-generator) stages need the producer-teardown check. The test matrix must include both a builtin stage and a streaming stage in the same pipe.

Verify (not a confirmed bug) · Cache integrity on early-exit streams P2 verify

An audit flagged possible cache poisoning when a stream is partially consumed by timeout or truncation. On inspection it is mostly not a bug, but it needs two assertions to lock it down:

  • Truncation does not poison: CachableAsyncIterator.drain() returns buffer + remaining (cachable_iterator.py:55-66), so the background drain spawned by apply_io caches the full file even after apply_safeguard truncates the visible output. Surprising-but-correct: cat big | head still drains the whole object into cache in the background. Add a test asserting the cached bytes equal the full file, not the truncated prefix.
  • Timeout does not write a partial entry: on CommandTimeoutError, apply_io at workspace.py:694 is never reached (it sits after the raise), so no cache write happens. Add a test asserting a timed-out streaming read leaves no cache entry for the path.
  • Residual to check: apply_io spawns _background_drain on an un-exhausted iterator (io.py:45-51) while _record_execution later materializes the same stdout. Confirm these two do not consume the same _source concurrently (which would interleave chunks and corrupt the cache). This race is pre-existing and not introduced by the timeout work, but the wrap changes stdout identity so it is worth a targeted test.

No code change expected unless the residual race reproduces. This task is two regression tests plus one investigation.

Risks

  • Task 2 is open-ended. The audit may surface many leakers across backends. Mitigate by committing per-backend and letting the locked-in registry test catch the rest incrementally.
  • Hot-path cost. Task 5 wraps the VFS op path (every FUSE read) and Task 6 wraps pipeline consumption. Both stay off when unconfigured (run_with_timeout short-circuits on a falsy timeout); benchmark the configured path before enabling broadly.
  • Producer teardown (Task 6). "End the whole pipeline" only works if streaming producers honor GeneratorExit on aclose(). The Step 3-4 tests will expose any producer that ignores it; those are fixed the same way as Task 2 and are a hard prerequisite.
  • Behavior change on overrides (Task 3). Users currently relying on the accidental 600s fallback for cross-mount ops will see their configured (shorter) limits take effect. This is the intended fix; call it out in the PR body.
