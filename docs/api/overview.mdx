The Mirage HTTP API creates workspaces, runs shell commands and reads or writes
files. Routes are under `/v1`. The local daemon runs on Python or TypeScript.
The hosted API serves the subset marked **Daemon and hosted** in the reference.
Shared routes use the same request and response bodies on both hosts.

<Note>
Embedding Mirage in a Python or TypeScript program? Use the library instead:
it runs the same workspaces in process, with no server. See
[Python](/python/quickstart) or [TypeScript](/typescript/quickstart).
</Note>

## Where it runs

| Host | Base URL | Routes |
| --- | --- | --- |
| Hosted API | `https://api.strukto.ai` | Rows marked **Daemon and hosted** in the reference, plus the hosted API's own account routes |
| Local daemon | `http://127.0.0.1:8765` by default | Every route in the [reference](/api/reference) |

The `mirage` CLI starts a daemon on the first command that needs one. To run
one from code, see [Launch a server](/home/access/http#launch-a-server).

## Resource groups

**Workspaces** contains lifecycle operations, shell execution, VFS file operations,
documents and asks. These operations create workspaces or act within one.

**Saved configurations** contains reusable VFS, CLI and runtime definitions. They
exist independently of a workspace. For example, Workspaces → VFS reads and writes
files; Saved configurations → VFS manages backend configurations to use in mounts.
Templates describe whole workspace configurations. Policies manage reusable rules.

## Contract

- [API reference](/api/reference): endpoints, searchable and filterable
  by resource.
- [`openapi.yaml`](https://github.com/strukto-ai/mirage/blob/main/docs/openapi.yaml):
  the OpenAPI document the reference is generated from. Both servers are
  checked against it in CI.
