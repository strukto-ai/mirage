`GmailVFS` browses labels, messages, and attachments via the Gmail API.

Both runtimes share the same OAuth config: a Google Cloud `clientId` / `clientSecret` plus a long-lived `refreshToken` for the user. Setup steps live at [Google Workspace Credentials](/home/setup/google).

## Node

```bash
pnpm add @struktoai/mirage-node
```

```ts
import { GmailVFS, MountMode, Workspace } from '@struktoai/mirage-node'

const gmail = new GmailVFS({
  clientId: process.env.GOOGLE_CLIENT_ID!,
  clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
  refreshToken: process.env.GOOGLE_REFRESH_TOKEN!,
})

const ws = new Workspace({ '/mail': gmail }, { mode: MountMode.READ })
await ws.shell('ls /mail/INBOX/')
```

## Browser

```bash
pnpm add @struktoai/mirage-browser
```

```ts
import { GmailVFS, MountMode, Workspace } from '@struktoai/mirage-browser'

const gmail = new GmailVFS({
  clientId: GOOGLE_CLIENT_ID,
  clientSecret: GOOGLE_CLIENT_SECRET,
  refreshToken: localStorage.getItem('gmail.refresh_token')!,
})

const ws = new Workspace({ '/mail': gmail }, { mode: MountMode.READ })
```

For OAuth in a browser, prefer PKCE so secrets stay off the page; the [Google setup guide](/home/setup/google) shows the flow.

| Field | Description |
| --- | --- |
| <code style={{ whiteSpace: 'nowrap' }}>accessToken</code><br />secret | OAuth access token, or a function (sync or async) that returns one. Takes precedence over `clientId` and `refreshToken`. |
| <code style={{ whiteSpace: 'nowrap' }}>clientId</code> | Google OAuth client ID. Required with `refreshToken` when `accessToken` is unset; mirage then mints and renews access tokens itself. |
| <code style={{ whiteSpace: 'nowrap' }}>clientSecret</code><br />secret | Google OAuth client secret, sent with the refresh-token grant. Omit it for a PKCE client. |
| <code style={{ whiteSpace: 'nowrap' }}>refreshToken</code><br />secret | User's OAuth refresh token. Required with `clientId` when `accessToken` is unset. |
| <code style={{ whiteSpace: 'nowrap' }}>refreshFn</code><br />secret | Function that exchanges the refresh token for `{ accessToken, expiresIn }` instead of Google's token endpoint, so the client secret can stay on a backend. Still needs `clientId` and `refreshToken`. |
| <code style={{ whiteSpace: 'nowrap' }}>apiBase</code> | One base URL that replaces every Google API host and the OAuth token endpoint, such as a test server. Unset uses Google's hosts. |
| <code style={{ whiteSpace: 'nowrap' }}>walkLimit</code><br />default `1000` | Most files one command walks under a folder: `grep -r`, `find` and other walks stop there, and a larger glob, `tar -c`, `cp -r` or `rm -r` is refused. `-1` lifts the limit, and the listing then keeps no message text. |

Fields marked secret are redacted in snapshots.

    #### `/<path>` layout

    ```text
    /<path>
      <label>/
        <yyyy-mm-dd>/
          <subject>__<message-id>.gmail.json    # email JSON file (the email itself)
          <subject>__<message-id>/              # attachments dir, only if any
            <attachment-filename>

      Email body is in the .gmail.json file. The sibling dir holds attachments
      only. Read with `cat`/`head`/`jq` on `<path>.gmail.json` (keep the suffix).

      Path: <label>/<yyyy-mm-dd>/<subject>__<message-id>.gmail.json
        <label>       Gmail label (INBOX, SENT, DRAFT, IMPORTANT, STARRED,
                      TRASH, SPAM, or any user label)
        <yyyy-mm-dd>  date the message was received, used for date narrowing
                      (ls /<path>/INBOX/2026-05-03/ pushes after:/before: into the
                      Gmail query - much cheaper than scanning the whole label)
        <subject>     sanitized subject (don't construct it; ls the date dir)
        <message-id>  Gmail message ID

      email JSON structure (mirage-processed, NOT the raw Gmail API response):
        {
          "id": "...",
          "thread_id": "...",
          "from":    { "name": "...", "email": "..." },
          "to":      [ { "name": "...", "email": "..." } ],
          "cc":      [ ... ],
          "subject": "...",
          "date":    "Mon, 3 May 2026 10:00:00 -0700",
          "body_text": "decoded plain-text body",
          "snippet":   "first ~200 chars from Gmail",
          "labels":  [ "INBOX", "IMPORTANT", ... ],
          "attachments": [
            { "id": "...", "filename": "invoice.pdf",
              "mime_type": "application/pdf", "size": 12345 }
          ]
        }

      Attachments: each message with attachments has a sibling directory at
      <subject>__<message-id>/ (same name as the .gmail.json file but without
      the extension). Cat a file inside to download bytes. grep -r over a
      date dir skips these binary files automatically.

      After a grep/rg hit, the result line points to .../<subject>__<id>.gmail.json
      — the sibling attachments dir is NOT in grep output. Once you have the
      message id (or the .gmail.json path), ls the same path with .gmail.json
      stripped to list attachments directly:
        ls /<path>/INBOX/2026-05-03/<subject>__<message-id>/
      ENOENT means the message has no attachments.

      Useful jq paths:
        .subject
        .from.email
        .body_text
        .labels[]
        .attachments[] | .filename

      To act on messages (read by id, triage, raw API calls), use the gws
      CLI if installed: gws gmail --help
    ```

    #### Supported Unix Commands for VFS

    Unix commands work on each path as on a local filesystem, as far as the path supports them:

    | Path | Supported |
    | --- | --- |
    | `/<path>` | Commands that read files (`ls`, `cat`, `grep`, `find`, `jq` and the rest). `grep -r` and `rg` use `gmail` search. |

    #### Limitations of Unix Commands for VFS

    Where a path differs from a local filesystem:

    | Path | Limitations |
    | --- | --- |
    | `/<path>` | Read only: no command changes files. `gmail` search covers only `*/*/*.gmail.json`; `grep -r` and `rg` read every other file. `grep -r`, `find` and `du` stop after 1000 files; a glob matching more, `tar -c`, `cp -r` and `rm -r` are refused. |

    Run `man` to list every command, and `man <cmd>` or `<cmd> --help` for one command's usage.

## Integration

What Gmail answers through its own API, so fewer files are read. [Integration](/home/integration/overview) explains each command.

| Command | On Gmail |
| --- | --- |
| `grep -r`, `rg` | The message text the listing keeps, for ASCII text. It misses nothing. |

The [Python Gmail docs](/python/vfs/gmail#integration) list when each search answers and what it can miss.

## Mount mode

`read`.

For the mounted layout (labels, dates, attachments) see the [Python Gmail docs](/python/vfs/gmail).
