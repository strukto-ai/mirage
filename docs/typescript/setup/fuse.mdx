title: FUSE

description: Expose a Node workspace's mounts as real folders through FUSE, FSKit or NFS.
---

A mount with a kernel `backend` also shows as a folder on the machine running
Mirage, so editors, `git` and any other program read and write it like a local
folder. The [FUSE overview](/home/setup/fuse) lists what each OS supports.
FUSE runs on Linux and macOS from Node; a browser or a Worker cannot mount a
folder.

## Install

<Steps>
  <Step title="Install FUSE for the OS">
    Follow the [Linux](/home/setup/linux) or [macOS](/home/setup/macos) guide.
  </Step>
  <Step title="Add the binding">
    ```bash
    pnpm add @struktoai/mirage-node @zkochan/fuse-native
    ```

    [`@zkochan/fuse-native`](https://www.npmjs.com/package/@zkochan/fuse-native)
    is an optional peer that compiles native code on install. Allow pnpm to
    build it, in `pnpm-workspace.yaml`:

    ```yaml pnpm-workspace.yaml
    onlyBuiltDependencies:
      - '@zkochan/fuse-native'
    ```

    Outside a pnpm workspace, put the same list under `"pnpm"` in
    `package.json`.
  </Step>
  <Step title="On macOS with macFUSE 4, link the library">
    macFUSE 4 ships `libfuse.2.dylib`, and the binding links the older name.
    Link it once, then rebuild:

    ```bash
    sudo ln -sf /usr/local/lib/libfuse.2.dylib /usr/local/lib/libosxfuse.2.dylib
    pnpm rebuild @zkochan/fuse-native
    ```
  </Step>
</Steps>

## Mount a folder

```ts
import { readdir, writeFile } from 'node:fs/promises'
import { Mount, MountBackend, MountMode, RAMVFS, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace({
  '/data': new Mount(new RAMVFS(), { mode: MountMode.WRITE, backend: MountBackend.FUSE }),
})
await ws.fuseReady()
const folder = ws.fuseMountpoints['/data']
await writeFile(`${folder}/hello.txt`, 'hello\n')
console.log(await readdir(folder)) // [ 'hello.txt' ]
await ws.close()
```

- Mounting is async: `await ws.fuseReady()` resolves once every folder is
  live, and rejects if one fails. `ws.close()` unmounts.
- `ws.fuseMountpoints` maps each prefix to its folder, a fresh
  `mirage-fuse-*` directory under the OS temp folder unless the mount sets
  `mountpoint`.
- The folder follows the mount's mode: a `read` mount cannot be written.

<Warning>
  The folder is served on the mounting process's event loop. A synchronous
  call on it from that process, such as `readFileSync`, `statSync` or
  `execFileSync('cat', ...)`, waits on a call only that loop can answer and
  hangs the mount. Use the async `fs` API and async child processes, or own
  the mount from a child process (`examples/typescript/fuse/helper.ts`).
  Other processes are unaffected.
</Warning>

## Backends

Each mount picks its own `backend`:

| `backend` | The mount is | Runs on |
| --- | --- | --- |
| `workspace` (default) | only inside Mirage | everywhere |
| `fuse` | also a folder, through FUSE | Linux, macOS |
| `fskit` | also a folder, through FSKit with no kernel extension; read-mostly | macOS 15.4+ |
| `nfs` | also a folder, read-only, through the OS's NFS client and no FUSE install | Linux (as root) and macOS |

```yaml
mounts:
  /data:
    vfs: ram
    mode: write
    backend: fuse
    mountpoint: /tmp/data   # omit for a temp directory
  /s3:
    vfs: s3
    backend: nfs
  /logs:
    vfs: disk               # no backend: stays inside Mirage
```

<Warning>
  macOS allows one FUSE mount per process: a second one fails. Put a kernel
  backend on one mount, or run the others in separate processes.
</Warning>

## Behavior

- **Files of unknown size.** Slack, Linear, Trello and other API-backed
  mounts cannot size a file without fetching it, so it stats as 0 bytes until
  something opens it, like a `/proc` file. `cat`, `grep`, `cp` and `wc -c`
  read it in full. `ls -l`, `du` and `find -size` show 0 until it is opened,
  and `tar` or `rsync` copy it empty. Mirage never fetches content during
  `stat`, which would cost one API call per file on every `ls -l`.
- **Symlinks.** Links made with `ln -s`, in the Mirage Shell or in the
  folder, show as real symlinks and resolve inside the folder.
- **Permissions.** The mode bits `chmod` and `chown` set are for display.
  Mount modes and policy decide access, never the kernel.
- **Extended attributes.** `getfattr` and `setfattr` in the folder read and
  write the same attributes as the Mirage Shell, on every VFS.

## FSKit on macOS

With macFUSE 5 on macOS 15.4+, `backend: 'fskit'` serves the folder through
FSKit instead of the kernel extension, which Apple is phasing out:

```ts
import { Mount, MountBackend, RAMVFS, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace({ '/data': new Mount(new RAMVFS(), { backend: MountBackend.FSKIT }) })
await ws.fuseReady()
console.log(ws.fuseMountpoints['/data']) // /Volumes/mirage-...
```

The rules match [Python's](/python/setup/fuse#fskit-on-macos): the folder is a
volume under `/Volumes`, every VFS on it must know its files' sizes, and
Mirage warns at mount time about either.

<Warning>
  From TypeScript, FSKit is read-mostly and experimental. New files can be
  written as NUL bytes, as in Python, and on top of that `create`, `mkdir`
  and `rename` return ENOSYS, because the binding cannot install the macOS
  callbacks FSKit needs for new names. A hung FSKit volume can block the
  system's mount table until the macFUSE FSKit process is killed. Use
  `fuse` for anything long-running or written to.
  `examples/typescript/fuse/fskit.ts` runs the end-to-end check.
</Warning>
