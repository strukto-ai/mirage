`WandbVFS` mounts Weights & Biases (W&B) experiments as read-only files: each
run's metadata, config, summary, metric history and logged files. The API key
and entities are set up on the [Weights & Biases page](/home/setup/wandb).

## Install

```bash
npm install @struktoai/mirage-node
```

## Configure

```ts
import { MountMode, Workspace, buildVfs } from '@struktoai/mirage-node'

const wandb = await buildVfs('wandb', {
  entities: ['my-team'],
  api_key: process.env.WANDB_API_KEY,
})
const ws = new Workspace({ '/wandb': wandb }, { mode: MountMode.READ })

const result = await ws.shell('find /wandb/my-team -maxdepth 3 -name run.json')
console.log(result.stdoutText)
```

`page_size` and `max_pages` bound each listing, and `base_url` points at
another W&B server.

## Authentication

The API key is sent as HTTP Basic auth and reads what its user can read.
Mirage does not discover entities from the key: set `entities` to the user or
team segment of a project URL (`wandb.ai/<entity>/<project>`). An empty
`api_key` sends no credentials. Only downloads from the `base_url` origin
carry the key.

## Layout

```text
/wandb/
  my-team/
    image-cls/
      3k9x2m7q/
        run.json
        config.json
        summary.json
        history.jsonl
        files/
          output.log
          wandb-metadata.json
```

A path is `/<entity>/<project>/<run-id>/`. Run IDs name the folders, so runs
that share a display name stay separate. `files/` holds the run's files at
their relative paths, as raw bytes.

`run.json` holds the run's metadata:

| Fields | Contents |
| --- | --- |
| `entity`, `project`, `run`, `path` | Run identity and its `entity/project/run-id` path |
| `storage_id`, `display_name`, `state` | W&B's opaque storage ID, display name, and reported state |
| `tags`, `sweep_name`, `group`, `job_type` | Experiment organization |
| `commit`, `created_at`, `heartbeat_at` | Source revision, creation time, and last heartbeat |
| `description`, `notes`, `user` | Run description, notes, and creator's `id`/`name`/`username`/`email` |
| `read_only` | W&B's reported edit permission; the Mirage mount remains read-only |
| `system_metrics` | Latest system metrics decoded as JSON, retaining nested values |
| `history_line_count`, `history_keys`, `file_count` | History row count, metric-key metadata including the last step, and file count |

## Behavior

- **Read only:** the mount registers no write operations and no W&B CLI.
- **`run.json`:** unavailable metadata is `null`; empty tags, zero counts,
  false permissions and original timestamp strings are kept. `user` is the
  run's creator, not the key's user, and is `null` when the creator is
  missing. Machine and runtime details are in `files/wandb-metadata.json` when
  uploaded. Listing and `stat` fetch none of these fields.
- **`config.json` and `summary.json`:** `config.json` unwraps W&B's `value`
  envelopes. `summary.json` is the stored summary, which can differ from the
  best value in history. Both keep run-defined keys, nested values, nulls and
  metric names holding `/` or `.`.
- **`history.jsonl`:** the full, unsampled history, in order, with missing keys,
  nulls and logged training-step fields kept; `_step` and a training-step
  metric are separate values. The last step is fixed when a read begins, so
  rows logged later show on the next read. Reads stream, so `head` stops
  before the whole history is fetched.
- **Sizes:** `run.json`, `config.json`, `summary.json` and `history.jsonl` have
  unknown sizes; file sizes come from W&B's file metadata.
- **Pagination:** listings follow W&B pagination, `page_size` (100, at most
  1000) items per page and at most `max_pages` (10000) pages. Running out fails
  rather than return a partial list. Recursive `du` stops at 1000 entries.

## Browser

`@struktoai/mirage-browser` ships the same VFS, built the same way with its
`buildVfs`. It calls W&B with the browser's `fetch`, so it works only where the
service's CORS rules allow the page's origin, and the API key reaches the page.
