`AirtableVFS` exposes the bases a personal access token can reach as a
read-only tree of tables, records, and saved views. Reads go through the
Airtable Web API with plain `fetch`, so one class serves Node and the browser.

Setup steps for the token live at [Airtable Credentials](/home/setup/airtable).

## Node

```bash
pnpm add @struktoai/mirage-node
```

```ts
import { AirtableVFS, MountMode, Workspace } from '@struktoai/mirage-node'

const airtable = new AirtableVFS({ token: process.env.AIRTABLE_TOKEN! })

const ws = new Workspace({ '/airtable': airtable }, { mode: MountMode.READ })
await ws.shell('ls /airtable/bases/')
```

## Browser

```bash
pnpm add @struktoai/mirage-browser
```

```ts
import { AirtableVFS, MountMode, Workspace } from '@struktoai/mirage-browser'

const airtable = new AirtableVFS({ token: AIRTABLE_TOKEN })
```

The Airtable API sends `access-control-allow-origin: *`, so the browser calls
it directly; a token in a page is visible to that page's user.

## Config

{/* generated: config-table airtable start */}
| Field | Description |
| --- | --- |
| <code style={{ whiteSpace: 'nowrap' }}>token</code><br />required, secret | Personal access token (or OAuth access token), sent as `Authorization: Bearer`. |
| <code style={{ whiteSpace: 'nowrap' }}>baseIds</code> | Only these bases are listed or readable. Unset shows every base the token can reach. |
| <code style={{ whiteSpace: 'nowrap' }}>baseUrl</code><br />default `'https://api.airtable.com/v0'` | Airtable API root; override to point at a fake or proxy. |
| <code style={{ whiteSpace: 'nowrap' }}>maxReadRecords</code><br />default `10000` | The most records one file renders. A full read of a larger table or view fails with `File too large` once it passes the cap; `head -n N` still reads its first records. |
| <code style={{ whiteSpace: 'nowrap' }}>requestsPerSecond</code><br />default `5` | Requests per second per base. Airtable allows 5 and answers a burst with a 30-second penalty. |

Fields marked secret are redacted in snapshots.
{/* generated: config-table airtable end */}

## Mount mode

`read`. Writes go through the [airtable CLI](/typescript/cli/airtable), which
takes the same config and names a base, a table and a record by the id after
the last `__` of the mount's directory names.

For the mounted layout (`bases/`, `table.json`, `records.jsonl`, `views/`)
and the reading rules see the [Python Airtable docs](/python/vfs/airtable).

    #### `/<path>` layout

    ```text
    /<path>
      bases/
        <base-name>__<base-id>/
          base.json                    base id, name, permission, table list
          <table-name>__<table-id>/
            table.json                 typed fields (with options) and views
            records.jsonl              one record per line
            views/
              <view-name>__<view-id>.jsonl   records the view shows, in its order
      Always ls directories first to discover exact names: the name part of
      a segment is sanitized, the id after the LAST "__" is exact.

      A records.jsonl line is a mirage-normalized record:
        record_id, created_time, and fields (keyed by field NAME, values as
        Airtable returns them). Read table.json for each field's type.
      Airtable omits empty cells, so a missing key means empty (checkbox
      false included). A link field is a list of record ids; an attachment
      url expires two hours after it was read.
      records.jsonl lists in the API's own order; a view file applies the
      view's filter and sort. A file over max_read_records records stops
      with File too large after that many, while head -n N fetches just N
      records:
        head -n 20 /<path>/bases/<base>/<table>/records.jsonl | jq .fields
      The airtable CLI, if installed, reaches what a file cannot: server-side
      filters (airtable record list --formula or --view), one record by id
      (airtable record get), and comments (airtable comment list).
    ```

    #### Supported Unix Commands for VFS

    Unix commands work on each path as on a local filesystem, as far as the path supports them:

    | Path | Supported |
    | --- | --- |
    | `/<path>` | Commands that read files (`ls`, `cat`, `grep`, `find`, `jq` and the rest). `grep` and `rg` ask `airtable` for the matching lines. `head` asks `airtable` instead of reading a file. |

    #### Limitations of Unix Commands for VFS

    Where a path differs from a local filesystem:

    | Path | Limitations |
    | --- | --- |
    | `/<path>` | Read only: no command changes files. `grep -r`, `find` and `du` stop after 1000 files; a glob matching more, `tar -c`, `cp -r` and `rm -r` are refused. |

    Run `man` to list every command, and `man <cmd>` or `<cmd> --help` for one command's usage.

## Integration

What Airtable answers through its own API, so fewer files are read. [Integration](/home/integration/overview) explains each command.

| Command | On Airtable |
| --- | --- |
| `grep`, `rg` on one file | A `filterByFormula` fetches only the records that may match |
| `head -n N` | Fetches N records |

The [Python Airtable docs](/python/vfs/airtable#integration) list when each search answers and what it can miss.
