`GCalVFS` mounts every calendar an account can see: each calendar becomes a
folder of days, and each event a `.gcal.json` file holding the Calendar API's
JSON. Credentials are set up on the
[Google Workspace page](/home/setup/google).

## Install

```bash
npm install @struktoai/mirage-node
```

## Configure

```ts
import { GCalVFS, MountMode, Workspace } from '@struktoai/mirage-node'

const gcal = new GCalVFS({
  clientId: process.env.GOOGLE_CLIENT_ID!,
  clientSecret: process.env.GOOGLE_CLIENT_SECRET!,
  refreshToken: process.env.GOOGLE_REFRESH_TOKEN!,
})
const ws = new Workspace({ '/gcal': gcal }, { mode: MountMode.READ })

const result = await ws.shell("ls /gcal && grep -lw standup /gcal/primary/2026-11-*/*.gcal.json")
console.log(result.stdoutText)
```

`bucketDays: 7` or `30` makes each folder a week or a month, `timeZone` sets
the zone days are cut in, and `startTime` and `endTime` limit the mount to a
time range. A `MountMode.WRITE` mount also allows `rm`.

## Authentication

Credentials come from the first of:

1. `accessToken`, a token or a function, sync or async, that returns one.
2. `clientId` and `refreshToken`, with `clientSecret` unless the client uses
   PKCE. Mirage trades the refresh token for access tokens on its own, or
   hands it to `refreshFn` when set, so the secret can stay on a backend.

The mount needs the Google Calendar API with the
`https://www.googleapis.com/auth/calendar` scope, or `calendar.readonly` for a
read-only mount. `rm` needs the `owner` or `writer` role on the event's
calendar; otherwise it fails with `Permission denied`.

## Layout

```text
/gcal/
  primary/
    calendar.json
    2026-11-16/
      7kq2m9__0900-0930_Team_Standup.gcal.json
  Engineering__team@group.calendar.google.com/
    2026-11-16/
      ...
```

- The primary calendar is `primary`; every other one ends in
  `__<calendar-id>`.
- An event file is named `<event-id>__<HHMM-HHMM>_<title>.gcal.json`. The
  times are clamped to that day, so an event running through it reads
  `0000-2400`, and an event over several days appears under each.
- An event file holds the unmodified Calendar API payload: attendees,
  description, location, and start and end with their offsets.
- `calendar.json` holds the calendar's access role and the zone its days are
  cut in.

## Behavior

- **Time range:** `ls` of a calendar lists days from all its history through
  90 days ahead. A date glob such as `ls /gcal/primary/2027-03-*` lists its
  own range, past that horizon. `startTime` and `endTime` (RFC 3339 with a
  timezone) limit every listing, path, glob and read; dates outside them are
  absent.
- **Days:** a well-formed date inside the range is a folder even when it holds
  no events. One zone covers the whole mount, the primary calendar's unless
  `timeZone` is set, so every calendar's `2026-11-16/` covers the same hours.
- **Calendars listed:** `minAccessRole` (`freeBusyReader`, `reader`,
  `writer` or `owner`) hides calendars where the account has less access.
- **Free/busy calendars:** Google returns no titles for a calendar shared as
  free/busy only, so its events read as `busy`.
- **Delete:** on a `write` mount, `rm` on an event file deletes the event for
  every attendee. Creating, editing and moving events go through the
  [`gws calendar`](/typescript/cli/gws) CLI, which takes the calendar and event
  ids the tree shows. A written event must carry an explicit UTC offset or
  time zone.

## Browser

The same `GCalVFS` comes from `@struktoai/mirage-browser`. In a page, an
`accessToken` function fetches a fresh token from a backend, so the client
secret never reaches the browser.

```bash
npm install @struktoai/mirage-browser
```

```ts
import { GCalVFS, MountMode, Workspace } from '@struktoai/mirage-browser'

const gcal = new GCalVFS({
  accessToken: async () => (await fetch('/api/google-token')).text(),
})
const ws = new Workspace({ '/gcal': gcal }, { mode: MountMode.READ })
```

- `/api/google-token` stands for a backend endpoint that returns an access
  token.
- A PKCE OAuth client needs no secret: `clientId` and `refreshToken` alone
  mount it.
- `refreshFn` sends each refresh to a backend instead of Google's token
  endpoint.

## Integration

Google Calendar answers these commands through its own API, so fewer files
are read. See [Integration](/home/integration/overview).

- `grep -r` and `rg` with `-w`: Calendar's event search names the event files
  to read, together with the text the listing keeps, so no match is missed.
  Every file is read when the search fails or finds nothing, and files other
  than events (`calendar.json`) are always read. `walkLimit: -1` in the
  mount's `"@all"` [command limit](/home/core/output-limits) turns the search
  off and reads every file.
