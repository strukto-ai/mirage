Mirage includes ten command-line programs for working with services and Git
repositories inside a workspace. Each program's `--help` describes the
commands and flags implemented by Mirage.

The [host `mirage` CLI](/home/access/cli) connects to and manages workspaces.
The programs on this page run in those workspaces through `ws.shell(...)`,
`mirage shell`, or another [access method](/home/access/overview).

All ten are available in Python and TypeScript on Node. The TypeScript Node
package provides `hf` and `himalaya`; the other eight live in core. These are
Mirage implementations of the listed command trees, not installed copies of
the upstream binaries. Each reference links its upstream project or service
API and documents its supported subset, limits and relevant licenses. See
[compatibility and licenses](/home/setup/clis#compatibility-and-licenses)
for the distinction between matching behavior and reusing code.

## Register a CLI

Account CLIs need credentials but do not need a service mount:

```typescript
import { SLACK, Workspace } from '@struktoai/mirage-node'

const ws = new Workspace({})
ws.registerCli('slack', SLACK, { token: 'xoxb-...' })
await ws.shell('slack --help')
```

`registerCli(name, spec, config)` validates the config object with the spec's schema.
`git` has no account config; register its `GIT` spec without the third argument.
Two installations of the same spec under different names can use different
accounts. Registration is a host operation, not an agent shell command.

The equivalent YAML entry is:

```yaml
clis:
  slack:
    cli: slack
    config:
      token: ${SLACK_TOKEN}
```

YAML config fields use snake_case in both languages. [Setup pages](/home/setup/clis)
cover credentials and imports for every program.

## Discover functionality

```bash
man
slack --help
slack send-message --help
man slack send-message
type -t slack
which slack
```

`man` and `--help` render the registered spec. Unknown commands and flags are
refused; wording and exit codes follow the program's declared style. Use each
reference for command-specific errors rather than assuming one exit code for
all CLIs.

Visible installed programs have read-only stubs under `/usr/bin`, so
`which slack` returns `/usr/bin/slack`. The stub describes the command without
exposing its config or credentials. Executing that path uses the same command
and policy checks. Changing `PATH` does not change Mirage's virtual command
lookup; host and remote runtimes use their own executable paths.

## Use CLIs with the VFS

| Operation | Where it goes |
| --- | --- |
| `cat`, `find`, `grep`, `jq` on mounted files | The selected VFS through workspace operations |
| Account commands such as `slack send-message` | The service configured for that CLI installation |
| File arguments such as `gh --body-file`, `ntn --filter-file`, `himalaya --attach` and `hf upload` paths | Workspace files through `CLIView` |
| `git -C /repo ...` | The repository and working tree on workspace mounts |

Credentials may be shared between a CLI and a VFS, but neither registers or
locates the other. A CLI write uses service IDs, while file arguments resolve
against the session's working directory and retain `PathSpec` semantics.
After an account CLI write, Mirage expires mounted caches so later reads can
observe the change.

Mount modes and path policy govern workspace file operations. A read-only
Slack mount does **not** disable `slack send-message`; use command policy to
restrict service actions. The service's own credentials and permissions still
apply to its API calls.
