[Pi Durable](https://github.com/earendil-works/pi/tree/main/packages/durable) is Pi's durable agent harness: conversations, turns and tool calls are stored before anything is shown, so a restarted process picks a run up where it stopped. Its built-in tools (`read`, `write`, `edit`, `bash`, code mode) reach files and commands only through an `ExecutionEnv`. `@struktoai/mirage-pi-durable` provides one over a Mirage `Workspace`, so the tools work on whatever the workspace mounts.

## Install

```bash
npm install @struktoai/mirage-pi-durable @struktoai/mirage-node @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord
```

## Usage

Install Pi's coding tools and the Mirage extension, and build a `MirageExecutionEnv` for each call:

```ts
import { BACKGROUND_CONTEXT } from '@earendil-works/chord/context'
import { builtinModels } from '@earendil-works/pi-ai/providers/all'
import { createRegistry, Harness, MemoryStorage } from '@earendil-works/pi-durable'
import { CodingTools } from '@earendil-works/pi-durable/tools'
import { MountMode, RAMVFS, S3VFS, Workspace } from '@struktoai/mirage-node'
import { MirageExecutionEnv, mirageExtension } from '@struktoai/mirage-pi-durable'

const context = BACKGROUND_CONTEXT
const ws = new Workspace(
  { '/': new RAMVFS(), '/s3': new S3VFS({ bucket: 'my-bucket', region: 'us-east-1' }) },
  { mode: MountMode.WRITE },
)

const registry = createRegistry()
registry.install(CodingTools)
registry.install(mirageExtension(ws))

const harness = await Harness.open(
  new MemoryStorage(),
  {
    models: builtinModels(),
    registry,
    env: ({ cwd }) => new MirageExecutionEnv(ws, { cwd: cwd ?? '/' }),
  },
  context,
)
const root = await harness.root(context, {
  agent: { model: { provider: 'anthropic', modelId: 'claude-sonnet-5-5' } },
})
const run = await root.submit({ type: 'input', content: 'Summarize /s3/reports' }, context)
await run.wait(context)
```

`mirageExtension` adds a `mirage` prompt section that describes the mounts. The conversation's `cwd` (`root.configure({ cwd })`) reaches the environment, so each conversation can work in its own directory.

## Durable runs

Open the harness on stored state to keep conversations across restarts. The workspace's files persist as their mounts do:

```ts
import { openNodeSqliteStorage } from '@earendil-works/pi-durable/storage/sqlite/node'

const harness = await Harness.open(
  await openNodeSqliteStorage('./session.sqlite'),
  { models: builtinModels(), registry, env: ({ cwd }) => new MirageExecutionEnv(ws, { cwd: cwd ?? '/' }) },
  context,
)
harness.resume()
```

## Use a workspace on a Mirage server

Give `MirageExecutionEnv` and `mirageExtension` where a [Mirage server](/typescript/access/server)'s workspace lives instead of a `Workspace`, and Pi's tools call it over HTTP: each file call goes to its VFS API, each command to its shell. The harness can then run where nothing is mounted, such as a Cloudflare Worker or Durable Object. Import from `@struktoai/mirage-pi-durable/remote` there, which leaves out the workspace code of this process. It replaces the first example's `@struktoai/mirage-pi-durable` import, `ws`, its `registry.install(mirageExtension(ws))` line and `harness`:

```ts
import { MirageExecutionEnv, mirageExtension } from '@struktoai/mirage-pi-durable/remote'

const remote = { url: 'https://mirage.example.com', workspace: 'ws_123', token: process.env.MIRAGE_TOKEN }
registry.install(mirageExtension(remote))
const harness = await Harness.open(
  new MemoryStorage(),
  { models: builtinModels(), registry, env: ({ cwd }) => new MirageExecutionEnv(remote, { cwd: cwd ?? '/', sessionId: 'agent' }) },
  context,
)
```

- The server owns the mounts, machines and profiles. `sessionId` names a session on the server, created on first use.
- `id` defaults to the server and workspace, so every process reaching one workspace shares Pi's file namespace.
- The prompt section lists the mounts as the server describes them.

## Behavior

- **Commands** run in Mirage's shell as one session. Each call starts from its `cwd`, so a `cd` or `export` does not carry over to the next one, as with a new process.
- **Sessions:** pass `sessionId` to act as a Mirage session, under its profile's mounts, hides and policies. A refused command's output ends with the policy's reason.
- **Long output** past Pi's bounds is written to a file under `/tmp` as it arrives, which needs a writable mount there. A command cancelled after that keeps its file.
- **Mount roots** cannot be removed or renamed, nor can a folder holding one, as in the shell.
- **Watching** polls: every `watch.pollIntervalMs`, Pi compares snapshots of each watched path, asked of the backend each time. A file new to a remote folder shows once the mount's listing of that folder refreshes.
- **Binary reads** copy the file when Pi opens it, so a later rename or rewrite of the path does not reach an open reader.

`MirageExecutionEnv` accepts:

| Option                 | Default             | Purpose                                                                   |
| ---------------------- | ------------------- | ------------------------------------------------------------------------- |
| `cwd`                  | `'/'`               | Where relative paths and commands start.                                  |
| `sessionId`            | default session     | The Mirage session every call acts as, under that session's profile.      |
| `id`                   | one per workspace   | Pi's file namespace: environments with one id see the same files.         |
| `watch.pollIntervalMs` | `2000`              | Milliseconds between the snapshots `watch` compares.                      |
