[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) is a plugin-based agent harness on Cordis where the filesystem and the shell are swappable capability seams. `@struktoai/mirage-dsh` provides both seams over one Mirage workspace: `ctx.fs` for dsh's read/write/edit tools and `ctx.shell` for its bash tool. Anything Mirage mounts — S3, Gmail, Slack, Notion, Postgres — becomes the world those tools operate in.

## Install

```bash
npm install @struktoai/mirage-dsh @struktoai/mirage-node @deepseek-ai/cordis @deepseek-ai/dsh-fs @deepseek-ai/dsh-shell
```

## Compose

Three Cordis plugins, mirroring dsh's own E2B provider group. `MirageService` owns the workspace; the two providers inject it. Mix any resources — here Gmail and Slack beside a scratch RAM mount:

```ts
import { Context } from '@deepseek-ai/cordis'
import { GmailResource, MountMode, RAMResource, SlackResource, Workspace } from '@struktoai/mirage-node'
import { MirageFileSystem, MirageService, MirageShellExecutor } from '@struktoai/mirage-dsh'

const ws = new Workspace(
  {
    '/notes': [new RAMResource(), MountMode.EXEC],
    '/mail': new GmailResource({ clientId, clientSecret, refreshToken }),
    '/slack': [new SlackResource({ token: slackBotToken }), MountMode.EXEC],
  },
  { runtimes: ['monty', 'vfs'] },
)

const ctx = new Context()
await ctx.plugin(MirageService, { workspace: ws }).await()
await ctx.plugin(MirageFileSystem, {}).await()
await ctx.plugin(MirageShellExecutor, {}).await()
```

Mirage mounts are read-only by default; the mode ladder is `READ` < `WRITE` < `EXEC`, so mount with `MountMode.WRITE` where dsh's write tools should work and `MountMode.EXEC` where scripts may run. dsh's bash tool now spans every source in one line:

```ts
const shell = ctx.shell
const sweep = await shell.run(
  shell.resolve({ command: 'grep -rln invoice /mail/INBOX /slack/channels | head' }),
)
```

`MirageService` also accepts `mounts` instead of a live `workspace`; it then constructs the workspace itself and closes it when the plugin unloads.

## Run Python with monty

Registering `runtimes: ['monty', 'vfs']` routes `python3` lines to [monty](https://github.com/pydantic/monty), a sandboxed Python interpreter with no host access, and keeps `vfs` for the shell commands. A script can live on any mount — upload `example.py` to a Slack channel and run it straight off the mount (uploads land under `<channel>__<id>/<date>/files/`, with the Slack file ID suffixed into the name):

```ts
const ran = await shell.run(
  shell.resolve({
    command: 'python3 /slack/channels/general__C0.../2026-08-13/files/example__F0....py > /notes/report.txt',
  }),
)
```

The pattern that fits monty is: **the fs seam and the shell do the file I/O, monty does the compute** — the shell's pipes and redirections file a script's stdout back into any writable mount. [`examples/typescript/dsh/slack.ts`](https://github.com/strukto-ai/mirage/blob/main/examples/typescript/dsh/slack.ts) is the runnable version, with the script in [`example.py`](https://github.com/strukto-ai/mirage/blob/main/examples/typescript/dsh/example.py).

## One execution world

dsh's architecture expects the filesystem and shell providers to share one execution world, so that a path from one seam is valid in the other. Both providers here read the same `ctx.mirage` workspace: `ctx.fs.processPath(target)` returns a virtual path that `ctx.shell` commands resolve to the same file, and a file written by the shell stats and edits through `ctx.fs`.
