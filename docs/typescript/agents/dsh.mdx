[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (`dsh`) is a plugin-based agent harness on Cordis where the filesystem and the shell are swappable capability seams. `@struktoai/mirage-dsh` provides both seams over one Mirage workspace: `ctx.fs` for dsh's read/write/edit tools and `ctx.shell` for its bash tool. Anything Mirage mounts — S3, Gmail, Slack, Notion, Postgres — becomes the world those tools operate in.

## Install

```bash
npm install @struktoai/mirage-dsh @struktoai/mirage-node @deepseek-ai/cordis @deepseek-ai/dsh-fs @deepseek-ai/dsh-shell
```

## Compose

Three Cordis plugins, mirroring dsh's own E2B provider group. `MirageService` owns the workspace; the two providers inject it. Mix any resources — here Gmail and S3 beside a scratch RAM mount:

```ts
import { Context } from '@deepseek-ai/cordis'
import { GmailResource, MountMode, RAMResource, S3Resource, Workspace } from '@struktoai/mirage-node'
import { MirageFileSystem, MirageService, MirageShellExecutor } from '@struktoai/mirage-dsh'

const ws = new Workspace(
  {
    '/notes': [new RAMResource(), MountMode.EXEC],
    '/mail': new GmailResource({ clientId, clientSecret, refreshToken }),
    '/data': [new S3Resource({ bucket: 'my-bucket', region: 'us-east-1' }), MountMode.WRITE],
  },
  { runtimes: ['monty', 'vfs'] },
)

const ctx = new Context()
await ctx.plugin(MirageService, { workspace: ws }).await()
await ctx.plugin(MirageFileSystem, {}).await()
await ctx.plugin(MirageShellExecutor, {}).await()
```

Mirage mounts are read-only by default; the mode ladder is `READ` < `WRITE` < `EXEC`, so mount with `MountMode.WRITE` where dsh's write tools should work and `MountMode.EXEC` where scripts may run. dsh's bash tool now spans every source in one line:

```ts
const shell = ctx.shell
const sweep = await shell.run(
  shell.resolve({ command: 'grep -rln invoice /mail/INBOX /data/reports | head' }),
)
```

`MirageService` also accepts `mounts` instead of a live `workspace`; it then constructs the workspace itself and closes it when the plugin unloads.

## Run Python with monty

Registering `runtimes: ['monty', 'vfs']` routes `python3` lines to [monty](https://github.com/pydantic/monty), a sandboxed Python interpreter with no host access, and keeps `vfs` for the shell commands. The pattern that fits monty is: **the fs seam and the shell do the file I/O, monty does the compute** — the shell's pipes and redirections file a script's stdout back into any mount:

```ts
await ctx.fs.writeText(
  await ctx.fs.resolve('/notes/report.py'),
  'import os\nwho = os.getenv("REPORT_OWNER", "nobody")\nprint("owner:", who)\nprint("total:", sum(range(100)))\n',
)
const ran = await shell.run(
  shell.resolve({ command: 'REPORT_OWNER=zecheng python3 /notes/report.py > /data/report.txt' }),
)
```

The TypeScript monty binding answers `os.getenv`/`os.environ` but not builtin `open()` or `os.listdir` yet; a script that must read mounted files itself should run under `pyodide` (WASM CPython, the default when no `runtimes` list is given), where `open()` and `os.listdir` work against the mounts. Either way the script executes inside the workspace, never on the host.

## One execution world

dsh's architecture expects the filesystem and shell providers to share one execution world, so that a path from one seam is valid in the other. Both providers here read the same `ctx.mirage` workspace: `ctx.fs.processPath(target)` returns a virtual path that `ctx.shell` commands resolve to the same file, and a file written by the shell stats and edits through `ctx.fs`.

## Semantics

- **Targets are canonical virtual paths.** `resolve()` collapses aliases and follows Mirage namespace symlinks once, yielding the stable `FsTarget` every other operation takes; `lstat()` probes the path entry itself and reports `symlink` for a link.
- **Versions are metadata tokens.** `FsVersion` derives from the backend's fingerprint, revision, or `modified` + `size`, so dsh's stale-write guards (`createIfAbsent`, `replaceIfVersion`) work without content hashing. A backend that reports none of those degrades to always-fresh.
- **Errors carry dsh codes.** Mirage's POSIX-stamped errors map onto the seam taxonomy: a missing path is `FS_NOT_FOUND`, a directory in a file slot is `FS_NOT_REGULAR_FILE`, a policy denial or read-only mount is `FS_PERMISSION_DENIED`.
- **Every op walks the workspace door.** Session grants, admission policies, cache read-through, and post-write invalidation fire exactly as they do for a Mirage shell command.

## Sandboxing and policy

Both providers report `sandboxMode` as `undefined` and ignore per-call `sandboxPolicy`: dsh's sandbox seam confines host OS processes, and there is no OS process here to confine. Confinement comes from Mirage instead — mount modes, session grants, and the policy layer bound what any command, file op, or guest script can touch, uniformly across both seams.

## Limitations

- `ctx.shell.start()` delivers output once the command completes; Mirage buffers a command's output rather than streaming it, and `kill()` aborts cooperatively at executor boundaries.
- dsh's `ctx.subprocess`, terminal, and LSP seams are not provided: Mirage's shell is an interpreter, not an OS. Compose profiles without those capabilities, or point them at a Mirage FUSE mount when real processes must see mounted data.
- Built against the published `@deepseek-ai/dsh-fs` and `@deepseek-ai/dsh-shell` release candidates; dsh is in developer preview and its seams may change.
