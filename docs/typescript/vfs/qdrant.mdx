`QdrantVFS` mounts a [Qdrant](https://qdrant.tech/) collection, read-only, as
nested folders, one level per group-by payload field. Each point is a `.json`
payload file, plus a `.txt` text file and an optional blob. Set up the cluster URL and API key as in [Qdrant setup](/home/setup/qdrant).

## Install

```bash
npm install @struktoai/mirage-node @qdrant/js-client-rest
```

## Configure

```ts
import { MountMode, QdrantVFS, Workspace } from '@struktoai/mirage-node'

const fashion = new QdrantVFS({
  url: process.env.QDRANT_URL!,
  apiKey: process.env.QDRANT_API_KEY!,
  collection: 'fashion',
  groupBy: ['gender', 'articleType', 'baseColour'],
  textField: 'productDisplayName',
})
const ws = new Workspace({ '/fashion': fashion }, { mode: MountMode.READ })

const result = await ws.shell('ls /fashion/Men/Shoes/White && cat /fashion/Men/Shoes/White/3.json')
console.log(result.stdoutText)
await ws.close()
```

A self-hosted Qdrant sets `host` and `port` (default `localhost:6333`) instead
of `url`. `blobField` and `blobExt` serve a payload field of raw or base64
bytes as a file, such as `3.jpg`.

## Authentication

A self-hosted Qdrant needs no key. Qdrant Cloud needs `apiKey`; a read-only
key, for the cluster or for the mounted collections, is enough to browse.

A filtered listing creates a keyword payload index for a `groupBy` field only
when Qdrant reports that one is required. A read-only key cannot create it, so
index those fields first or use a key that manages the collection.

## Layout

```text
/fashion/
  Men/
    Shoes/
      White/
        3.json
        3.txt
  Women/
    Tops/
      Blue/
        12.json
        12.txt
```

Each folder level filters on one `groupBy` field, in order. Once every field is
bound, the folder lists each point's files, named by point id, or
`<name>__<id>` with `nameField`. Without `collection`, every collection is a
top-level folder. A value holding `/` renders as `∕`, and a blank or dot-led
value is led by `⁄`, so every value keeps its own folder that lists and opens.

- `<id>.txt` is the `textField` value, the text the vector was built from.
- `<id>.json` is the full payload as compact JSON, without the vector and the
  blob.
- `<id>.<blobExt>` is the raw bytes of `blobField`, when it is set.

## Behavior

- **Read-only:** no command changes the collection.
- **Nested fields:** fields take Qdrant's dotted keys. For LangChain-style
  chunks, `groupBy: ['metadata.source']`, `basenameFields: ['metadata.source']`,
  `nameField: 'metadata.page'` and `textField: 'page_content'` show page `004`
  of `s3://docs/policies/refund-2026.pdf` as
  `refund-2026.pdf/004__<point-id>.txt`.
- **File names:** the point id stays in every name, so two equal labels never
  collide. Only the name a listing shows opens: another label in front of the
  same id reads as absent. A label that is not a string is written as compact
  JSON (`true`, `1`, `1e-7`).
- **Basenames:** `basenameFields` keeps only the last path or URL segment of a
  value. Two values with one basename under the same parent are refused rather
  than merged, and opening a basename folder checks every point of its parent,
  so a second source past `maxRows` is refused rather than hidden. A name over
  255 bytes is cut to fit and ends in `__` plus the md5 of the whole name.
- **Listing cap:** one folder listing scrolls at most `maxRows` (1,000) points;
  points past it are left out. Keep `groupBy` to low-cardinality fields on a
  large collection.

### Semantic search

The `search` CLI runs Qdrant's vector query. Register
it on the workspace:

```ts
import { SEARCH } from '@struktoai/mirage-node'

ws.registerCli('search', SEARCH)
```

Each hit prints the point's `.txt` path, or its `.json` without `textField`,
with the similarity score, then the content. `--top-k` defaults to
`searchLimit` (10). `--threshold` is the lowest score kept. `--method` takes
only `semantic`.

The query needs a vector. `embed`, a `(text: string) => Promise<number[]>`,
builds it in-process, so a self-hosted Qdrant works with any model. Without it,
`cloudInference: true` sends the query text to the cluster, which must have
inference enabled (Qdrant Cloud) and store vectors from the same
`embeddingModel`. With neither, `search` refuses the query. `embed` never lands
in a snapshot, so a restored mount needs a fresh `QdrantVFS`.

## Browser

The same `QdrantVFS` runs in the browser from `@struktoai/mirage-browser`.

```bash
npm install @struktoai/mirage-browser @qdrant/js-client-rest
```

```ts
import { MountMode, QdrantVFS, Workspace } from '@struktoai/mirage-browser'

const fashion = new QdrantVFS({
  url: 'https://xyz-example.eu-central.aws.cloud.qdrant.io:6333',
  apiKey: QDRANT_API_KEY,
  collection: 'fashion',
  groupBy: ['gender', 'articleType', 'baseColour'],
  textField: 'productDisplayName',
})
const ws = new Workspace({ '/fashion': fashion }, { mode: MountMode.READ })
```

- The page calls Qdrant directly, so the server must accept requests from the
  page's origin.
- The API key is visible to anyone who loads the page: use a read-only key
  limited to the mounted collections.
