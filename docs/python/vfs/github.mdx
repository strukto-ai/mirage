The GitHub VFS uses GitHub's [REST API](https://docs.github.com/en/rest)
to mount a repository as a read-only virtual filesystem. It does not imitate
another CLI.

For token setup, see [GitHub Setup](/home/setup/github).

## Config

```python
import os

from mirage import MountMode, Workspace
from mirage.vfs.github import GitHubConfig, GitHubVFS

config = GitHubConfig(token=os.environ["GITHUB_TOKEN"])
vfs = GitHubVFS(
    config=config, owner="my-org", repo="my-repo", ref="main")
ws = Workspace({"/github": vfs}, mode=MountMode.READ)
```

The filesystem mirrors the repository tree. No owner/repo/branch in
the path - those are specified at mount time.

## Tree Fetching

The full recursive tree is fetched on the first read, not at mount time, so
constructing the VFS never blocks on the network. For repos with

> 100K entries, it falls back to per-directory fetching.

## Cache

The GitHub VFS uses `IndexCacheStore` with SHA-based fingerprinting. Content is content-addressed - if the SHA matches, the content is identical.

Under `read: fresh`, a cached listing is checked against the head commit
the `ref` resolves to: one small check per command (a shallow
`git/trees/{ref}`), after which every cached listing of the mount at that
commit is served. A mount whose `ref` is a full 40- or 64-hex commit sha
serves its cached listings with no request: github.com refuses a branch or
tag named with 40 or 64 hex characters, so such a ref always names a commit
(a GitHub Enterprise host is assumed to do the same). A repository whose recursive
tree comes back truncated stores no version, so each folder is re-listed
once per command.

## Example

```python
import asyncio
import os

from dotenv import load_dotenv

from mirage import MountMode, Workspace
from mirage.vfs.github import GitHubConfig, GitHubVFS

load_dotenv(".env.development")


async def main():
    config = GitHubConfig(token=os.environ["GITHUB_TOKEN"])
    vfs = GitHubVFS(
        config=config, owner="my-org", repo="my-repo", ref="main")
    ws = Workspace({"/github": vfs}, mode=MountMode.READ)

    # List repository root
    r = await ws.shell("ls /github/")
    print(await r.stdout_str())

    # Read a file
    r = await ws.shell("cat /github/README.md")
    print(await r.stdout_str())

    # Search for a pattern
    r = await ws.shell('rg "def main" /github/')
    print(await r.stdout_str())

    # Tree view
    r = await ws.shell("tree -L 2 /github/")
    print(await r.stdout_str())

    # File metadata with SHA
    r = await ws.shell("stat /github/README.md")
    print(await r.stdout_str())


if __name__ == "__main__":
    asyncio.run(main())
```

See [`examples/python/vfs/github/github.py`](https://github.com/strukto-ai/mirage/blob/main/examples/python/vfs/github/github.py) for the full working example.

## Finding SHAs

Git blob SHAs are available via the `stat` command:

```bash
stat /github/README.md
# -> extra={"sha": "a1b2c3d4e5f6..."}

stat /github/src/main.py
# -> extra={"sha": "f6e5d4c3b2a1..."}
```

## Working with Large Repos

Tips for efficient access on large repositories:

```bash
# Find files by name
find /github/ -name "*.py"

# Search whole words with rg (uses GitHub code search on large repos)
rg -w "TODO" /github/

# Read only the first lines of a file
head -n 20 /github/src/main.py

# Check file sizes
du /github/src/

# List deeply nested directories
tree -L 3 /github/src/
```

## Integration

What GitHub answers through its own API, so fewer files are read. [Integration](/home/integration/overview) explains each command.

| Command | On GitHub |
| --- | --- |
| `grep -r`, `rg` | GitHub code search, for whole words, on the default branch, under a path with more than 100 files. It can miss recent pushes. |
| `find`, `du`, `ls -R`, `tree` | One recursive tree listing |

`grep -rw` and `rg -w` read only the files GitHub code search names when:

- the scope holds more than 100 files; a smaller one is read directly,
- the mounted ref is the default branch, the only one code search indexes,
- the repository tree was listed in full,
- and the search returns every hit, 100 at most.

Every file is read otherwise. Files code search never indexes are always read.

Each file is one request, so `grep -r`, `git grep`, `find` and the other walks
stop after `walk_limit` files (default 5000) and keep what they printed,
and a glob matching more, `tar -c`, `cp -r`, `rm -r` and the [other whole-tree
commands](/home/integration/search#walk_limit) are refused above it:

```bash
$ grep -r TODO /github/
/github/src/main.py:# TODO: retry
grep: /github/: stopped after 5000 files (walk_limit); narrow the path
```
