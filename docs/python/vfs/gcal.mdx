`GCalVFS` mounts every calendar an account can see: each calendar becomes a
folder of days, and each event a `.gcal.json` file holding the Calendar API's
JSON. Set up the credentials as in [Google Workspace setup](/home/setup/google).

## Install

```bash
pip install mirage-ai
```

## Configure

```python
import os

from mirage import MountMode, Workspace
from mirage.vfs.gcal import GCalConfig, GCalVFS

config = GCalConfig(
    client_id=os.environ["GOOGLE_CLIENT_ID"],
    client_secret=os.environ["GOOGLE_CLIENT_SECRET"],
    refresh_token=os.environ["GOOGLE_REFRESH_TOKEN"],
)
ws = Workspace({"/gcal": GCalVFS(config)}, mode=MountMode.READ)

result = await ws.shell("ls /gcal && grep -lw standup /gcal/primary/2026-11-*/*.gcal.json")
print(await result.stdout_str())
await ws.close()
```

`bucket_days=7` or `30` makes each folder 7 or 30 days, `time_zone` sets
the zone days are cut in, and `start_time` and `end_time` limit the mount to a
time range. A `MountMode.WRITE` mount also allows `rm`.

## Authentication

Credentials come from the first of:

1. `access_token`, a token or a callable that returns one.
2. `client_id` and `refresh_token`, with `client_secret` unless the client
   uses PKCE. Mirage trades the refresh token for access tokens on its own.

The mount needs the Google Calendar API with the
`https://www.googleapis.com/auth/calendar` scope, or `calendar.readonly` for a
read-only mount. `rm` needs the `owner` or `writer` role on the event's
calendar; otherwise it fails with `Permission denied`.

## Behavior

- **Time range:** `ls` of a calendar lists days from all its history through
  90 days ahead. A date glob such as `ls /gcal/primary/2027-03-*` lists its
  own range, past that horizon. `start_time` and `end_time` (RFC 3339 with a
  timezone) limit every listing, path, glob and read; dates outside them are
  absent.
- **Days:** a well-formed date inside the range is a folder even when it holds
  no events. One zone covers the whole mount, the primary calendar's unless
  `time_zone` is set, so every calendar's `2026-11-16/` covers the same hours.
- **Calendars listed:** `min_access_role` (`freeBusyReader`, `reader`,
  `writer` or `owner`) hides calendars where the account has less access.
- **Free/busy calendars:** Google returns no titles for a calendar shared as
  free/busy only, so its events read as `busy`.
- **Delete:** on a `write` mount, `rm` on an event file deletes the event for
  every attendee. Creating, editing and moving events go through the
  [`gws calendar`](/python/cli/gws) CLI, which takes the calendar and event
  ids the tree shows. A written event must carry an explicit UTC offset or
  time zone.

## Integration

Google Calendar answers these commands through its own API, so fewer files
are read. See [Integration](/home/integration/overview).

- `grep -r` and `rg` with `-w`: Calendar's event search names the event files
  to read, together with the text the listing keeps, so no match is missed.
  Every file is read when the search fails or finds nothing, and files other
  than events (`calendar.json`) are always read. `walk_limit: -1` in the
  mount's `"@all"` [command limit](/home/limits#command-output) turns the search
  off and reads every file.
