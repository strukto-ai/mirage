`NotionVFS` mounts the Notion pages and databases shared with a connection as
read-only JSON files: pages with their content as Markdown, and databases with
their schema and rows. Set up the token as in [Notion setup](/home/setup/notion).

## Install

```bash
pip install mirage-ai
```

## Configure

```python
import os

from mirage import MountMode, Workspace
from mirage.vfs.notion import NotionConfig, NotionVFS

config = NotionConfig(api_key=os.environ["NOTION_API_KEY"])
ws = Workspace({"/notion": NotionVFS(config)}, mode=MountMode.READ)

result = await ws.shell("tree -L 3 /notion && grep -r deadline /notion/pages")
print(await result.stdout_str())
await ws.close()
```

`base_url` points at a proxy. `api_version` sets the `Notion-Version` header,
`2025-09-03` when unset.

## Authentication

The token is an internal connection's API token (`ntn_...`) with the read
content capability. The connection reaches only the pages and databases
shared with it; child pages inherit access, so sharing a top-level page
exposes its whole subtree. A personal access token with the **Notion API**
capability also works: it acts with its creator's permissions and needs no
sharing. The update and insert content capabilities are only for writes
through the [`ntn`](/python/cli/ntn) CLI.

## Layout

```text
/notion/
  pages/
    Engineering_Wiki__<page-id>/
      page.json
      Onboarding__<child-id>/
        page.json
  databases/
    Roadmap__<database-id>/
      database.json
      Roadmap__<data-source-id>/
        data_source.json
        rows.jsonl
```

Titles are sanitized and end in `__<id>`, so `ls` the parent instead of
building a path. `pages/` mirrors Notion's page tree, with child pages as
nested folders. Since the `2025-09-03` API, a database is a container of one
or more data sources, so `databases/` is one level deeper. A single-source
database repeats its name, since Notion names the data source after its
database.

- **`page.json`:** a page, a database row included. Blocks render to
  `markdown` and stay raw under `blocks`; blocks with children embed them
  under `children`. A row's cell values are under `properties`, as Notion's
  own property objects; a standalone page's `properties` holds only its
  title.
- **`database.json`:** the container: `database_id`, `title`, `url`,
  timestamps, `parent`, `archived`, `is_inline` and the `data_sources` that
  name the folders beneath it. It carries no `properties`.
- **`data_source.json`:** the typed column schema under `properties`, with no
  rows. A data source id is not its database id; `ntn datasources resolve
  <database-id>` turns one into the other.
- **`rows.jsonl`:** every row, one JSON object per line in query order: the
  row's `page.json` without the body, plus `path`, where that `page.json` is
  below the data source folder.

```bash
jq -r 'select(.properties.Priority.number > 1) | .title' "$DS/rows.jsonl"
grep -c '"checkbox":true' "$DS/rows.jsonl"
cat "$DS/$(jq -r 'select(.title == "Write spec") | .path' "$DS/rows.jsonl")"
```

## Behavior

- **Read only:** the mount cannot change pages. Use the [`ntn`](/python/cli/ntn)
  CLI, which takes the same token, to create, edit and trash pages, query data
  sources and reach every other route. Ids
  are positional: use the `<page-id>`, `<database-id>` or `<data-source-id>`
  from a path segment.
- **Rows in one file:** a query answers a hundred rows' cells in one call,
  while each row folder costs calls of its own, so rows are one file and
  `grep -r` or `find` over a large database stays cheap. Row folders are not
  listed; open one by the `path` on its line. Reading `rows.jsonl` costs one
  query call per hundred rows.

## Integration

Notion answers this command through its own API, so less is read. See
[Integration](/home/integration/overview).

- `head -n N`: renders only the first N rows.
