A mount with a kernel `backend` also shows as a folder on the machine running
Mirage, so editors, `git` and any other program read and write it like a local
folder. The [FUSE overview](/home/setup/fuse) lists what each OS supports.

## Install

<Steps>
  <Step title="Install FUSE for the OS">
    Follow the [Linux](/home/setup/linux), [macOS](/home/setup/macos) or
    [Windows](/home/setup/windows) guide. Windows is experimental.
  </Step>
  <Step title="Add the extra">
    ```bash
    uv add "mirage-ai[fuse]"
    ```
  </Step>
</Steps>

## Mount a folder

```python
from pathlib import Path

from mirage import Mount, MountBackend, MountMode, RAMVFS, Workspace

with Workspace(
    {"/data": Mount(RAMVFS(), mode=MountMode.WRITE, backend=MountBackend.FUSE)}
) as ws:
    folder = Path(ws.fuse_mountpoints["/data"])
    (folder / "hello.txt").write_text("hello\n")
    print(sorted(p.name for p in folder.iterdir()))   # ['hello.txt']
```

- The constructor returns once every folder is live, so the folder is ready
  inside the `with` block. Leaving the block unmounts it.
- `ws.fuse_mountpoints` maps each prefix to its folder, a fresh
  `/tmp/mirage-*` directory unless the mount sets `mountpoint`.
- The folder follows the mount's mode: a `read` mount cannot be written.

<Accordion title="In async code, never block the workspace's loop on the folder">
  The folder is served on the workspace's event loop. A synchronous `open()`
  on that loop, or a subprocess started with `cwd` inside the folder, waits
  on a call only that loop can answer. Use `asyncio.to_thread`, or pass the
  folder's paths as arguments. A workspace first used in a `with` block, or
  run by a [`WorkspaceRunner`](/python/access/server#on-its-own-event-loop)
  or the server, has a loop of its own, so blocking calls are fine there.
</Accordion>

## Backends

Each mount picks its own `backend`:

| `backend` | The mount is | Runs on |
| --- | --- | --- |
| `workspace` (default) | only inside Mirage | everywhere |
| `fuse` | also a folder, through FUSE | Linux, macOS, Windows (experimental) |
| `fskit` | also a folder, through FSKit with no kernel extension | macOS 15.4+ |
| `nfs` | also a folder, read-only, through the OS's NFS client and no FUSE install | Linux (as root) and macOS |

```yaml
mounts:
  /data:
    vfs: ram
    mode: write
    backend: fuse
    mountpoint: /tmp/data   # omit for a temp directory
  /s3:
    vfs: s3
    backend: nfs
  /logs:
    vfs: disk               # no backend: stays inside Mirage
```

<Warning>
  macOS allows one FUSE mount per process: a second one fails with
  `fuse: cannot register signal source`. Put a kernel backend on one mount,
  or run the others in separate processes.
</Warning>

## Behavior

- **Files of unknown size.** Slack, Linear, Trello and other API-backed
  mounts cannot size a file without fetching it, so it stats as 0 bytes until
  something opens it, like a `/proc` file. `cat`, `grep`, `cp` and `wc -c`
  read it in full. `ls -l`, `du` and `find -size` show 0 until it is opened,
  and `tar` or `rsync` copy it empty. Mirage never fetches content during
  `stat`, which would cost one API call per file on every `ls -l`. On
  Windows, opening the file to stat it fetches it, so the size shows at once.
- **Symlinks.** Links made with `ln -s`, in the Mirage Shell or in the
  folder, show as real symlinks and resolve inside the folder.
- **Permissions.** The mode bits `chmod` and `chown` set are for display.
  Mount modes and policy decide access, never the kernel.
- **Extended attributes.** `getfattr` and `setfattr` in the folder read and
  write the same attributes as the Mirage Shell, on every VFS.

## FSKit on macOS

Apple is phasing out kernel extensions, and on Apple Silicon the macFUSE
kext needs a reduced-security boot. With macFUSE 5 on macOS 15.4+,
`backend: fskit` serves the same folder through FSKit instead, with no kext:

```python
from mirage import Mount, MountBackend, MountMode, RAMVFS, Workspace

with Workspace(
    {"/data": Mount(RAMVFS(), mode=MountMode.READ, backend=MountBackend.FSKIT)}
) as ws:
    print(ws.fuse_mountpoints["/data"])   # /Volumes/mirage-...
```

- The folder is a volume under `/Volumes`. macOS creates it and removes it on
  unmount, and refuses a `mountpoint` anywhere else.
- Every VFS on an FSKit mount must know its files' sizes: a file that stats
  0 before it is opened reads as empty. Byte stores (RAM, Disk, Redis, S3,
  GridFS) and Linear qualify; Mirage warns at mount time about any other.
- `fskit` raises on other OSes; there is no automatic choice between it and
  `fuse`.

<Warning>
  Treat FSKit mounts as read-mostly. The macFUSE FSKit layer can write new
  files as NUL bytes with no error, so Mirage warns on a writable FSKit mount;
  use `fuse` for writes. Two more open macFUSE issues: a binary on the volume
  runs only after it has been read once
  ([#1181](https://github.com/macfuse/macfuse/issues/1181)), and new entries
  in the volume root may not appear in a live mount
  ([#1165](https://github.com/macfuse/macfuse/issues/1165)).
</Warning>

[`examples/python/fuse/fskit.py`](https://github.com/strukto-ai/mirage/blob/main/examples/python/fuse/fskit.py)
runs an FSKit mount end to end: the size warning, reads, and each write with
its result.
