`monty`, `wasi` and `local` run `python3` on your own machine. A **sandbox
runtime** runs selected programs inside another machine: a container, a
microVM, a cloud sandbox or an SSH host. Use one when a line needs a real OS,
heavy packages or a GPU. Mirage connects to a machine you started; it never
creates, sizes or deletes one.

| Runtime | Connects to | Config |
| --- | --- | --- |
| [`docker`](/python/runtime/sandbox/docker) | A container you started (`docker run`) | `container`, `mount_type` |
| [`apple_container`](/python/runtime/sandbox/apple_container) | A container under Apple's [`container`](https://github.com/apple/container), or one per agent | `container`, `containers` |
| [`smolvm`](/python/runtime/sandbox/smolvm) | A [smolvm](https://smolmachines.com) microVM you started | `machine` |
| [`daytona`](/python/runtime/sandbox/daytona) | A [Daytona](https://www.daytona.io) sandbox you created | `sandbox_id`, `api_key` |
| [`e2b`](/python/runtime/sandbox/e2b) | An [E2B](https://e2b.dev) sandbox you created | `sandbox_id`, `api_key`, `mount_type` |
| [`ssh`](/python/runtime/sandbox/ssh) | Any machine running sshd | `host`, `username`, `identity_file` |

A Docker container shares its host's kernel; an Apple Container and a smolvm
microVM each boot their own. [Sandlock](/python/runtime/sandbox/sandlock)
instead confines a program on the local Linux host.

## What goes to the sandbox

A sandbox runtime defaults to `captures: ["@external"]`: a program name
Mirage does not resolve runs in the sandbox, and Mirage's own commands, pipes
and redirects stay in the workspace.

- `python3 job.py | grep error > /logs/errors` sends only `python3`; Mirage
  runs `grep` and writes the file.
- `captures: ["python3", "node", "@external"]` also sends those interpreters.
  `captures: ["*"]` sends the whole line.
- Builtins such as `cd`, `export` and `echo` stay in Mirage even when named.
- A named capture is a program: `which gcc` prints `/usr/bin/gcc`, a file
  naming its runtime. A name only `@external` takes has no file, so `which`,
  `command -v` and `type` report it missing, and running it still works.
- Unquoted globs expand against the workspace first (`python3 job.py *.csv`
  runs `python3 job.py a.csv b.csv`), and command rules judge that argv. The
  script is a file operand, judged on `job.py` however it is spelled.

## The workspace inside the sandbox

A program in the sandbox opens files at the same paths as the host
workspace, so the sandbox must see the mounts at the same prefixes. Mirage
rewrites nothing: the line, its cwd and every path pass through as typed.
`docker` and `e2b` can serve the mounts themselves, by `mount_type`:

| `mount_type` | What the sandbox sees |
| --- | --- |
| `ssh` | Every prefix the session sees, served from this workspace over SFTP and mounted with `sshfs`. |
| `fuse` | Only what a Mirage inside the sandbox serves. |
| `both` | The sandbox's own mounts where it has them, this workspace's everywhere else. |
| unset | Nothing from Mirage: serve it yourself, as under `fuse`. |

```yaml
runtimes:
  - name: e2b
    captures: ["python3"]
    config:
      sandbox_id: ${E2B_SANDBOX_ID}
      mount_type: ssh
  - workspace
```

### Served from the workspace (`ssh`)

- The first captured line mounts each prefix, later lines follow mounts added
  or hidden since, and closing the workspace unmounts them.
- Every file operation in the sandbox is one of the line's session: hides,
  mount modes and path rules hold, and a host change shows at once. RAM and
  local-disk mounts work like any other.
- The sandbox needs only `sshfs` (`apt-get install sshfs`) and FUSE: no
  Mirage, no credentials. A Docker container needs
  `--device /dev/fuse --cap-add SYS_ADMIN`.
- Each file operation is a round trip to this workspace (about 150 ms for a
  small file from a laptop to E2B), so keep bulk data in the sandbox with
  `both`.
- The mounts show one session: the first that runs a line there. Another
  session's line is refused, so give each agent its own sandbox.
- The root mount and `/dev` are not served; the sandbox's own come first.

### Served by the sandbox itself (`fuse`)

Run Mirage inside the sandbox with the same mounts at the same prefixes,
each FUSE-mounted at its prefix:

```yaml
# sandbox.yaml, inside the sandbox
mounts:
  /data:
    vfs: s3
    config:
      bucket: my-bucket
      aws_access_key_id: ...
      aws_secret_access_key: ...
    backend: fuse
    mountpoint: /data
```

```bash
mirage workspace create sandbox.yaml # in the entrypoint, or once by hand
```

- Inside the sandbox, `/data` is a real directory: a read pulls from the
  backend and a write streams back, with no sync step.
- The sandbox config can differ from the host's where it should: an endpoint
  (`host.docker.internal` instead of `127.0.0.1`), scoped-down credentials.
  None of it crosses the provider's exec API.
- Keeping the prefixes in step with the host is your job; a mismatch shows
  only when a path misses.
- The image needs `fuse3` and Mirage with your backends
  ([The sandbox image](#the-sandbox-image)).

A prefix the sandbox serves itself follows the sandbox's config, mount modes
included, and this workspace's rules never see it. So under `fuse` and
`both`, a line is refused while the session's profile hides or narrows
anything under such a prefix, a whole hidden mount included. Under `both`, a
sandbox mount nested inside a prefix this workspace serves fails loud, since
serving the prefix would cover it.

<Note>
  The `ssh` runtime can skip all of this when the files live on the SSH
  machine: mount them with the ssh VFS at a prefix equal to their remote path.
  See [Skip the FUSE](/python/runtime/sandbox/ssh#skip-the-fuse).
</Note>

## The sandbox image

The repository's Dockerfile builds an image with `fuse3` and Mirage from the
current checkout:

```bash
docker build -f docker/sandbox/Dockerfile --target fuse -t mirage-python-fuse .
```

It installs the `sandbox` extra (every mountable backend plus FUSE). Narrow
it to the backends you use:

```bash
docker build -f docker/sandbox/Dockerfile --target fuse \
  --build-arg MIRAGE_EXTRAS=s3,postgres -t mirage-fuse-lean .
```

The same image serves every provider: run it under Docker, Apple's
`container` (`container build`, same flags) or smolvm, or use it as a Daytona
image or snapshot, or an E2B template base. Add the programs your captures
need, such as Node.js for `node`. The host application can use either SDK.

## Selecting in YAML

A sandbox runtime is a `runtimes` entry like any other, with a `config`
block describing the machine:

```yaml
runtimes:
  - name: docker
    captures: ["python3"]
    config:
      container: my-sandbox
  - workspace
mounts:
  /data:
    vfs: s3
    config:
      bucket: ${AWS_S3_BUCKET}
```

## Resource limits

`command_limits` apply to a sandboxed program as to any command: past
`timeout_seconds` it exits 124, and `max_bytes` and `max_lines` cap its
output.

<Warning>
  A timeout stops Mirage waiting; it does not always stop the program. E2B
  tries to kill the command, but its descendants may survive. Other
  providers leave it running. Use the provider's own timeouts and lifecycle
  limits.
</Warning>

## Route-policy scripts

A sandbox runs programs but does not evaluate expressions, so it cannot run
a [route-policy script](/home/policy/route-policy). Subclass it and implement `eval`
with your own transport, as the
[docker eval examples](https://github.com/strukto-ai/mirage/tree/main/examples)
do by piping a harness to the container's `python3 -`.
